# Threat model: connected apps, MCP and outbound webhooks (FL-780)

Status: audit of shipped code, November 2026. Planned as a spike before the features were built; FL-803 (OAuth 2.1
apps, PR 1005), FL-844 (MCP server, PR 1053), FL-819 (signed event webhooks, PR 1013) and FL-1420 (SSRF guard on every
hop, PR 1063) have since merged, so this document checks that code against the threat model.

Verdicts: **Mitigated** (code and a test cited), **Partly** (some of it), **Missing**. Paths are relative to `server/`.
Line numbers are as of this branch.

## 1. Scope

In scope:

- OAuth authorization endpoint: `GET oauth/apps/authorize`, the Allow page (`/auth/allow-app`) and
  `POST oauth/apps/authorize[/start]`.
- Token endpoint and revocation: `POST oauth/apps/token`, `POST oauth/apps/revoke`.
- Dynamic client registration (RFC 7591): `POST oauth/apps/register`; administrator registration
  `POST admin/oauth/apps`.
- Use of app tokens on the REST API (`AuthService.authenticate`).
- MCP transport: `POST/GET /api/mcp`, `/api/mcp/assistant`, `GET /api/mcp/preview`.
- Each MCP tool (`src/services/mcp.service.ts`).
- Webhook delivery: the core plugin's webhook step for photo triggers and Frameleaf event triggers
  (`src/services/workflow-execution.service.ts`, `src/utils/public-fetch.ts`, `src/utils/workflow-event.ts`).

Out of scope: Connect (`/api/connect`, Lightroom) beyond the shared OAuth code, Frameleaf Cloud's broker
(`mcp.frameleaf.cloud`), the relay edge itself, and the web Allow page's wording.

## 2. Assets

| Asset                                                                            | Why it matters                                                                               |
| -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Library content: photos, thumbnails, originals                                   | The product. Originals are the most sensitive.                                               |
| Library text: file names, captions, OCR, album/people/place names                | Private, and attacker-controllable (a shared photo's caption) so a prompt-injection carrier. |
| Locked and rule-hidden items                                                     | Shared only with partners. Never with an app, in any session state.                          |
| GPS                                                                              | Partners see each other's GPS; apps acting for a non-owner do not.                           |
| Access and refresh tokens, authorization codes, PKCE verifiers                   | Bearer credentials.                                                                          |
| Webhook signing secrets and header values                                        | Let a receiver trust a message.                                                              |
| The home network (Home Assistant, router, NAS admin) and cloud metadata services | Reachable from the server, not from the internet.                                            |
| Account activity (audit log)                                                     | How a person sees what an app did.                                                           |

## 3. Actors and trust boundaries

Actors: the signed-in person; an app (a public OAuth client: an AI assistant connector, Home Assistant, a desktop
app); an AI model driving an MCP client; a hostile app that registered itself; a hostile web page in the person's
browser; whoever wrote text into the library (a partner, a shared-album member, a file name from a camera or a
download); a webhook receiver; an attacker on the network path.

Boundaries:

1. Internet or LAN to the API (relay, direct, or home). Remote use requires a Frameleaf sign-in
   (`AuthService.applySessionPolicy`, `src/services/auth.service.ts:1323`).
2. App to Frameleaf: everything an app sends (tool arguments, token requests, registration metadata) is untrusted.
3. Library text to the model: content goes out through MCP and must not be read as instructions.
4. Frameleaf to the outside: webhook deliveries leave the server; the destination is typed by the owner.
5. Browser to the Allow page: the only place consent is given.
