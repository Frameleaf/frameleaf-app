title: Studio import publication qualification

The publication qualification utility is a pure structural gate. It validates both profiles, refuses missing approved evidence references or disabled PostgreSQL durability flags, and compares the normalized configuration. It does not qualify any deployment. The default durability adapter remains `UNQUALIFIED`; no writer is enabled by this utility or its synthetic tests.

Every configuration string must contain nonblank text, contain no Unicode control/format characters, and fit within 1024 characters. Profiles and database objects are strict: missing fields, unknown fields and coerced booleans refuse. Approved evidence references contain 1–64 entries; observation references may be empty but must otherwise follow the same format. Each reference is at most 2048 characters and is either `sha256:` followed by 64 lowercase hexadecimal digits or an absolute HTTPS URL without credentials, whitespace, controls, backslashes, query or fragment. SHA-256 references preserve offline/private immutable receipts. HTTPS references identify hosted receipts. Neither format establishes review or authenticity, and the utility never fetches a receipt.

Schema parsing determines field order, including database fields. Comparison excludes evidence references, allowing observations without receipt references and avoiding JSON insertion-order drift. All configuration fields remain bound, including PostgreSQL WAL storage and the tested failure boundary. Malformed profiles throw `storage_unqualified`; false `fsync`, `synchronousCommit` or `fullPageWrites` on either valid profile throws `database_durability_unqualified`; any other configuration difference throws `storage_qualification_changed`.

The authenticated deployment owner must supply an approved profile only after independently checking actual evidence. Clients and uploads must never submit profiles. The future owner boundary must provide these checks before this function can be used for publication:

| Obligation                                  | Binding and owner responsibility                                                                                                                                                                                                                                                                     |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Server and adapter versions                 | `serverVersion` and `adapterVersion` bind exact reviewed implementations.                                                                                                                                                                                                                            |
| Runtime, kernel and architecture            | `runtime` carries the exact runtime/kernel versions; `architecture` binds the architecture. The owner observes their truth. No dedicated kernel field exists.                                                                                                                                        |
| Namespace identity and bridge               | `mountIdentity`, `rootIdentity`, `linkDomain` and `bridge` bind the actual namespace and exact bridge/backend version. The owner verifies namespace isolation and file/ancestor/link/unlink evidence.                                                                                                |
| Backing storage and options                 | `backingStorage` and `storageOptions` carry exact device, driver/filesystem/storage versions and relevant policy, including mover, dataset and flush options. Changed facts must change these values.                                                                                                |
| Database durability                         | Boolean fields and `database.walStorage` bind the observed PostgreSQL policy and WAL storage. Truth and durable commit behavior still require independent observation.                                                                                                                               |
| Evidence review and expiry                  | The owner resolves SHA-256 references or HTTPS receipts to independently reviewed bytes, checks dates/currentness and expiry, and refuses absent, unreviewed, expired or mismatched records before calling the gate. No review, signature, date or expiry field exists in this structural interface. |
| Full-storage propagation and phase receipts | The owner checks that the evidence proves actual file and namespace barriers through every layer and all required publication phases at `failureBoundary`. A guest sync success or one syntactically valid reference does not establish those facts.                                                 |

The test source covers structural refusal when the approved evidence packet is absent, configuration drift including kernel details carried in `runtime`, malformed references and disabled database policies. It cannot distinguish a real namespace/host-propagation/phase receipt from an invented well-formed reference. Neither matching strings nor a pure unit pass can prove authenticity, expiry, host propagation or crash durability.

Task12 still requires separately owned observed qualification packets for Linux EXT2/3/4, XFS and Btrfs; Linux ZFS/TrueNAS; DSM; the configured Unraid pool and share/mover/underlying path chain; APFS Desktop host-bind and VM-disk profiles; Windows/WSL/full VM; and every additional documented configured Unix-compatible namespace. A tuple qualifies only its exact stack, with the existing support level and database exclusions. APFS host-bind needs authoritative semantics and observed host full-storage propagation, or a separately designed and reviewed root-scoped adapter before it can qualify. No filesystem label, easier VM tuple, unsupported fallback or synthetic receipt closes a missing target.

Execution of real crash workers at every prepare/target/cleanup barrier, migrated PostgreSQL integration, cancellation/reference/Buddy races, reload/bundle persistence, producer/SDK checks and final integrated acceptance remain required. Process restart evidence cannot claim physical power-loss durability. The source gate and test fixtures are not qualified deployment manifests, runtime evidence, a release command or a completed Task12 acceptance result.

## Test-only crash hooks and executable Linux worker

`studio-import-faults.ts` defines the eight approved boundaries. The file repository invokes the six file/namespace hooks after the corresponding operation completes; `retainImport` invokes prepare/final commit hooks after the journal acknowledges the commit. They are injected internal dependencies with an inert default. No API field, public endpoint, environment switch in product code or qualification toggle installs them. A hook rejection preserves the existing error and cleanup ordering. A published result's cleanup failure remains journal-discoverable.

`test/fixtures/studio-import-barrier-faults.ts` parks at one actual hook. `studio-import-crash-bootstrap.mjs` is launched directly with Node, using only builtin static imports and no loader preload. It parks before tsx or worker loading; after the driver verifies and migrates the exact child and sends its release, the bootstrap independently checks membership, registers tsx, and imports `studio-import-crash-worker.ts`. Transform helpers therefore start only inside the admitted lane. The worker uses the real `retainImport`, durable SQL journal and `StudioImportFileRepository` with actual Linux adapter primitives. Its adapter qualification receipt is **deliberately synthetic and test-only**: it permits controlled process-restart testing in the fixture, and never certifies storage or enables the default writer. The worker creates a detached descendant before publication; direct-child death or process-group absence cannot pass this test.

`studio-import-crash-driver.py` adapts the reviewed owner-bound cgroup descriptor route from `linux-owner.py` in the FL139 Linux acquisition source packet. It consumes an existing private Root-owned record, authenticates its boot/source/driver/guardian/cgroup/scratch identities, starts a nonroot child parked before application execution, checks its unreaped PID birth and privilege state, migrates that exact child into the pinned root-owned lane, and only then releases it. It verifies the detached descendant is in the lane and uses the pinned `cgroup.kill` descriptor followed by `cgroup.events populated=0` readback. It never uses `killpg` as descendant closure. The [kernel cgroup v2 documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html) specifies subtree kill behavior, fork/migration handling and migration permission requirements; deployed-kernel admission and observed containment controls remain required.

The restarted worker reconnects to the same fixture database with a new one-connection pool, reads the actual receipt, cancels unfinished intents, and calls the real journal/file release path. Before-prepare scratch uses the real journal's owner/path/reference cleanup guard with an accelerated stale-file threshold and existing exact-file checks. The parent independently checks committed receipt/ready rows, cleanup flags, bytes, SHA-256, inode/link identities, preserved lineage and a foreign same-hash inode. It does not infer durable outcomes from the reported barrier sequence. The parent pool is limited to one connection for this opt-in route; the worker has one, preserving the combined two-connection bound and existing SQL/lock limits. No database server is crashed.

### Pure checks available without a runtime window

From the repository root, with prepared dependencies:

```sh
node studio/tools/prepare-server-subtitle-runtime.mjs
node server/node_modules/vitest/vitest.mjs run --config server/test/vitest.config.mjs server/src/utils/studio-import-faults.spec.ts server/src/services/studio-import-publication.service.spec.ts server/src/repositories/studio-import-file.repository.spec.ts
python3 server/test/fixtures/studio-import-crash-driver.py --self-test
node --test server/test/fixtures/studio-import-crash-bootstrap.test.mjs
```

These are synthetic controls. The Python self-test validates record refusal and mocked kernel-closure outcomes; it does not open a cgroup, spawn a worker, signal a process, access PostgreSQL or qualify containment. The bootstrap controls reject missing, wrong and unreadable membership before invoking a mocked loader, model helper inheritance after readback, and statically check the direct Node launch and builtin-only imports. No helper or worker is launched by these controls. Neither these checks nor TypeScript/parse checks count as a real crash run. The later runtime admission must include cold-cache tsx/esbuild helper membership and pre/post-release failure closure checks; pure controls do not qualify those kernel outcomes.

### Later Root-owned Linux runtime window

The executable medium entry point is the existing `test/medium/specs/services/studio-import-retention.service.spec.ts`, using `test/vitest.config.fl111.mjs`. Its crash cases are explicitly skipped when `FL111_CRASH_OWNER` is absent. A skip is missing evidence. Root must review and provide the finite runtime/SQL window, migrated PG19 template, exclusive test storage namespace, readable exact source/dependencies/Node/tsx, private socket/authentication access for the nonroot worker, and independently armed cleanup before executing it.

The lane record is `/run/fl111-crash-<32 lowercase hex nonce>/owner.json`, a regular Root-owned 0600 file in a nonsymlink Root-owned 0700 directory. It binds `nonce`, `bootId`, exact `sourceHead` and `sourceTree`, SHA-256 of the driver, worker and builtin bootstrap (`driverSha256`, `workerSha256`, `bootstrapSha256`), `workerUid`/`workerGid` greater than zero, `scratchRoot` and its `{device,inode,uid:0}` identity, `controlGroup` `/fl111_crash_<nonce>.slice` and its same-shaped root identity. It also binds `driverUnit` `fl111-crash-driver-<nonce>.service`, `driverControlGroup` `/system.slice/<driverUnit>`, its actual `driverInvocation`, `guardianUnit` `fl111-crash-guardian-<nonce>.service`, and its actual `guardianInvocation`. Both invocation IDs are 32 lowercase hexadecimal digits. `expiresAt` is an absolute Unix time no more than 600 seconds ahead. The driver and guardian must be active with `RuntimeMaxUSec` exactly `2min` and `10min`, respectively. `NoNewPrivileges` must be inherited by the nonroot worker; its effective/permitted/inheritable/ambient capabilities must be zero. Its supplementary groups are removed.

Root must independently verify that the guardian actually kills/readbacks this exact lane on driver death, expiry or cancellation, and that the worker has no cgroup migration/delegation, namespace or privilege escape route. The leaf lane starts empty, has no subtree controllers, stays Root-owned without group/other write permission and cannot contain the driver. The private scratch root must permit traversal by the worker, retain its recorded root ownership/identity and remain exclusively allocated. Each case creates one private `case-*/exports` subtree owned by the worker. The driver provisions no systemd units, cgroups, mounts, users, capabilities, guardian, socket, grants or PostgreSQL server. The record describes an already admitted window; it is not a source-generated grant or authenticity/qualification proof. Missing or replaced bindings refuse.

Inside that reviewed driver service, from `server/`, the future command is:

```sh
FL111_CRASH_OWNER=/run/fl111-crash-<reviewed-nonce>/owner.json \
IMMICH_TEST_POSTGRES_URL='<root-owned migrated template URL>' \
node node_modules/vitest/vitest.mjs run --config test/vitest.config.fl111.mjs test/medium/specs/services/studio-import-retention.service.spec.ts
```

Use the actual private nonce and URL from the reviewed window; the placeholders are not executable evidence. Preserve the Root controller/guardian receipts and actual source/identity/hash observations outside product data. A driver failure or unknown populated-zero closure prevents recovery and test deletion; the guardian owns residual reconciliation. The test deletes only its exact success-verified fixture paths after both process closures and reference-guarded recovery. It retains failed fixtures for the Root owner's handoff. Unknown crash closure also preserves the SQL clone after closing the parent pool; it never drops a database an unresolved worker may still own.

This is a first Linux **process-restart** harness. No real worker crash, native admission, migrated SQL, VM/storage-loss test or supported-platform qualification was performed to prepare its source. Actual descendant admission, cancellation/deadline/driver-loss controls, real SQL/file recovery at all eight points, and review of the assembled runtime packet remain gates. Full Linux/TrueNAS/DSM/Unraid/APFS host-bind/APFS VM-disk/Windows-WSL/full-VM/other documented Unix coverage, shared-reference/Buddy/race cases and integrated acceptance remain Task12 scope. A process pass cannot fill a missing full-storage/namespace/host-propagation receipt or certify physical power-loss survival. The default writer stays `UNQUALIFIED` until separately reviewed target-specific evidence exists.
