# Administrative iCloud edit authority

The owner-session edit APIs accept a specific baseline or successor using verified local receipts and current bytes. An administrative decision is an owner-confirmed binding, not an Apple revision, source chronology, or proof that two sources represent the same edit. Changing an opaque native version token does not establish chronological order. Automatic source successor selection and qualification against the current Apple baseline remain separate requirements.

First call `GET /api/icloud-sync/edits/evidence?assetId=<owned asset UUID>` with the owner's authenticated session. API keys and shared links cannot use this workflow. Discovery does not refresh PIN elevation. Every response is `Cache-Control: private, no-store`. The complete bounded snapshot separates stored receipts, current administrative authority, owned holders and live claims, and incoming verified candidates. It exposes no credential, raw provider URL, managed filename, or local path. Protected assets and hidden incoming candidates require current access and elevation. An oversized item is refused rather than silently truncated. `admissionGuaranteed: false` means the snapshot is not a future publication grant; decisions recheck all evidence and authority under their transaction fences.

An original receipt's empty `nativeVersion` is an actual stored fact. Its `suggestedAdministrativeLabel: "administrative-original"` supplies an explicit administrative baseline label; that label must never be described as a provider revision. Edit receipt tokens remain opaque. Submit `POST /api/icloud-sync/edits/baseline` with a new `requestId`, the discovered `receiptId`, the expected authority generation (zero when absent), the owned device or sync holder, a source-incarnation UUID for the accepted source, and the explicitly accepted version label/token. The response is an administrative decision ID, generation, and canonical version ID. An unhealthy prior owner is subject to the 72-hour automatic handover boundary; `takeOver` is an explicit manual handover and cannot bypass a healthy owner or a live competing claim.

Submit `POST /api/icloud-sync/edits/successor` with a new `requestId`, the expected generation and current version ID, and the discovered verified device or sync resource. The default `keep` policy retains at most twenty active edited assets for the whole item, independently of connection. The immutable original is separate. Identical bytes in an unrelated asset are not a canonical binding. Reusing a previous render requires explicit `reuseVersionId` acceptance of its actual current digest, ownership, status and access. Missing proof, stale authority, ambiguity, or an unavailable canonical asset requires review. Request replay compares the immutable actual receipt/digest binding before returning the old acknowledgement. An already committed upload may settle after handover without publishing again or changing the canonical primary.

Each edited stack member needs its own accepted item ledger, actual same-byte receipt, current owned bytes and access. Shared-family disagreement preserves a previously source-owned or manually selected primary only under the actual membership and primary fence. Unaccepted legacy renders require review; dates and hashes cannot supply missing edit ordering. Authority changes persist local relations dispatch and queue admission atomically. This local job does not enumerate or contact iCloud. Event delivery failure retains the transactionally committed relation event for a token-fenced retry; a cancelled or stale executor cannot publish relations.

The `supersede` option currently returns a review conflict. Implementing the reversible Trash policy, transaction-aware configuration resolution and primary protection remains required work. These APIs do not activate a live account, enable a provider worker, or claim full FL-296 or hardware acceptance.
