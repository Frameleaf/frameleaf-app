# Library import adapters

The multi-source importer is in Beta. The Manager offers PhotoPrism, Photoview, PiGallery2, Lychee, Nextcloud, Piwigo and LibrePhotos imports, and Ente Photos from an export folder the owner makes with the Ente CLI, to everyone with a Beta label (owner decision, FL-1149). Synology DSM is not offered. A schema reader passing its tests does not establish migration support for every version; see [Manager imports from other photo apps](#manager-imports-from-other-photo-apps).

## Manager imports from other photo apps

The Manager recognises a photo app by its image repository, not an exact image digest. It stops the app, then captures its database: a SQLite snapshot, or a dump of a MariaDB/MySQL/PostgreSQL database restored into a disposable container started from the source's own database image with no network. The offline preparation container shares only that restore container's network namespace and reaches it on `127.0.0.1`. Ente Photos has no container to stop: the owner exports it with the official CLI and the Manager mounts that folder read-only with no database at all (the `export` delivery); see [Ente Photos import contract](./library-import-ente.md#manager-import).

`frameleaf-admin prepare-library-import` takes a version 2 request with `action: "inspect"` or `"prepare"`. Each source kind has one adapter in `server/src/library-import/preparation/<kind>.ts`. Inspect reads the frozen source and reports accounts, counts and every reported difference without writing anything. Prepare hashes the originals from the read-only mount, derives owner intents from the source's login facts and the administrator's chosen email addresses, and publishes the sealed bundle for the common command.

Versions are not pinned. When the captured schema matches a qualified fixture the reader runs in its strict mode. Otherwise it runs best effort: version, schema and migration pins are skipped, integrity and relationship checks stay, and the import records `SOURCE_VERSION_UNTESTED`. The Manager suggests upgrading to the tested version first but lets the administrator continue. Photos, videos and albums must come across; other source data that cannot be represented is listed as a reported difference that the administrator approves. An account whose sign-in restrictions cannot be described is imported as restricted, never as an open account. A missing original refuses the import.

## Imported account authentication

Preserve accounts and compatible password/PIN verifiers where source authentication semantics have been qualified. Require explicit destination identities; an email collision must be rejected instead of adopting an existing account. Preserve source restrictions and multi-factor requirements: a readable hash alone does not authorize enabling a destination login. Source sessions, API keys, reset tokens and OAuth identity bindings are not transferred. Source administrative privileges do not grant destination administration. Existing `import-immich` password/PIN preservation remains unchanged.

The internal destination owner policy can retain a source account with acknowledged login restrictions while preserving any compatible local verifier. Such owners keep `importClaimPending` set and cannot sign in or redeem a password link. The policy requires complete source login facts and every matching restriction reason; a disabled account, disabled password login, required second factor or external identity, restricted owned-library access, or another known restriction cannot be replaced with an unrestricted preserve/claim policy. Missing or unknown privacy evidence still refuses import. Restricted-account counts distinguish retained verifiers from active sign-in capability.

Generic account claims require the retained owner mapping, protected owner inputs and valid activated proof. An ordinary permitted claim can proceed; a restricted policy, incomplete migration, damaged evidence or missing mapping remains blocked. Resolving unsupported source restrictions requires a separate reviewed recovery procedure. Restore generic accounts together with their complete migration journal and protected evidence; restoring user rows alone cannot preserve this policy. These destination checks do not establish source qualification or equivalent album/asset permissions.

The internal PhotoPrism, Photoview and PiGallery2 SQLite readers and LibrePhotos SQLite/PostgreSQL readers expose a separate `password` channel bound to explicit operation/source-owner/destination-owner IDs. Ordinary content records remain credential-free. Supported bcrypt and Django PBKDF2-SHA256 verifiers are wrapped with the destination bcrypt policy without knowing the plaintext password; source normalization is retained. The protected representation is stable across resume for the same mapping and is redacted when serialized or inspected. It can be checked through the existing Server login and password-change verifier. This is internal implementation, not a source compatibility claim or a complete account provisioning workflow.

The hosted PhotoPrism local-account check runs the pinned ARM64 application against its own disposable SQLite store. It verifies a real local administrator login and wrong-password rejection, stops the source, captures a consistent snapshot, requires the pinned schema/build and verifies the separately imported password against the same credentials and source user ID. The application runs as the runner user; staging credentials, containers, anonymous volumes and newly pulled unused images are removed through run-scoped cleanup. The native matrix also exercises the existing synthetic administrator with disabled, expired and deleted states, super-administrator overrides, local/default/empty/OIDC/LDAP provider values and all four supported MFA method aliases. Each case restores a stopped baseline store, including WAL files, before its controlled mutation; failed-login rate limits remain enabled and cannot accumulate across cases. It compares the application's login result with the retained account flags, expiry/deletion dates and independently readable compatible verifier. In the tested password-mode configuration, OIDC with a local verifier permits local login, LDAP rejects that local login, and OIDC plus MFA rejects a password-only login. These account cases do not qualify licensed roles, successful MFA challenges, external identity-provider authentication or sharing.

The same disposable native application also indexes two synthetic JPEG originals and receives manual captions, dates, locations, favourites, private state and an album through its API. Authenticated original downloads are compared against independently generated bytes; anonymous private-original downloads must be denied. With the source stopped and restart disabled, a separate native acceptance case snapshots its database, produces a protected common bundle, copies originals into a fresh canonical Frameleaf database and exercises the common preflight/run/verify/activation command. It independently checks imported bytes, ownership, private state, manual metadata, album membership and the compatible password without granting administrator access. Folder-album filters are materialized through the source API. The test checks durable regeneration scheduling; it does not execute model jobs. This is single-local-administrator copy-mode acceptance, not multi-user privacy, relocation, Manager browser or combined release qualification. The destination container and uniquely tagged database image share the source run's cancellation cleanup; pre-existing or in-use images are retained.

Use the internal `importClaimPending` flag when credentials cannot be securely transferred or their authentication requirements cannot be represented. Accounts with unavailable or incompatible credentials are created without a local verifier; compatible verifiers can remain retained while unresolved restrictions block login. A destination administrator must already exist.

Pending owners cannot sign in with a password, OAuth or Frameleaf, or authenticate through sessions, API keys or public links. An administrator uses the existing emailed, single-use password link to claim the account. This requires configured outgoing email and a public server address. Only the link hash is stored; changing the destination email invalidates the link. Redemption checks expiry after acquiring the account lock and activates the owner in the same transaction that removes stale sessions, API keys, identity links and public links. Imported sharing must be reconstructed separately after its permissions have been verified.

Existing accounts default to their previous behavior. A database downgrade refuses to remove the flag while any owner remains unclaimed. The common importer uses these account checks. Manager account mapping and full source/combined migration qualification remain under development.

## PHP account password formats

Lychee's admitted SQLite reader has a separate protected password channel for local accounts. LDAP accounts select secure claims; their cached credentials are not read. The Nextcloud reader recognizes local-account password versions `1|`, `2|` and `3|`. Unprefixed legacy Nextcloud verifiers remain unqualified.

The protected verifier supports qualified PHP bcrypt and Argon2i/Argon2id encodings. Argon2 parameters must match their complete canonical representation: extra parameters, key references, associated data and noncanonical encodings refuse preflight rather than being silently discarded. Supported Argon2 versions are 16 and 19, with 8–102,400 KiB memory (Django's Argon2 default), 1–10 iterations, 1–16 lanes, 16–64 output bytes and 8–64 salt bytes; memory must also satisfy the algorithm's lane minimum. These are implementation limits, not a complete application compatibility claim.

The native asynchronous `@node-rs/argon2` binding performs memory-hard work outside the event loop. Existing `async-lock` serializes that work, permits eight waiting verifications and bounds waiting to ten seconds. Overload and malformed stored settings fail closed. Ordinary native passwords and the existing source formats keep their current paths.

The synthetic interoperability fixture records the exact Lychee PHP 8.5.12 and Nextcloud PHP 8.5.10 image digests. Both generated version-19 Unicode/NUL vectors and independently verified version-16 vectors, including wrong-password refusal. Native cryptographic compatibility does not establish that a source account may sign in: LDAP, disabled accounts, multi-factor requirements and global authentication configuration still require separate controller qualification before activation. These checks still apply to Manager Beta imports.

### Piwigo account password formats

The admitted Piwigo reader provides a protected callback for explicitly mapped account passwords, separate from its media batches. Default PHPass and legacy MD5 credentials preserve the ability to use the source password under the destination bcrypt policy; neither plaintext nor the original verifier is stored. Guest accounts have no portable credential. Custom authentication, source login hooks and MFA remain activation gates; a compatible digest alone never authorizes enabling an owner. See [Piwigo account passwords](./library-import-piwigo.md#protected-account-passwords) for resource limits, native test provenance and the stricter legacy comparison.

## Internal common command

`frameleaf-admin import-library <action> --source <family> --config <private-file>` dispatches all ten source kinds through the same common importer. Actions are `preflight`, `run`, `status`, `resume`, `verify`, `rollback` and `abandon`; only `verify --activate` permits activation. The execution lock is acquired before application bootstrap. Offline initialization prepares the database and job handlers without starting media workers. The existing `import-immich` command remains compatible.

Mutating commands require Manager's matching installation and operation identity. When the importer requests source authority, Manager compares the installation, operation, destination, source identity/revision/schema, manifest checksum and file-plan checksum with its retained review, then runs the caller's live source-verification callback. A fresh challenge and matching reply travel over the existing command pipes; Server receives no Docker socket or new network endpoint. Missing, substituted, expired or disconnected authority fails closed. Status can inspect an existing journal without live Manager authority when no runner holds the execution lock. Errors retain migration records and do not imply that restarting the source is safe.

This connection does not qualify an adapter, establish ownership/privacy evidence, add source discovery or finish Manager account/storage review. Callers must supply qualified source evidence and real source fencing; manifest declarations are insufficient. Source setup, deferred content baselines for fast adoption and combined acceptance remain under development. The Manager drives this command for its Beta photo-app imports.

## Native application imports in Docker

Each Docker-runnable source has an end-to-end check that runs its pinned application, seeds synthetic photos through the application's own API or CLI (an album, captions, a favourite or rating where the application has one, and a local account), stops it with restart disabled, captures its database and imports the capture through the common command into a fresh destination. The check then compares every imported original's bytes, owner, caption, favourite/rating, capture time, album membership and the preserved account password with what the application reported.

| Source      | Script                                               | Source database            |
| ----------- | ---------------------------------------------------- | -------------------------- |
| PhotoPrism  | `server/scripts/qualify-photoprism-application.mjs`  | SQLite                     |
| Photoview   | `server/scripts/qualify-photoview-application.mjs`   | SQLite                     |
| Lychee      | `server/scripts/qualify-lychee-application.mjs`      | SQLite                     |
| PiGallery2  | `server/scripts/qualify-pigallery2-application.mjs`  | SQLite                     |
| Nextcloud   | `server/scripts/qualify-nextcloud-application.mjs`   | SQLite (Photos + Memories) |
| Piwigo      | `server/scripts/qualify-piwigo-application.mjs`      | MariaDB restore            |
| LibrePhotos | `server/scripts/qualify-librephotos-application.mjs` | PostgreSQL                 |

Each script requires `FRAMELEAF_NATIVE_IMPORT_RUN_ID` (`<number>-<number>`; PhotoPrism and Photoview keep their own run-ID variables) and a dedicated `TMPDIR` named `frameleaf-<source>-<run id>`, and removes only the containers, volumes, networks and images it labelled or pulled. The import half runs `library-import-lifecycle.spec.ts` in `native-<source>` mode with `test/medium/fixtures/library-import-native-<source>.mjs`, which shares `library-import-native-common.mjs`. The import runner needs Linux; on macOS run the scripts from a Linux container that shares the Docker socket and keeps `TMPDIR` on a path the Docker host resolves identically. These checks cover the stated synthetic cases only. Ente Photos (whose uploads need its client-side encryption) and Synology Photos (DSM) are not covered.

## PhotoPrism SQLite reader

The checked-in structural fixture was generated by the migrations in the official PhotoPrism `261029-963b58c50` ARM64 release, source commit `963b58c5034a45010b3944841f2bcc2e289abadd`. The fixture records the executable version, release archive checksum, container runtime digest, SQLite writer version, schema fingerprint, migrations and upstream AGPL provenance. It contains schema definitions only, with no media, account credentials or database contents.

`captureSqliteSnapshot` captures committed WAL contents through SQLite's backup API and verifies integrity and foreign keys. The caller must first stop source writers and authorize the source and private staging paths. A database backup does not establish consistency with the originals directory. Originals must be inventoried and hashed while source services and restart mechanisms remain fenced.

`openPhotoprismSnapshot` reads that captured snapshot in a read transaction. It refuses unknown versions, schema differences and missing, failed or unfinished migrations. Extraction uses bounded keyset batches and preserves integer identities as `bigint`. Only approved tables and columns are accessible. This reader does not create destination users, transfer files or activate a library.

| Source information                                                        | Extraction                                                                     | Destination preservation requirement                                                                                                    |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| Photos, manual titles/captions, dates, locations, private/favourite state | Source values and provenance fields retained                                   | Map manual fields before regeneration; verify time zones and restrictions                                                               |
| Files, duplicates, primary/sidecar flags, missing/deleted state           | Separate file records retained                                                 | Resolve originals storage independently from generated storage; hash bytes independently; preserve multiple originals and companions    |
| Albums and memberships                                                    | Albums, membership flags/order and filters retained                            | Preserve folder organization; disclose unsupported dynamic albums and hidden/excluded relationships                                     |
| Users and access rules                                                    | Identity, roles, scope, attributes, base paths and permission records retained | Require explicit owner mapping and equivalent or stricter destination access; exclude built-in anonymous principals from human accounts |
| Labels, keywords, subjects and human face markers                         | Source records and geometry retained                                           | Verify geometry/orientation before creating named faces; regenerate embeddings                                                          |
| Camera, lens, place and detailed metadata                                 | Source records retained                                                        | Preserve unsupported fields in the protected migration archive                                                                          |
| Account password verifiers                                                | Separate protected channel; excluded from ordinary content records             | Preserve qualified authentication semantics; use secure claims only when transfer is unavailable or unsafe; never log verifiers         |
| Reset/invite tokens, sessions, API credentials, public link tokens        | Excluded                                                                       | Do not transfer or log these values                                                                                                     |
| Model embeddings and generated renditions                                 | Excluded from transfer                                                         | Regenerate from verified originals                                                                                                      |

The internal reader does not infer ownership from directory names, email matches or `created_by` alone. The pinned application's CLI indexer produces photos with an empty creator, so outside the Manager, global library ownership needs explicit operator mapping, with base-path and role restrictions assessed separately. Manager imports apply the FL-1149 rule below instead: `created_by` decides ownership, and content with no recorded creator belongs to the primary administrator. A path hash or PhotoPrism's own file hash is not the independent migration checksum.

The `261029-metadata.json` fixture records a synthetic photo and private manual album after supported API edits, together with the API's independently read-back metadata. Source photo normalization preserves manual values and provenance, keeps the encoded local wall time separate from the capture instant, and flags `Local` time zones and unknown capture times for review. When both stored clocks are known, manifest assembly resolves the `Local` case by retaining the capture instant and exact source wall clock while leaving the named time zone empty; it never assigns the destination machine's zone. Missing capture clocks still require review. PhotoPrism's absent-coordinate sentinel `(0,0)` maps to explicitly empty coordinates, protected by the existing destination metadata locks so regeneration cannot restore stale embedded GPS. Source removal resets location provenance, so this rule does not depend on a manual-edit marker. PhotoPrism's computed quality score is not a user rating. An archived photo has `deleted_at` set and quality greater than `-1`; removed photos have a negative quality score. Private state remains separate from either state. Album normalization retains membership order and hidden/missing flags; excluded relationships are not revived. Folder and filtered albums require explicit membership materialization.

The `261029-files.json` fixture includes two generated synthetic PNG originals indexed by the pinned application, their source records and independent SHA-256 checksums. File classification treats the source root `/` as the originals storage identifier, with paths relative to an explicitly configured library root. Files in the `sidecar` storage tree are regenerable renditions, even when marked primary. Non-primary originals and original-tree sidecars remain separate records. Unsafe relative paths, unqualified storage roots and missing or watermarked originals are refused. Source file hashes are retained only in the archive; they do not supply the migration checksum. Classification does not resolve paths, hash live files or authorize a transfer.

`readPhotoprismInventory` streams logical photos, physical files, album headers, memberships and source principals separately. It uses the captured database for indexed detail lookups and relationship checks, rather than collecting a library-sized lookup map in memory. Before emitting records, it checks both photo identifiers on files, orphan details and memberships, active album references and the presence of an original for each logical photo. Historical hidden/missing membership references remain excluded records. Consumers must close the iterator if they stop early; completion, refusal and iterator return close the source transaction. Credential-free source rows are emitted separately for a future protected migration archive, preserving SQLite scalar types. The synthetic `261029-records.json` fixture was extracted using the same table/column allowlist.

Manual and batch label assignments with uncertainty below 100 map to owner-scoped Frameleaf tags alongside the photo's stored keywords. Rejected assignments, generated classifications, soft-deleted labels and negative-priority labels remain in the protected archive. Unsupported tag spellings are archived with an explicit unacknowledged loss rather than silently normalized. Label IDs and photo IDs are joined independently; missing or duplicate relationships fail preflight. Original label attributes and assignment records remain archived. These rules follow the pinned [photo-label API](https://github.com/photoprism/photoprism/blob/963b58c5034a45010b3944841f2bcc2e289abadd/internal/api/photo_label.go); they do not qualify source permissions or complete native application acceptance.

The two built-in anonymous principals are identified by pinned IDs and checked against their expected provider, role and login state. They are separate from human account candidates. For Manager imports (owner decision, FL-1149) a photo or album belongs to the account that added it (`created_by`); content with no recorded creator belongs to the primary administrator. Album memberships that would cross owners are removed and reported. Email matches never merge source principals. Inventory extraction does not establish owner mappings, independent byte integrity or permission equivalence, and does not create destination accounts or sharing.

Qualification remains incomplete. Synthetic SQLite originals, API-edited metadata and a private manual album have been exercised. The free PhotoPrism installation also runs locally in Docker with MariaDB, as described below. Additional restricted account roles refused setup in the pinned binary without membership; their privacy behavior remains unqualified. Destination mapping, complete preservation, rollback and combined acceptance remain unfinished.

The SQLite and MariaDB account projections retain PhotoPrism's numeric account `id` alongside its stable `user_uid`, without converting integers through JavaScript `Number`. The numeric identity is required to resolve the source's authentication-provider fallback when `auth_provider` is empty. It remains protected source metadata; the UID still identifies the mapped owner. Retaining either identity does not authorize login or transfer source administrative privileges.

### Password interoperability checks

`fixtures/password-vectors.json` contains synthetic bcrypt verifiers generated independently by Go `golang.org/x/crypto/bcrypt` v0.22.0 and the recorded native PHP runtime. The Go runtime image is pinned by its recorded image ID. These vectors exercise Unicode, embedded NUL bytes, PHP `$2y$` normalization and the 72-byte bcrypt boundary, including the source verifier's behavior for longer inputs. A separate Python-generated PBKDF2-SHA256 vector exercises Django's encoded format. They contain no real account credentials.

`createImportedOwner` writes the explicitly mapped owner and its private cluster group atomically. A protected password makes the account usable with its existing password; an absent portable credential selects the secure-claim fallback. It refuses cross-operation or cross-owner credentials, existing-email collisions and a missing destination administrator. It accepts no source administrative flag, OAuth binding, session, API key or reset token. The operation controller must call it inside the journal's owner mapping transaction, after qualifying source login restrictions and permissions. The generic controller and full source authentication qualification remain incomplete.

## PhotoPrism MariaDB schema admission

The `261029-mariadb114.json` structural fixture was captured from the same pinned PhotoPrism executable after it created and migrated a fresh MariaDB 11.4.5 database in Docker. Both immutable image digests and the complete server version are recorded. The native installation indexed two synthetic originals, whose source hashes and byte counts were independently checked against the original bytes, including SHA-256 hashing. Its schema contains 41 InnoDB tables and 48 completed migrations. The fixture contains database definitions and migration/version records, with no account credentials or media. The disposable containers, database volume and network are removed after capture.

`admitPhotoprismMariadbSchema` requires the pinned source build, database version and case-sensitive table-name setting, the complete schema fingerprint and the exact completed migration inventory. Its catalog includes columns, indexes, constraints, key relationships, foreign-key rules, checks, triggers, routines and events. Changed or incomplete catalogs, unexpected objects, failed migrations and a different latest executable version are refused. These tests qualify structural admission only. Complete preservation, ownership/privacy mapping and end-to-end migration acceptance remain unfinished.

`readPhotoprismMariadbInventory` reads an isolated restored database with source writers fenced separately. It requires the pinned engine, case-sensitive table names, global read-only mode, no Galera replication, complete metadata privileges and a single application database. A global read lock and consistent read-only transaction protect bounded primary-key batches, relationship checks, detail lookups and repeated schema/migration admission. Completion, refusal and consumer cancellation close the connection and release its locks. A source capture and its original-file inventory must still be bound by the operation controller.

The SQLite and MariaDB paths share projections, relationship checks and metadata normalization. MariaDB binary text is decoded with strict UTF-8 without stripping a leading byte-order mark. Capture instants and encoded local wall times remain separate; a UTC session and the pinned source's DATETIME semantics supply the database timestamp representation. Full credential-free source records remain available to the protected archive. A bounded protected callback preserves compatible PhotoPrism passwords with explicit account mappings; escaped or expired callbacks refuse access. This does not qualify source login restrictions or enable destination accounts.

Run `node server/scripts/qualify-photoprism-mariadb.mjs` with installed Server dependencies and Docker on ARM64. It creates a disposable database from the application-generated schema and synthetic content fixtures, runs the native reader tests, then removes its containers, volume and private credentials. Images newly pulled by the runner are removed when unused; existing shared images are retained. The same pinned ARM64 restore runs in the Library import qualification workflow. Tests cover manual metadata, privacy flags, every original, more than 1,000 physical records, Unicode path preservation, protected passwords, cancellation/lock release, writable-source refusal and schema/relationship/migration errors. These are reader checks, not complete source or migration qualification.

## Primary originals in the common bundle

Manifest version `2` requires a `primaryFileId` for every logical asset. It must identify an attached physical file whose role is `original`. Other originals, sidecars and companions remain separate entries in `fileIds`; primary selection never removes them from byte verification or transfer. A thumbnail, sidecar, missing file or another asset's unattached file cannot become the primary.

Version `1` remains accepted when each asset has exactly one original, with its existing serialized structure and fingerprint. An ambiguous version-one asset with several originals refuses preflight with `PRIMARY_ORIGINAL_REQUIRED`; capture explicit source primary evidence or obtain an operator-reviewed selection in a version-two bundle. File order, extension and resolution are not primary-selection evidence. Changing the selected primary changes the manifest fingerprint and cannot silently alter a journalled operation.

This contract separates logical asset identity from physical original identity. It does not establish source ownership/privacy evidence, implement destination multi-original storage or complete any adapter's qualification. The destination writer and reconciliation must preserve every source relationship before activation.

### Destination original references

The internal `asset_original` relation attaches additional originals to one logical photo through canonical `physical_file` records, while `asset.originalPath` remains the selected primary. A physical original can remain attached after another photo that used it as its primary is removed. File reference counting protects the remaining attachment, and the database refuses deletion of its physical record. Removing the final attachment releases that reference. Downgrade refuses to drop a populated attachment table.

Managed asset deletion snapshots additional originals with the existing path-lock and removal transaction. Failed cleanup queuing retains the asset and its attachments. Each released original travels with its owner, filename, checksum and byte count into file-trash cleanup; replay preserves its bytes and provenance. External-library originals, offline files and files explicitly retained on disk follow the existing primary-original retention policy. Deletion usage adjustment includes the removed additional-original bytes.

Storage statistics and both quota recount paths include every attached original's physical size in addition to the primary original. Attachments do not multiply logical photo/video counts. Existing owner, managed-library, trash and privacy filters remain unchanged, and developed artifacts and revision charges remain included in the full recount. An absent primary EXIF size does not hide known attachment bytes.

This remains internal infrastructure. It does not import attachments, authorize file linking, extend portable library exports, preservation packages, backup inventories, initial quota charging or Locked encryption. Those integrations and canonical reconciliation remain required before migration activation; the new adapters remain unqualified.

### Original archive downloads

Original-mode ZIP downloads stream every attached original through the existing permission, embedded-metadata and Locked-read checks. Archive planning includes additional original sizes without multiplying logical asset IDs. Original filenames use the existing collision-safe archive naming. An as-shown download keeps the selected display version. A failure opening an encrypted file closes the unfinished archive.

The version-one portable library inventory represents one original per logical asset. A portable export containing additional originals is refused before archive creation, so it cannot silently omit their relationships. Versioned portable export/restore, preservation and backup inventories, initial charging and Locked-writer integration remain required before migration activation. These archive checks do not qualify any new source adapter.

Sealed manifest assets may carry an exact `localDateTime` wall clock instead of a named `metadata.timeZone`. This field contains no offset or zone and retains up to six fractional digits. Supplying both representations is refused. The capture instant is still required. The canonical writer uses Frameleaf's existing clock columns and metadata locks, and independent readback compares both stored clocks. Existing named-zone manifests keep their serialized form and verification hashes.

PhotoPrism account preferences (`auth_users_settings`) are retained in the protected source archive by both pinned SQLite and MariaDB readers. Language, time zone, download-format choices and other UI preferences keep their source user IDs and original values. These preferences do not establish access permissions or enable destination login; source authentication and privacy qualification remain separate. Password verifiers still use the private credential path, and sessions and account tokens remain excluded.
