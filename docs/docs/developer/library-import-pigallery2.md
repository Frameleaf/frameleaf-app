# PiGallery2 import qualification

PiGallery2 migration is internal groundwork and is not available through a CLI or the Manager. The expanded migration feature remains unreleased until all ten source families qualify.

## Pinned native evidence

The synthetic source uses PiGallery2 `3.5.2`, source commit [`ed21d7f94bb346b5ba98e846bd71cd59782b453a`](https://github.com/bpatrik/pigallery2/tree/ed21d7f94bb346b5ba98e846bd71cd59782b453a), archive SHA256 `e63cc03767d4b97d9f6bcc1c0f6bfb31cd7262a4afc81c3af176866eee1741d1`. The official ARM image is `bpatrik/pigallery2@sha256:afc40f0513831ff260171c37bdbf872e52505cd2b35fa7276f0a28566bb43739`; its ARM SLSA provenance records that source commit. Native runtime versions are Node `v22.22.0`, better-sqlite3 `11.10.0`, SQLite `3.49.2` and application data-structure version `41`.

The native application created 13 tables and 47 schema objects. Its complete schema fingerprint is `c2cb2ba31b20e4e37d8ef198fe6eafd79327d43536b81914c4599f32388dae89`, independently established in Python and the actual Server Node 22 reader. Public fixtures contain native DDL, eight credential-free content projections, selected global privacy configuration, independently defined access expectations and original-file hashes. Required source MIT provenance is retained beside them. Raw snapshots, passwords, share keys, cookies and full configuration remain private.

The installer does not have a conventional migration inventory: [SQLConnection](https://github.com/bpatrik/pigallery2/blob/ed21d7f94bb346b5ba98e846bd71cd59782b453a/src/backend/model/database/SQLConnection.ts) drops and rebuilds the database when its recorded data-structure version differs. Never start a source application against an unqualified snapshot to inspect or upgrade it. Extraction requires a frozen, consistent backup and reads it without running the source application.

## Read-only snapshot extraction

`openPigallery2Snapshot` requires the pinned application version, exact complete schema, exactly one matching data-structure-version record and valid declared foreign keys. Unknown or modified schemas fail before content. It uses one read-only transaction, disallows SQLite extensions and returns integer-safe batches of at most 1,000 rows. Authentication material and generated projection caches are excluded. Query and file errors use sanitized refusal codes.

This reader preserves source records; it does not interpret access predicates or establish ownership. Global authentication, guest-role and allow/block settings require a separately verified configuration inventory. Database rows alone are insufficient privacy evidence. Username, directory names, sharing creators and content hashes must never become inferred owners. The destination requires explicit library/owner mappings and equivalent or stricter access before activation.

## Original and metadata-file paths

`resolvePigallery2File` joins each native directory path/name and file name relative to the independently verified `Media.folder` root. It does not use generated thumbnails, best-fit videos or public URLs. Root, nested and Unicode directory cases match the pinned native `DiskManager`; the actual Server reader/resolver also matches the four native original paths, lengths and independent SHA256 values. Unsafe paths, mismatched directory identities, unknown table/discriminator combinations and invalid media lengths refuse resolution.

Media and metadata-file identities have separate table namespaces. Metadata files retain their directory association and sidecar role; their byte count remains unknown until independently read. The additional SQLite fixture below covers native Markdown/GPX records and one video; general metadata-file and video qualification remains incomplete. The caller still must reconcile the directory graph, cross-record collisions, configured originals/cache roots, filesystem containment and symlink/hardlink policy, source fencing, explicit owners and privacy before transfer or activation.

## Preservation requirements

| Source information                    | Captured evidence                                                                      | Required destination behavior                                                                                                             |
| ------------------------------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Directories, media and metadata files | Directory hierarchy, media/file identities and names                                   | Resolve actual originals and required sidecars through a verified storage root; independently hash bytes and retain every relationship    |
| Captions, titles, dates and location  | Current metadata columns, source date value and separate nullable offset               | Preserve current values ahead of stale embedded metadata; do not infer a known timezone from a missing offset                             |
| People and faces                      | Person records, junctions and source metadata fields                                   | Retain unsupported data in the protected archive; assign names/coordinates only after verified orientation and geometry conversion        |
| Saved searches                        | Album identity, name and serialized search predicate                                   | Preserve the predicate; materialize unsupported dynamic albums as explicitly identified, verified membership snapshots                    |
| Users and privacy                     | Roles and per-user override/allow/block predicates, plus separate global configuration | Require explicit mappings and evaluate inherited settings and block precedence; missing or unsupported privacy evidence blocks activation |
| Public sharing                        | Creator, search predicate, expiry and password-presence flag                           | Never migrate bearer keys or password hashes; recreate only equivalent or stricter sharing, otherwise restrict affected content           |
| Projection caches                     | Excluded from extraction                                                               | Regenerate from preserved source records and destination permissions                                                                      |

## Native comparison and limits

Four generated JPEG originals include duplicate bytes in different directories, EXIF captions and a date without a recorded timezone offset. Four source accounts and a saved search were created through the native application. Caption-based allow predicates combined with a filename block predicate produced independently expected search inventories: administrator four, Alice two, Bob two and Mallory one. Nine permitted original downloads matched independent SHA256 values; seven prohibited original requests returned HTTP 403 without media bytes. An Alice-created password-protected share exposed only the shared original and retained her filename block restriction. A separate native installation restored from the stopped database backup and copied generated originals reproduced all four identities, exact search inventories, nine original hashes, seven denials, the saved search and protected share. All 14 projected records, complete schema and selected global privacy settings remained unchanged after that restored application ran. These checks establish that synthetic baseline, not general permission equivalence.

Directory-type allow predicates caused the pinned native SQLite application's restricted root listing to fail with `no such column: directory.path`. That failure is retained as a separate qualification risk. It is not evidence of an empty or unrestricted library and must not be silently converted into either. The final fixture's successful account rules use caption predicates; its saved search retains a directory predicate. General directory-query behavior and saved-search membership evaluation remain unqualified.

The actual Server Node 22 reader reconciles all 14 projected records across eight tables against the stopped source capture. The additional fixture below extends source-record evidence for people, metadata files and video. Native RAW/JPEG pairs, Live Photos, other orientation/geometry cases, video/metadata-file privacy, missing files, additional global/per-user policy combinations, encrypted/remote storage, MySQL, broader restored-application cases and complete semantic reconciliation remain unqualified. Destination accounts, protected archive persistence, Manager integration, transfer/recovery, activation and combined ten-source acceptance remain incomplete. Protected Unraid shares remain entirely outside qualification and agent access.

## Additional native metadata and sidecars

A second SQLite fixture uses the same immutable source image and schema. The native application indexed two generated JPEGs, a generated video, Markdown and GPX files, nine XMP sidecars and one synthetic named face. Three original downloads matched independent byte hashes; a case-sensitive Linux source inventory matched all 14 generated files. Writers were stopped before a SQLite backup captured the committed database. The Server reader reconciled all 16 directory/media/metadata-file/person/junction records against the native capture, and its file resolver matched the three original paths and lengths plus both metadata-file paths. The source face box was independently checked for orientation 1 only; this does not qualify destination face assignment or other orientations.

PiGallery2 does not list these XMP sidecars in `file_entity`. Its photo loader uses the first parsed candidate in this order: full filename plus `.xmp`, full filename plus `.XMP`, filename without extension plus `.xmp`, then filename without extension plus `.XMP`. Its video loader visits all four and merges them in order. The fixture demonstrates an XMP title, caption, rating and tags overriding stale embedded metadata, a basename/uppercase fallback and the video's final-sidecar caption. Markdown and GPX remain distinct native metadata-file records with directory relationships.

`pigallery2SidecarCandidates` reproduces the native candidate paths without reading the filesystem or deciding which files exist. Inventory must probe and independently hash every existing candidate through the verified original root, preserving every source relationship. Metadata precedence must follow the captured current database values. Case-sensitive `.xmp`/`.XMP` pairs must not be collapsed on a case-insensitive destination; an unrepresentable layout requires review or refusal before transfer. Source identity, containment, symlink/hardlink policy, actual snapshot completeness, ownership, privacy and destination metadata preservation remain controller requirements.

## Native MySQL schema evidence

The pinned PiGallery2 image also created a fresh MySQL schema through its own `SQLConnection.getConnection()` and schema synchronization. The isolated qualification engine is MySQL `8.4.13`, image `mysql@sha256:a0225d1ea6631c8bc2385dc4c2faba17bbf1834ecf369e1659a9a382bd8d5dd7`. The source image uses Node `v22.22.0` and the `mysql` driver `2.18.1`; the synthetic engine explicitly enables native-password authentication for that driver. This setting is fixture provenance, not a production configuration recommendation.

The native schema has 12 InnoDB tables, 91 columns, 58 index entries and 12 foreign keys, with data-structure version `41`. SQLite's additional internal sequence table is not an application table. The credential-free fixture retains native table DDL and complete collected metadata. Database JSON values keep the fingerprint independent of a client driver's integer-to-string conversion. The application-side collector and Server reader agree with the independently computed fingerprint `87b120325d104fa6bc44c97d7eec7e9e2902ac42ed738542d0b7837a75dd2dbb`.

MySQL metadata collection includes index visibility and expressions, constraint enforcement, foreign-key update/delete rules and check expressions. Referenced schemas use a binary comparison with the selected source database: local names normalize consistently, while external references cannot match the native fingerprint. The existing MariaDB collection and Piwigo fingerprint remain unchanged. `admitPigallery2MysqlSchema` requires the pinned application version, engine version, structure version and full schema fingerprint; missing metadata or altered rules refuse admission. The helper does not verify binary identity; the source controller must independently verify the pinned build before qualification.

## Internal MySQL restore reader

`readPigallery2MysqlRestore` reads only a dedicated restored database on the pinned engine. It requires both global read-only settings, complete direct metadata privileges, no active roles and no other application database. A global read lock remains held across the read-only repeatable-read transaction. The reader verifies the full schema before querying source objects, checks actual foreign-key relationships and reconciles each table's count against integer-safe keyset pages of at most 1,000 records. Schema and isolation are checked again before normal completion. Remote connections require certificate and hostname verification; driver and consumer errors are sanitized. Cancellation and failures close the dedicated connection.

The MySQL and SQLite readers share the eight credential-free projections. An optional awaited callback reads a specified account's bcrypt verifier through the protected password capability bound to explicit operation, source-user and destination-user IDs. It does not expose raw passwords in content batches. The capability cannot be invoked after the callback exits. Account mapping, retention and login qualification remain separate steps.

The MySQL password callback has a 30-second inactivity deadline, renewed when an account read starts or completes. A stalled callback expires the capability and closes the connection, releasing the global read lock and any queued generator cancellation. A progressing multi-user inventory may take longer overall. The controller must not perform unrelated slow work while holding this source lock. Consumer return at a yielded batch closes the connection directly; it cannot synchronously interrupt an awaited callback before that callback completes or expires.

A fresh pinned MySQL installation was initialized by the native application, then seeded with the same 14-record synthetic inventory. The reader matched every projected record, and a password generated and independently checked by PiGallery2 verified through Frameleaf's protected import representation. Native checks confirmed that the global lock blocked a concurrent update, changed read-only settings refused completion, cancellation released the lock and an orphaned sharing creator refused extraction before credential access. Empty people and metadata-file tables do not establish their content semantics; the 1,001-record pagination case is a reader unit test.

These checks establish the internal extraction boundary, not a MySQL migration compatibility claim. Native MySQL application permission/download comparisons, original-byte acceptance, richer content, source-build identity and configuration capture remain unqualified. The controller must independently prove the original source was frozen, capture a consistent backup and keep writers and restart mechanisms fenced. It must fully consume and reconcile the reader before activation. Manager integration, destination account qualification and combined ten-source acceptance remain unfinished; the expanded release remains gated.

A full native application startup on this MySQL engine failed before HTTP readiness. PiGallery2's `SQLConnection.removeUnusedTables()` selects `table_name` from `information_schema.tables`, then reads `r.table_name`; this engine/driver returns the `TABLE_NAME` property. The resulting `DROP TABLE undefined` fails with MySQL error 1051. Initial schema creation and direct ORM password checks therefore do not prove that the complete application runs on this engine. This combination remains unqualified until an unmodified source build passes application, permission and download checks; the qualification harness must not patch or skip the failing source startup path.
