# LibrePhotos import qualification

The LibrePhotos adapter is under development. Its internal SQLite and PostgreSQL readers do not create destination accounts, transfer originals or expose migration support. All ten source families must pass combined qualification before the expanded feature releases.

## Pinned source evidence

The structural fixture comes from native Django migrations in LibrePhotos `1.5.1`, source commit `2097ce7b44a318039c68997816bc91d85da3ea31`. It was generated in the official Linux ARM64 unified image `reallibrephotos/librephotos-unified@sha256:a03393fc07ab80b69d58f4c4f083b4ec99a25c3f9e9d7cd235b50e5f4875ff9f`, with the image's source revision checked before use. The documented `librephotos.settings.production_noproxy` settings and `DB_BACKEND=sqlite` selected SQLite 3.46.1. The source produced 83 tables and 295 applied migrations; schema SHA256 is `28c2f23c08a1c32150cf3c094ed29b96524b19d4f8f64a6f2a866806a178dc95`.

The content fixture uses generated PNGs and four synthetic accounts. The pinned application's models and API created five logical photos, five physical files, an additional original variant, a duplicate-path alias, manual metadata, hidden/archive/trash state, a stack, a named face and a locked collaborative album with photos belonging to different owners. Source-native thumbnails were generated before checking photo access. Independent source API assertions verified that the owner sees the manual caption and person label, a restricted viewer cannot see location/caption/person names, and an unrelated actor receives 404 for the photo and album. Capture-time edits were checked in both the API response and the persisted source record.

The source container was stopped with restart disabled before a backup through `captureSqliteSnapshot`. The snapshot passed integrity and foreign-key checks. Public fixtures contain generated schema, allowlisted synthetic rows and selected API expectations, without source credentials, bearer links, model vectors or host paths. The upstream MIT permission notice accompanies the generated fixture.

## Reader and preservation matrix

`openLibrephotosSnapshot` accepts only the pinned version, exact schema and complete migration inventory. Missing, additional, duplicated or unfinished migration records and broken foreign keys are refused before content is returned. Reads use one read-only transaction, bounded keyset batches and `bigint` integer values. The caller must independently verify source application identity and fence source writers and restarts; a schema fingerprint cannot prove binary identity or consistency with original files.

| Source data                                                                                                    | Reader behavior                                                                                                                    | Destination requirement                                                                                              |
| -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Photo UUID, owner, physical-file relationships                                                                 | Retain independent photo and file identities, main-file and variant relationships, embedded-media links and duplicate-path aliases | Explicit owner mapping; independently hash bytes; retain every relationship                                          |
| Manual title, caption, tags, rating, capture date and location                                                 | Retain current fields, embedded values and edit history separately                                                                 | Manual edits take precedence; protect unsupported history                                                            |
| Hidden, archived, trashed and removed flags                                                                    | Retain independent states                                                                                                          | Reconcile states without making restricted content visible                                                           |
| Albums, memberships, roles, contributor permissions and album ceilings                                         | Retain separate records, including the actor adding each photo                                                                     | Recreate only equivalent or stricter access; album locks control edits and do not establish privacy                  |
| Direct, library, person and public sharing settings                                                            | Retain policy and recipient records; exclude public bearer slugs                                                                   | Prove all effective access paths; keep unsupported sharing restricted and disclose losses                            |
| Named people and face coordinates                                                                              | Retain raw coordinates and source relationships; exclude encodings and generated face crops                                        | Qualify thumbnail geometry and orientation conversion before assigning destination faces                             |
| Stacks, collections, automatic albums, comments, likes, OCR and other content metadata                         | Retain allowlisted records for mapping or a protected archive                                                                      | Disclose unsupported features; do not silently discard relationships                                                 |
| Source account settings                                                                                        | Retain identity and relevant privacy/date/favourite settings                                                                       | Explicit account mapping; preserve qualified authentication; secure claims are fallback; never match owners by email |
| Provider credentials, sessions, API keys, mail settings, public link slugs, model embeddings and task payloads | Excluded                                                                                                                           | Never migrate or log values; regenerate model outputs and previews                                                   |

A `Photo` has a UUID primary key. `File.hash` includes an owner-related salt, and a physical `File` can be referenced by different owners. `Photo.image_hash` can remain stale after a file rekey. None of these values is the migration content checksum, nor can its suffix establish ownership. Shared physical bytes require special care during copy, adoption, deletion and rollback so one owner's actions cannot destroy another owner's original.

Source capture dates are stored as wall-clock values tagged UTC, with a separately nullable offset; manual edits also set `timestamp`. Do not treat every database value as a known instant. Preserve source date rules and timezone evidence. `Photo.rating`, user `rating_mode` and `favorite_min_rating` are distinct from the file's embedded rating. The source metadata API's `keywords` readback still reports scanned file keywords after a manual tag edit; `edited_keywords` and tag relationships preserve the user's changes.

`normalizeLibrephotosPhoto` maps photo metadata from rows and complete current tag relationships belonging to the same admitted snapshot. It checks owner and context identities, retains independent state flags and uses current tags instead of restoring removed embedded keywords. Manual capture dates take precedence over stale rule values. A known minute offset produces a capture instant while retaining microsecond precision; an unknown offset leaves the instant unset and requires review. It does not guess an IANA timezone from coordinates or account preferences. Public source flags are retained as evidence and do not grant destination access. Unsupported metadata remains available in the reader's raw records for the protected archive, whose persistence is still outstanding.

Face boxes use big-thumbnail pixel coordinates and additional local orientation. A thumbnail aspect ratio alone is insufficient for reliable conversion. The current fixture exercises one measured, unrotated named face; rotated and video faces remain unqualified.

## Outstanding acceptance

Complete supported media/companion fixtures, orientation conversion, every sharing path, destination privacy, protected archive persistence, byte transfer, resumable recovery, Manager integration and full migration acceptance remain outstanding. No end-to-end source compatibility claim follows from reader tests. Protected Unraid shares are outside the qualification environment and all agent access.

## PostgreSQL schema and value qualification

The same source commit and image also generated a PostgreSQL installation using the upstream deployment's PostgreSQL 18 major. The qualified engine is PostgreSQL `18.6`, Linux ARM64, immutable image `postgres@sha256:10a5c69a83035ab5239f5620d708520e8b28f5aa1f2b20143e6024532edadfb5`. Native source migrations and the synthetic owner/viewer/unrelated-user API checks passed. A native custom-format dump was restored into a second isolated database; 82 application tables, 295 migrations, all five photos, manual metadata and measured face coordinates were verified after restore. Both source applications and database instances were stopped with restart disabled.

The PostgreSQL structural fixture was then read in one repeatable-read, read-only transaction using a non-superuser account without row-security bypass. It includes namespaces, relations, columns, constraints, table inheritance, indexes, sequence definitions, types, routines, triggers, policies, views and extensions. OIDs, database owners and live sequence positions are excluded from structural identity. The schema SHA256 is `89e98e5d54fe605c7b6e830ad776ff7e02b6bf9421dcac979cc7b830ebd6abfc`. The fixture contains structural definitions, not credentials or source authentication records.

`createLibrephotosPostgresDecoder` admits only the pinned source version, engine version and catalog fingerprint. It consumes explicit PostgreSQL `column::text` projections, with the source session set to UTC. Integer values become `bigint`, booleans become the same strict `0n`/`1n` flags used by the SQLite reader, and native UUID values become consistent 32-character source IDs across primary and foreign keys. JSONB remains validated JSON text. Timestamp text retains microseconds and removes only the known UTC session suffix; capture dates still need the source-specific wall-clock/offset interpretation. Unknown tables, columns, types and malformed values are refused.

The SQLite reader and PostgreSQL decoder share one credential-free projection allowlist. The PostgreSQL content fixture retains the 56 projected synthetic records used for value conversion tests. Catalog admission and decoding do not establish application identity, writer fencing, permission equivalence or verified original files. Recovery integration remains outstanding.

A native inheritance regression adds an existing compatible membership table as a child of another. PostgreSQL then returns two rows where it previously returned one. The fingerprint includes parent/child relationships and inherited-column/constraint flags, and refuses this schema before decoding records. See [PostgreSQL inheritance behavior](https://www.postgresql.org/docs/18/ddl-inherit.html).

## PostgreSQL snapshot streaming

`openLibrephotosPostgresSnapshot` reserves one dedicated connection and starts a read-only repeatable-read transaction. It requires stopped-writer evidence and refuses elevated roles, table write authority, other database clients, an unqualified engine/schema or incomplete migration inventory. The caller must still verify the source binary and fence services and restart mechanisms before opening the snapshot; admission checks cannot prevent a later external connection.

Allowlisted content is read in batches of at most 1,000 records using native indexed primary keys, explicit text projections and `FROM ONLY`. Sorting qualifies the source relation so PostgreSQL cannot substitute a text-projected output alias for the native key. Each fully consumed table stream must reconcile its row count against a separate `count(*)` in the same snapshot; malformed counts, excess rows and incomplete inventories fail the read. A 2,505-record native integer-key regression reproduces the former omission of 899 records and verifies ordered pages of 1,000, 1,000 and 505 after correction. The same page inventory passed against a fresh restore of the pinned PostgreSQL 18.6 source database under Node 22.23.4, using the actual catalog and read-only admission checks. The connection is never replaced after transport loss. Errors expose fixed codes. Explicit close ends the private pool with a five-second termination timeout; disconnecting rolls back its read-only transaction without waiting for another SQL command. A restored native fixture yielded all 56 expected records across all 51 allowlisted tables; a concurrent synthetic metadata edit remained invisible inside the snapshot, and terminating its backend caused a read failure without reconnection. A query blocked behind an exclusive table lock also closed within the bounded termination window. These checks qualify source reading only, with synthetic data and the pinned PostgreSQL engine.

## Recorded file resolution

`classifyLibrephotosFile` maps the database's actual Linux `File.path` through an explicitly chosen source root. It refuses root `/`, traversal, ambiguous separators, paths outside that root, missing files and unknown source file types. Source image, video, XMP and RAW types are retained separately; an incoming `embedded_media` relationship identifies a video companion. Its actual recorded path can map through a separate embedded-media root. The caller must supply all incoming relationships, never infer companions from a filename, and validate parent references against the complete inventory. `normalizeLibrephotosFileCopy` retains duplicate-path aliases pointing to the source file identity without inventing ownership or a content checksum.

The generated PNG fixture retains the five application-indexed originals and one exact-copy alias with independently calculated byte counts and SHA256 checksums. It exercises shared physical identity and multiple-original relationships alongside the existing logical-photo fixture. This evidence does not qualify RAW, video or Live Photo bytes. The helper performs no filesystem access: mounted-root identity, symlinks, actual bytes, collisions, aliases and source changes still require verification. Indexed sidecar modification records are historical scan evidence, not a complete sidecar inventory; required XMP and Takeout metadata sidecars still need filesystem inventory and verification before migration can activate.

Account password verifiers use a separate protected channel on both admitted database engines. Django PBKDF2-SHA256 credentials can retain the source password; absent credentials and Django unusable-password markers select the secure-claim fallback. Missing owners, malformed verifiers, lost or closed snapshots and database errors refuse the read instead of silently downgrading it to a claim. Source login restrictions and multi-factor requirements still need qualification before enabling a destination account.

## Common manifest mapping

`readLibrephotosManifest` consumes every approved table from one admitted SQLite or PostgreSQL snapshot and maps logical photos, physical originals, owners, user albums and compatible stacks into the common import manifest. It accepts independent file checksums and modification times; source file identities never supply those checksums. Multiple originals keep their explicit source primary. Unknown schemas, missing evidence, orphan relationships, ambiguous media and unsupported companions refuse mapping before destination effects. Removed-only records without a source trash timestamp also stop for review; the mapper does not invent a deletion date. The caller retains the snapshot until private account credentials have been read, then closes it even on failure.

Source captions, ratings, current tags, favourites and hidden/archive/trash state are authoritative. Empty coordinates remain explicitly empty and protected against stale embedded GPS. Capture offsets recorded by the source preserve both the capture instant and wall clock. A manually entered date has no known offset in the [pinned source model](https://github.com/LibrePhotos/librephotos/blob/2097ce7b44a318039c68997816bc91d85da3ea31/apps/backend/api/models/photo.py#L259) and [edit implementation](https://github.com/LibrePhotos/librephotos/blob/2097ce7b44a318039c68997816bc91d85da3ea31/apps/backend/api/metadata/edits.py#L173); an API `Z` suffix is not evidence otherwise. Such dates require an explicitly reviewed per-photo offset in minutes. Source-absent dates use verified file modification time as a reported fallback requiring acknowledgement.

Albums start owner-only. A cross-owner membership can become a private partition for that photo's owner only when the source explicitly grants that owner access to the album; otherwise the relationship remains in the protected archive. This prevents disclosing a private album's name merely because it contains someone else's photo. Unqualified member roles refuse mapping. Restricted sharing and partitioned or archived memberships are reported for review. Stacks are retained when their owners, visibility and memberships fit the destination rules; incompatible groups remain archived without changing asset visibility.

The source's [file-copy records](https://github.com/LibrePhotos/librephotos/blob/2097ce7b44a318039c68997816bc91d85da3ea31/apps/backend/api/models/file.py#L171) are duplicate-path scan bookkeeping. Their paths and independent byte verification remain protected archive records, rather than becoming new visible originals or extra transfers. Actual `Photo.files` variants remain separate originals. Titles, people and remaining source-only metadata also stay in the protected archive with disclosed differences; embeddings and previews are regenerated. Face assignment, companion conversion, source capture authority, full Manager integration and combined qualification remain unfinished.

The Source manifest mapping job checks the admitted SQLite fixture, PostgreSQL decoder fixture and canonical preparation contract. These are mapping checks, not a complete PostgreSQL migration or source compatibility claim. It runs alongside the existing native reader checks; it does not replace the complete Server, Manager or combined acceptance gates.
