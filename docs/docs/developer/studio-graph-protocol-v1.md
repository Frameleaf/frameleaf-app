# Studio graph protocol v1

This page specifies the Studio project graph. The native Frameleaf apps for iPad and Android tablets edit Studio projects from this page alone, and must produce exactly the graph, and the same `digest`, that the web Studio engine produces for the same edit.

It is a clean-room specification. It was written by reading the engine, and it describes behaviour only: it contains no engine source text. The engine is an adapted build of Freecut (MIT, see `studio/notices/freecut.txt`), pinned at revision `4d62e8082c5eb387a96275bcbd323d28f6e41a62`. The protocol is versioned with that pin. A change of engine revision is a new protocol version unless the conformance fixtures still pass unchanged.

Machine-readable files sit beside the other Studio contracts:

| File                                    | What it is                                                                                                                                                       |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `studio/graph-schema-v1.json`           | JSON Schema (2020-12) of a graph in normal form, and of the media record an edit reads.                                                                          |
| `studio/graph-conformance-v1.json`      | Conformance fixtures generated by running the real engine: inputs, expected graphs, digests, id draws, rejections, history scripts and test vectors.             |
| `studio/frameleaf-studio-commands.json` | The command catalogue (ids, payload field types, scopes). This page gives the commands their graph meaning.                                                      |
| `studio/graph-parameters-v1.json`       | The parameter catalogue, generated from the engine: every effect, transition, blend mode, title style, template and rate a graph or a command may name (13.2.1). |

Where the engine's behaviour is accidental or inconsistent, this page says **implementation-defined** and gives the rule a native client must follow. It never invents semantics the engine does not have.

The page is delivered in four parts:

| Part | Story             | Covers                                                                          |
| ---- | ----------------- | ------------------------------------------------------------------------------- |
| 1    | FL-306 (NAPI-017) | The document, units, ids, ordering, digests, batches, undo/redo, fixtures.      |
| 2    | FL-307 (NAPI-018) | Mutation rules for clips, timeline edits, tracks and markers.                   |
| 3    | FL-308 (NAPI-019) | Effects, transitions, keyframes, easing, blends and parameter schemas.          |
| 4    | FL-309 (NAPI-020) | Compositions, titles, sequence and project settings, and full command coverage. |

Sections 1 to 11 are part 1, section 12 is part 2, section 13 is part 3 and section 14 is part 4. Sections 15 to 17 add captions (FL-111), Lottie maps (FL-105) and masks and relinking (FL-348). Section 18 points to the render spec: what each effect and transition draws. Section numbers never change: a later part added sections after them, and section 8.3, which lists every command.

## 1. Where the graph lives

A Studio project's head revision carries an **envelope** (OpenAPI `StudioProjectEnvelopeDto`):

| Field            | Value                                                                                        |
| ---------------- | -------------------------------------------------------------------------------------------- |
| `schemaVersion`  | `1`. The server accepts exactly this value.                                                  |
| `engine`         | `"freecut"`.                                                                                 |
| `engineRevision` | The pinned engine revision above, as a string.                                               |
| `graph`          | The graph this page specifies. The server stores it byte for byte and never reads inside it. |

A save (`StudioProjectSaveDto`) sends the envelope, the head it was built on (`expectedRevision`), a `requestKey`, and the `commands` that produced it (section 8). The server checks the envelope's four fields, the graph's size, and each command envelope against the catalogue. It does **not** re-run the engine, so a native client is trusted to produce the graph this page describes. The conformance fixtures are how a client proves that it does.

## 2. The graph document

A graph is one JSON object: Freecut's project document. `studio/graph-schema-v1.json` is its schema in normal form. This section names the parts and the rules the schema cannot express.

### 2.1 Top level (the project)

| Field                    | Type   | Notes                                                                                |
| ------------------------ | ------ | ------------------------------------------------------------------------------------ |
| `id`                     | string | The engine's project id. It is not the server's Studio project id and never changes. |
| `name`, `description`    | string | Display only.                                                                        |
| `createdAt`, `updatedAt` | number | Milliseconds. Commands never change them (section 4.3).                              |
| `duration`               | number | Commands never change it.                                                            |
| `schemaVersion`          | `15`   | The engine's document version. See 2.6 for older values.                             |
| `metadata`               | object | Canvas and frame rate (2.2).                                                         |
| `timeline`               | object | The main timeline (2.3). Absent only on a graph that has never been opened.          |
| anything else            | any    | Preserved unchanged by every command (2.5).                                          |

### 2.2 `metadata`

| Field             | Type           | Notes                                                                                                                             |
| ----------------- | -------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `width`, `height` | integer        | Canvas size in pixels.                                                                                                            |
| `fps`             | number         | The engine's frame rate as a float: exactly `frameRate.num / frameRate.den`. At most 120 (14.6.1).                                |
| `frameRate`       | `{ num, den }` | The exact frame rate (section 3). Always present in normal form.                                                                  |
| `backgroundColor` | `#rrggbb`      | Optional.                                                                                                                         |
| `colorManagement` | object         | Optional record of four fields (`studio/spec/hdr.md`, H1). Absent is not SDR: placed HDR media make a project HDR (H3).           |

### 2.3 `timeline`

| Field                                         | Type           | Notes                                                                                                                               |
| --------------------------------------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `tracks`                                      | array of track | In stored order; compositing order comes from each track's `order` (section 5).                                                     |
| `items`                                       | array of item  | Every clip of the main timeline, on every track (2.4).                                                                              |
| `masterBusDb`                                 | number         | Project master gain in dB. `0` by default.                                                                                          |
| `masterGainEnvelope`                          | array          | Optional sorted project master points `{id, frame, gainDb}`; section 14.7 defines their bounds and root-time evaluation.            |
| `masterBusMuted`                              | boolean        | `false` by default.                                                                                                                 |
| `busAudioEq`                                  | object         | Optional.                                                                                                                           |
| `currentFrame`, `zoomLevel`, `scrollPosition` | number         | View state the engine writes back as it read it. Commands do not change them, except that a retime carries `currentFrame` (14.5.2). |
| `inPoint`, `outPoint`                         | integer frame  | Optional. Clamped to the timeline's extent (12.2.7).                                                                                |
| `markers`                                     | array          | Present only when non-empty.                                                                                                        |
| `transitions`                                 | array          | Present only when non-empty.                                                                                                        |
| `keyframes`                                   | array          | Present only when non-empty. One entry per animated item.                                                                           |
| `compositions`                                | array          | Present only when non-empty. Compositions and groups (14.2.1).                                                                      |
| `topLevelSequenceIds`                         | array of id    | Present only when non-empty. Composition ids shown as timeline tabs (14.2.1).                                                       |

The timeline object is closed: the engine rebuilds it from its stores, so a field not listed here is **dropped** on the next edit. Native clients must not add timeline fields.

**Track.** `id`, `name`, `kind` (`video` or `audio`), `height`, `locked`, `syncLock`, `visible`, `muted`, `solo`, `volume` (track gain in dB, −60 to 12), `order`, and `items`, which is always an empty array in a stored graph (items live in `timeline.items`). In normal form `height` is always `100`: it is a local view preference that the engine resets on load. Optional fields: `gainEnvelope` (sorted owning-sequence `{id, frame, gainDb}` points; 13.10 defines admission and independent owner-time evaluation), `audioEq`, `color`, `parentTrackId`, `isGroup`, `isCollapsed`. Tracks are stored in ascending `order`, and names of the form `V1` or `A1` are derived from position (12.2.8).

**Marker.** `{ id, frame, color }`, plus `label` only when it is non-empty. A marker added without a colour gets `#3B82F6`.

### 2.4 Items

Every item has `id`, `trackId`, `from` (first frame, integer, at least 0), `durationInFrames` (integer, at least 1), `label` and `type`. The types are:

| `type`               | Required beyond the common fields                        | Notes                                                                                                  |
| -------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `video`              | `sourceStart`, `sourceEnd`, `sourceFps`, `mediaId`       | Library media. `src` is stored as `""`.                                                                |
| `audio`              | `sourceStart`, `sourceEnd`, `sourceFps`, `mediaId`       | A video's linked sound, or audio media.                                                                |
| `image`              | `mediaId`                                                | A still.                                                                                               |
| `text`               | `text`, `color`                                          | A title or caption.                                                                                    |
| `shape`              | `shapeType`                                              |                                                                                                        |
| `composition`        | `compositionId`, `compositionWidth`, `compositionHeight` | An instance of a composition (14.2.1).                                                                 |
| `adjustment`         |                                                          | Applies its effects to the tracks above it.                                                            |
| `controller`         | `controllerKind: "null"`, `transform`                    | A null object.                                                                                         |
| `lottie`, `subtitle` |                                                          | Produced by editor features; Lottie override maps may be updated by section 16. Preserve other fields. |

Source fields of a media clip are integer frames counted at `sourceFps`, the source's own rate, not the project's (section 3.4): `sourceStart`, `sourceEnd` and `sourceDuration`. `trimStart` and `trimEnd` are legacy counters. They are written as `0` when a clip is placed and must be preserved as found.

Common optional fields: `originId` (lineage shared by the parts of a split clip), `linkedGroupId` (shared by linked audio and video), `transform`, `crop`, `cornerPin`, `effects`, `blendMode`, `volume`, fades, audio EQ fields, `speed`, `motionModifiers`, `motionLayers` and `transformParent`. Parts 2 to 4 specify the commands that write them. The schema lists their types and ranges. Part 2 also reads and writes `embeddedAudioMuted` (set on a video that was unlinked from its sound, 12.6.1) and reads `textRole` and `captionSource` on text items (attached captions, 12.2.1). Part 3 writes `effects` (13.2.2), `motionModifiers` (13.6.2), `textMotion` on titles (13.7.1) and `frameleafKenBurns` on stills (13.7.2), and says how `blendMode` is edited (13.8.4). Part 4 writes `compositionId` and the composition window (14.2.1), `compositionControlOverrides` (14.4.2), and the style fields of a title (14.3.2).

`generatedId` replaces `mediaId` on an item that shows Frameleaf-generated media (for example a reversed conform). Such an item never carries `mediaId`, `src`, `audioSrc`, `thumbnailUrl`, `waveformData` or any `reverseConform*` field in a stored graph.

### 2.5 Unknown fields

- Fields of the project object and of items that this page does not know survive every command unchanged. A native client must carry them through without reordering or rewriting them.
- Unknown fields of the `timeline` object are dropped (2.3). Treat the timeline as closed.
- Key order inside objects does not matter. Array order does (section 6).

Fixture `normal-form/unknown-fields` shows both cases.

### 2.6 Normal form

The engine does not apply a command to the stored graph directly. It loads the graph, normalising it, applies the command, then serialises its state back. Every graph the engine writes is therefore in **normal form**, and normal form is a fixed point: applying an empty batch to it returns it byte for byte. Every applied fixture records this as `fixedPoint: true`, apart from the marked exceptions of section 10.

Loading normalises as follows:

- `schemaVersion` below 15 is migrated to 15.
- `metadata.frameRate` is written from `fps` when absent (section 3.2).
- Each track gets `height: 100`, and `syncLock: true`, `volume: 0`, `locked`, `visible`, `muted` and `solo` (false) when absent. `volume` is clamped to −60..12. `kind` other than `video`/`audio` is removed. Layer-group tracks (`isGroup`) are flattened away.
- Each track of a composition gets `syncLock: true` when absent (14.2.1), and a track of the main timeline that lists `items` has the list emptied.
- A frame rate above 120 is read as 120.
- Each item's `from` is rounded to a whole frame (at least 0) and `durationInFrames` to a whole frame (at least 1).
- `speed` is clamped to 0.1..10, `volume` to −60..12, and fades to at least 0.
- `transform.rotation` is reduced to 0..360, `transform.opacity` is clamped to 0..1, and `transform.cornerRadius` to at least 0.
- Overlapping items on one track are repaired by pushing the later one to the end of the earlier one, unless a transition joins them.
- Tracks are written in ascending `order`, and classic `V`/`A` names are renumbered by position (12.2.8, fixture `normal-form/tracks-sorted-and-renamed`).
- `inPoint` and `outPoint` are clamped to the timeline's extent (12.2.7, fixture `normal-form/in-out-clamped`).
- Empty `transitions`, `keyframes` and `markers` arrays are removed.

Fixture `normal-form/normalises-a-hand-written-graph` shows each rule.

**Native rule.** A native client edits only graphs in normal form, which is every graph the web engine or a conforming native client has saved. It must not write a graph that is not in normal form. If it receives a graph whose `schemaVersion` is not `15`, or which lacks `metadata.frameRate`, it must open it read-only and ask the person to open it once on the web. Version migrations are implementation-defined, and this protocol does not specify them. The web engine itself can save a graph outside normal form in the few cases section 11 lists (an overlap, a speed above 10, a clip gain or a rotation out of range, a rate above 120). A native client opens such a graph read-only too. The one exception is a graph that only has to **settle** (14.2.3): a native client reads it as its settled form and edits it.

## 3. Time, duration and rate

### 3.1 Two representations

- **Command payloads** carry exact rational seconds: `{ "num": integer, "den": integer }`, with `den > 0`. The catalogue types `time`, `duration` and `rate` are all this shape. A `time` is an instant on the sequence, a `duration` is a length or a signed delta, and a `rate` is frames per second or a speed factor.
- **The graph** stores integer frames at the project rate (`from`, `durationInFrames`, keyframe `frame`, marker `frame`, transition `durationInFrames`), and integer source frames at the clip's `sourceFps`.

Rationals sent to the server must be **reduced**: the greatest common divisor of `num` and `den` is 1, so zero is `{ "num": 0, "den": 1 }`. Both must be safe integers (magnitude below 2^53). The engine accepts unreduced pairs, but the server refuses them, so a native client always reduces.

### 3.2 The project rate

The exact project rate is `metadata.frameRate`. The engine reads it from `metadata` as follows:

1. If `frameRate` is present and `frameRate.num / frameRate.den` equals `fps` (within 1e-9), `frameRate` is the rate.
2. Otherwise it reads `fps`. An integer is itself. A decimal within 1e-9 of `n/1001`, or equal to `n/1001` rounded to three decimals, is `n/1001`, for `n` in 24000, 30000, 48000, 60000 and 120000 (23.976, 29.97, 47.952, 59.94 and 119.88). Any other value has no exact reading, and every command on such a graph is refused (`invalid`, "The project frame rate has no exact reading").

On output the engine always writes both: `frameRate` as the exact pair and `fps` as the float `num / den` (for example `29.97002997002997`). Fixture `normal-form/legacy-decimal-rate` shows a legacy `29.97` graph gaining its pair.

### 3.3 Seconds to frames

A payload time `t = num/den` seconds becomes the frame nearest `t × rate`. Exact halves round towards positive infinity:

```text
frames = floor( (2 · num · rate.num + den · rate.den) / (2 · den · rate.den) )
```

Compute this with exact integers (64-bit is not always enough; use arbitrary precision). The result must be a safe integer, or the command is refused (`invalid`, "The time is out of range").

- A `time` field that rounds to a negative frame is refused ("must not be negative").
- A signed `duration` delta (`clip.push`, `clip.slide`, `clip.slip`) may be negative. Its halves also round towards positive infinity, so −½ frame becomes 0 and −1½ frames becomes −1. This is not the "away from zero" rounding of the host's playback helper. **Native rule:** use this formula for every payload conversion.
- A value that is not a rational with safe-integer `num` and `den` and positive `den` is refused ("must be an exact rational time"). This includes a JSON number.

`vectors.frames` in the fixtures lists worked cases, including NTSC rates and an overflow (`frames: null`).

### 3.4 Source frames

A media clip's `sourceStart`/`sourceEnd` count frames of the source at `sourceFps`. That is the media's own frame rate, copied from the media record when the clip is placed. Converting a source time to source frames uses the same formula with `sourceFps` read as in 3.2, step 2. A source whose rate has no exact reading cannot be edited by commands that convert source time.

### 3.5 The media record

Commands that place library media read a **media record** for each asset. This is the engine's view of the asset, and it is not stored in the graph. The fields that matter (schema `$defs/mediaRecord`):

| Field             | Meaning                                                                                             |
| ----------------- | --------------------------------------------------------------------------------------------------- |
| `id`              | The library asset id. It becomes the item's `mediaId`.                                              |
| `fileName`        | Becomes the item's `label`.                                                                         |
| `mimeType`        | `image/*` places an `image`, `video/*` a `video`. Anything else is refused.                         |
| `duration`        | Seconds.                                                                                            |
| `width`, `height` | Pixels. They become `sourceWidth`/`sourceHeight`.                                                   |
| `fps`             | The video's frame rate (0 for a still). It becomes `sourceFps`.                                     |
| `audioCodec`      | Present when the video has sound. Its presence alone decides whether a linked audio item is placed. |
| `colorTransfer`   | Optional: `sdr`, `pq`, `hlg` or `hdr`. The last three make a project HDR (`studio/spec/hdr.md` H3). |

A native client builds the record from the asset's metadata, as the web host does when it probes the asset. `GET /studio/assets/{id}/media-facts` (FL-348) reads the original for it: `fps` (the exact `frameRate` pair as a float), `width`, `height`, `durationSeconds`, and `audioCodec`, present exactly when `hasAudio` is true. The fixtures give the records they used (`media.standard`). Two clients that disagree on a record produce different graphs. That is a media qualification issue, not a protocol one.

## 4. Ids

### 4.1 Which ids exist

All ids are strings, unique within their kind in the graph: items, tracks, transitions, keyframes, effects, markers, compositions, modifiers and published controls. Ids minted by commands have the UUID version 4 layout (8-4-4-4-12 lowercase hex). Ids already in a graph may have any non-empty form (`v1`, `main`), and they must never be rewritten.

### 4.2 Deterministic minting

The engine does not mint random ids while applying a command. Every id an envelope creates is drawn, in order, from a stream seeded by:

```text
seed = idempotencyKey + ":" + batchIndex
```

Here `batchIndex` is the envelope's zero-based position in the batch the engine was given. The web host gives the engine one envelope at a time, so in practice the index is `0` and the seed is `idempotencyKey + ":0"`. Retrying an envelope with the same key therefore mints the same ids, and two envelopes with the same key at different positions mint different ones (fixture `ids/same-key-different-index`).

The stream is a 32-bit generator seeded by a string hash. All arithmetic is on unsigned 32-bit integers. "Multiply" keeps the low 32 bits of the product, "rotl r" rotates left by r bits, and "xor" is bitwise.

1. **Hash the seed.** Let `h = 1779033703 xor L`, where `L` is the seed's length in UTF-16 code units. For each UTF-16 code unit `c` of the seed, in order, set `h = h xor c`, then `h = h × 3432918353`, then `h = rotl13(h)`.
2. **Draw four state words.** Each draw sets `h = (h xor (h >> 16)) × 2246822507`, then `h = (h xor (h >> 13)) × 3266489909`, then `h = h xor (h >> 16)`, and yields `h`. The first four draws are `a`, `b`, `c`, `d`.
3. **Generate.** Each output computes `t = a + b`, then sets `a = b xor (b >> 9)`, `b = c + (c << 3)`, `c = rotl21(c)`, `d = d + 1`, `t = t + d`, `c = c + t`, and yields `t`. All additions wrap modulo 2^32, and `>>` is a logical shift.
4. **Make an id.** Take 16 consecutive outputs and keep the top byte of each (`output >> 24`). That gives bytes 0 to 15. Set byte 6 to `(byte6 and 0x0f) or 0x40` and byte 8 to `(byte8 and 0x3f) or 0x80`. Write the bytes as lowercase hex, grouped 8-4-4-4-12 with hyphens.

Each id consumes 16 outputs. `vectors.uuids` in the fixtures gives the first ids for several seeds, including non-ASCII and long ones. Use it to test an implementation before anything else.

### 4.3 Which draw goes where

Each applied fixture records, for each envelope, its `draws`: draw number `n`, the id, and every graph path that holds it. Draws that a command makes but does not keep are listed with no paths. They still consume their 16 outputs, and a native client must skip them in the same order. Unkept draws after an envelope's last kept one are not listed, because nothing depends on them. Parts 2 to 4 give the draw order for each command in prose. The fixtures are authoritative where the two differ. A track that a command creates has the id `track-` followed by the drawn id; `draws` lists that draw at the track's `id` path.

For example, `clip.add` of a video with sound (fixture `ids/clip-add-draws`) draws the shared `originId` first, then the shared `linkedGroupId`, then the video item's `id`, then the audio item's `id`.

The engine also fixes its clock to the envelope's `issuedAt` while it applies it. No field written by a command in this protocol depends on the clock. `createdAt`, `updatedAt` and `duration` on the project are left as they were (fixture `ids/issued-at-does-not-change-ids`).

## 5. Ordering and overlap

- **Array order is data.** The engine writes `timeline.items` in its own order: existing items keep their positions, and items a command creates are appended in the order the command creates them. Removed items leave no gap. Tracks are written in ascending `order` (12.2.8). Each command's rules (parts 2 to 4) say where its new entries go, and the fixtures fix it exactly.
- **Compositing order** is the track `order` value, ascending: the lowest `order` is the top layer. `order` may be fractional (`track.add` at an index between two tracks takes the midpoint).
- **No overlap on a track.** Two items on one track never share a frame, unless a transition joins them (13.2.3). Commands that would create an overlap are refused (`failed`, "... would overlap ..."), or they place, trim or ripple so that none results, as each command's rules state. `clip.move` is the exception: it does not check (12.3.3). Loading a graph that has an overlap repairs it (2.6). A native client must never save one.
- **Linked items** share a `linkedGroupId`: normally a video and its sound. How far an edit to one reaches the others differs by command: 12.2.1 defines linked groups, synchronised clips and attached captions, and each command states what it does with them.
- **Locked tracks.** A track with `locked: true` is meant to be left alone, but the engine enforces that command by command, and several commands do not check (12.2.2). A native client treats a lock as binding for every command.

## 6. Canonical serialisation and digests

Both digests are the lowercase hex SHA-256 of the UTF-8 bytes of a **canonical JSON** text.

Canonical JSON of a value:

- `null`, `true`, `false`: as JSON.
- A number: the shortest round-tripping decimal form, as ECMAScript's `Number.prototype.toString` writes it. `1e21` is written `1e+21`, `1e-7` is written `1e-7`, `-0` is written `0`, and `5e-324` stays `5e-324`. Integers below 1e21 have no exponent and no `.0`. Non-finite numbers never occur in a graph.
- A string: JSON-quoted as ECMAScript's `JSON.stringify` writes it. `"` and `\` are escaped, as are control characters below U+0020 (`\b \f \n \r \t`, others as `\u00XX` with lowercase hex). Every other character, including non-ASCII, U+007F and U+2028, is written as itself in UTF-8.
- An array: `[` + the elements' canonical JSON joined by `,` + `]`, in order.
- An object: `{` + members joined by `,` + `}`, where each member is the JSON-quoted key + `:` + the value's canonical JSON. Members are sorted by key in ascending UTF-16 code-unit order (not code-point order, and not locale order). Members whose value is absent are omitted.
- No whitespace anywhere.

`vectors.canonicalJson` in the fixtures gives the canonical text and its SHA-256 for edge cases: number forms, escapes, non-ASCII and astral keys, and nesting.

The two digests:

| Digest              | Over                                                                                                 | Where it appears                                                                                      |
| ------------------- | ---------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **Graph digest**    | The graph object                                                                                     | The engine's own result. Every fixture's `digest`.                                                    |
| **Envelope digest** | `{ "schemaVersion": 1, "engine": "freecut", "engineRevision": <pinned revision>, "graph": <graph> }` | The server's `digest` on a project, a revision and a save response. Every fixture's `envelopeDigest`. |

A native client computes the envelope digest of what it saves. If it equals the head's `digest`, the save is a no-op (`unchanged: true`). A retried save must carry the same `requestKey` and the same digest.

## 7. Commands and batches

### 7.1 The envelope

A command envelope is `{ id, payload, revision, idempotencyKey, issuedAt }`:

| Field            | Rule (server-checked)                                                                                                                                                                                          |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`             | A command id from the catalogue.                                                                                                                                                                               |
| `payload`        | An object. Every required field is present, every present field has its catalogue type, and no other field is allowed. Optional fields may be `null` to clear what they name (where a command's rules say so). |
| `revision`       | The head revision the client was editing (integer, at least 0). It must not be later than the save's `expectedRevision`.                                                                                       |
| `idempotencyKey` | 1 to 128 characters, unique among the commands of one save. It seeds the id stream (4.2).                                                                                                                      |
| `issuedAt`       | Milliseconds since the epoch, finite.                                                                                                                                                                          |

### 7.2 Applying a batch

The engine applies an ordered batch of envelopes atomically. Either every envelope applies, or the input graph is returned untouched with the **first** failing envelope's index and a reason:

| Reason            | Meaning                                                                                                            |
| ----------------- | ------------------------------------------------------------------------------------------------------------------ |
| `invalid`         | The payload contradicts the graph or the rules: a missing clip, a time outside a clip, a malformed value.          |
| `failed`          | The payload is well formed, but the edit cannot be made here: a locked track, an overlap, not enough source media. |
| `not-implemented` | The command is in the catalogue but the engine does not implement it (8.2).                                        |

The web host adds `stale-revision` (the graph changed while the engine worked) and, for undo/redo, its own refusals (section 9).

Later envelopes in a batch see the graph the earlier ones produced. That includes a rate change: after `sequence.setSettings` changes the project rate, later envelopes' times convert at the new rate (fixture `batch/rate-change-moves-later-times`).

The fixtures record a refusal's index, reason and the engine's English `detail`. A native client must match the index and reason. The detail text is informative only.

### 7.3 What a save carries

A save's `commands` are the envelopes that produced the graph, in order, up to 500. The server checks each one (7.1) and counts them into the revision summary. Only commands the catalogue marks `mutatesGraph` may appear. The `history.*` commands are not sent in a save (section 9).

## 8. Command index

### 8.1 Status of every graph-changing command

The catalogue has 74 commands with `mutatesGraph: true`.

- **Engine (56):** the engine gives them meaning. Their mutation rules are in parts 2 to 4, captions, Lottie maps, masks and relinking: sections 12 to 17.
- **Host (2):** `history.undo` and `history.redo` are answered by the host's history (section 9).
- **Bundle (1):** `project.importBundle` creates a new project from an uploaded bundle through the bundle import API. It does not change the open graph.
- **Not implemented (15):** the remaining 15 are refused by the engine as `not-implemented` (8.2).

## 9. Undo and redo

Undo and redo are not engine operations. The host answers them over graphs it has already stored.

- **Session history.** Each accepted engine command records the graph it replaced. `history.undo` restores the most recent replaced graph exactly, byte for byte, as the next draft. `history.redo` re-applies the graph that undo replaced. A new accepted command clears the redo stack. A refused command records nothing. The session keeps the 100 most recent replaced graphs and drops the oldest beyond that.
- **Past the session.** When the session history is empty and the head revision is above 1, `history.undo` restores the stored revision `head − 1` as a new revision. History is append-only, so a restore is itself a new revision whose `restoredFromRevision` names its source. Which graph `head − 1` holds depends on when autosave wrote revisions, so the result is **implementation-defined**. **Native rule:** a native client keeps its own session history with the same semantics and limit, and goes past it only through the server's revision restore, never by guessing a graph.
- **`toRevision`.** With `toRevision`, undo or redo restores that stored revision as a new head and clears the session history. A value below 1, or a revision that cannot be restored, is refused (`invalid`). The current head is a no-op.
- **Nothing to do.** With no session history, undo at revision 1 and redo with nothing undone are refused (`invalid`).
- **Saving.** A graph produced by undo or redo is saved like any other. Its `commands` are the envelopes still in effect, and the `history.*` envelopes themselves are not sent.

The `history` scripts in the fixtures replay sequences of commands, undos and redos through the host's own history. For each step they record the outcome, the graph digest, the earliest earlier state with the same digest (`sameAs`, where 0 is the base), and the undo and redo depths. They model each staged graph as one stored revision, so steps that undo past the session show the implementation-defined case above.

| Key             | Contents                                                                                                                            |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `engine`        | The engine name and pinned revision the answers came from.                                                                          |
| `media`         | Named sets of media records (3.5).                                                                                                  |
| `seeds`         | Hand-written starting graphs, possibly not in normal form.                                                                          |
| `bases`         | `seed` + `setup` envelopes → the engine's `graph` and `digest`. Cases start from a base's `graph`.                                  |
| `vectors`       | `canonicalJson`, `uuids`, `frames` and `retime` (14.5.1) test vectors.                                                              |
| `cases`         | `base`, `media`, an `envelopes` batch → `expect`. `outsideNormalForm`, `engineArithmetic` and `settlesOnLoad` mark the cases below. |
| `history`       | `base` + `steps` (command, undo or redo) → one outcome per step (section 9).                                                        |
| `commandStatus` | Each graph-changing command's `status`, owning `story` and `section` of this page (8.3).                                            |

A case's `expect` is one of:

- `{ "status": "applied", "graph", "digest", "envelopeDigest", "fixedPoint", "clockIndependent", "draws" }`: the graph is the full expected graph, and `draws` lists each envelope's id draws (4.3). `fixedPoint` records that an empty batch returns the graph unchanged (2.6). `clockIndependent` records that the same batch with a different `issuedAt` gives the same graph (4.3).
- `{ "status": "rejected", "index", "reason", "detail" }`.

A case with `"outsideNormalForm": true` records an edit the engine **accepts but should not**: its `graph` is not in normal form, so `fixedPoint` is `false` and the graph breaks the schema or the no-overlap rule of section 5. Section 11 lists these edits. They are recorded so that the engine's behaviour is pinned, not so that a native client copies it.

A case with `"engineArithmetic": true` is an applied case whose graph is in normal form but holds values this protocol does not specify to the last bit (13.1). Its answer is the engine's.

A case with `"settlesOnLoad": true` is an applied case whose graph is one load short of normal form (14.2.3). `fixedPoint` is `false`, and `expect` also holds `"settled": { "digest", "envelopeDigest", "fixedPoint" }`: the digests of the graph after one load, and that the loaded graph is a fixed point. A case is never both `settlesOnLoad` and `outsideNormalForm`.

**Running them natively.** For each case, load the base graph, apply the envelopes with the case's media records, and compare the result:

- An applied case must give the expected graph, compared by graph digest, and the expected ids.
- A rejected case must be refused at the same index with the same reason, leaving the graph untouched.
- A case marked `outsideNormalForm` must be **refused** by a native client at the index of its last envelope, leaving the graph untouched. A native client never produces its graph.
- A case marked `settlesOnLoad` must give the **settled** graph: compare with `expect.settled.digest`. The settled graph is `expect.graph` with the two changes of 14.2.3.
- A case marked `engineArithmetic` must give the expected graph, bit for bit, in a client that offers the edit. A client that does not offer it must refuse the batch at the index of its last envelope (13.1).

Run the vectors first: id generation, canonical JSON and the two rounding rules must be right before any graph can match.

**Drift.** Two checks keep this page and the engine together:

- The engine replay runs in the Studio engine workflow. It recomputes every answer, fails on any difference, and checks that a second run gives identical answers. The same run rebuilds the parameter catalogue from the engine registries and fails on any difference (13.2.1).
- `studio/tools/graph-protocol.test.mjs` runs in the Scripts unit tests on every pull request, without the engine. It re-derives every digest, id draw and rounding answer from an independent implementation of sections 3, 4 and 6, and validates every graph against the schema. For part 2 it also checks the rules of section 12 that can be computed from a graph alone: no overlap, track order and names, in and out points, the transitions repair keeps, split and trim source frames, retimed length and speed, and that every part 2 command has applied and rejected cases. For part 3 it re-derives the parameter catalogue's own digest, requires the effects, blend modes and transitions the command catalogue names, and checks that every effect, transition, easing, modifier and text motion preset in a graph is one the catalogue lists. For part 4 it re-derives the retime vectors, and checks that a case settles on load exactly when it is marked so and that its settled digest follows from the rule of 14.2.3. Then it replays every case of parts 2, 3 and 4 through `studio/tools/graph-reference.mjs`, an implementation written from sections 12 to 14 and the parameter catalogue without the engine, and requires the engine's graph, digest and refusal for each. That file is a test of this page, not part of the protocol: it shows that the prose is enough. It skips, by name, only the six cases of engine arithmetic.
- **Coverage.** The same check reads the command catalogue and this page. Every `mutatesGraph` command must have a `commandStatus` entry and exactly one row in section 8.3 that agree, in a section that exists. An engine command must have applied and rejected fixtures (`music.add`: rejected only). A command the engine does not apply must have a fixture in which the engine refuses it as `not-implemented`, and a native rule in its row. A host command must also appear in a `history` script. A command added to the catalogue without all of this fails the check.

A change to the engine that alters any answer or any catalogue value fails the first check. A hand edit of any answer or catalogue value fails the second, and so does a command that this page does not cover.

## 12. Part 2: clips, timeline edits, tracks and markers

This section gives the mutation rules of the 28 commands of FL-307 (NAPI-018). The engine implements all of them at this revision. `music.add` is implemented as a refusal (12.8.4).

| Commands                                                                                  | Section |
| ----------------------------------------------------------------------------------------- | ------- |
| `clip.add`, `clip.delete`, `clip.move`, `clip.split`                                      | 12.3    |
| `clip.trimStart`, `clip.trimEnd`, `clip.roll`, `clip.slip`, `clip.slide`, `clip.setSpeed` | 12.4    |
| `clip.push`, `clip.reorder`, `clip.insert`, `clip.overwrite`, `clip.join`                 | 12.5    |
| `clip.setLink`, `clip.update`, `clip.setTransform`, `clip.setTransformParent`             | 12.6    |
| `track.add`, `track.remove`, `track.reorder`, `track.set`, `track.closeGap`               | 12.7    |
| `marker.add`, `marker.update`, `marker.remove`, `music.add`                               | 12.8    |

Every command has fixtures named `<command>/<case>` in `studio/graph-conformance-v1.json`, both applied and rejected (`music.add` has only rejected ones). Cases named `…busy-timeline…` run a command on a timeline with two video layers, a linked chain and a transition, so that its linked, sync-lock and transition consequences show together. Where this prose and a fixture differ, the fixture is right and this page has a defect.

### 12.1 How to read the rules

- A **clip** is an item of the main timeline (`timeline.items`). Commands address clips of the main timeline only. An id of a clip inside a composition is unknown to them (fixture `clip.move/rejects-clip-inside-composition`).
- `end(c)` is `c.from + c.durationInFrames`: the first frame after the clip. A clip **spans** frame `f` when `c.from < f < end(c)`.
- Each command lists its **refusals in the order the engine checks them**. The first that applies decides the reason. A native client must report the same reason.
- These refusals are common to every command and are not repeated: a required string field that is missing, empty or not a string is `invalid`; a `clipId` that names no clip, and a `trackId` that names no track, is `invalid`; a time field is checked as section 3.3 says.
- After its checks, a command applies its edit and then **verifies the result**. Where the engine could not make the edit exactly as asked, the command is refused as `failed` and nothing changes. So limits below are stated as conditions: when one does not hold, the command is `failed`.
- A command that asks for what is already so is **applied and changes nothing**, unless its rules say otherwise.
- Where a command is refused because two clips of a track would **share a frame**, a transition between the two does not excuse it. The exception of section 5 applies to stored graphs, not to these checks.
- Each command states five consequences: **Linked** clips, **Locks**, **Sync lock**, **Overlap** and **Transitions**. "None" means the command neither reads nor changes that.
- **Draws** lists the ids the command mints, in order (section 4.3).

### 12.2 Shared rules

#### 12.2.1 Linked clips

- The **linked group** of a clip `c` is every item with `c`'s `linkedGroupId`. A clip with no `linkedGroupId` has a **legacy link**: if it is a video or audio clip with an `originId` and a `mediaId`, its group is itself plus every clip of the other kind (audio for video, video for audio) with the same `originId`, the same `mediaId`, the same `from` and the same `durationInFrames`. Otherwise its group is itself alone. Fixtures `clip.move/legacy-linked-pair` and `clip.move/legacy-link-ends-when-extents-differ`.
- The **synchronised** clips of `c` are the members of its linked group that have the same `from`, `durationInFrames`, `sourceStart`, `sourceEnd` and speed as `c` (an absent `speed` is 1; an absent source field equals only another absent one). `c` is always one of them.
- The **attached captions** of a clip that is not a text item are the text items with `captionSource.clipId` equal to its id. Captions are made by caption features outside this protocol's commands. A native client never creates them, and must carry them through as these rules say.
- The **linked set** of some clips is those clips, every member of their linked groups, and the attached captions of all of these.
- The engine has a linked-selection switch. It is **on** when a command runs, except where a command's rules turn it off. With it off, the linked set of some clips is those clips and their attached captions only.

#### 12.2.2 Locks

A track with `locked: true` is locked. Lock checking is **per command and is not uniform**:

| Lock checking                                     | Commands                                                                                                                                                 |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Refuse when any clip they would change is locked  | `clip.roll`, `clip.slip`, `clip.slide`, `clip.push`, `clip.join`, `clip.reorder`, `clip.overwrite`, `track.closeGap`, `track.remove`                     |
| Check some of what they change (see each command) | `clip.move`, `clip.setSpeed`, `clip.insert`                                                                                                              |
| Check nothing                                     | `clip.add`, `clip.delete`, `clip.split`, `clip.trimStart`, `clip.trimEnd`, `clip.setLink`, `clip.update`, `clip.setTransform`, `clip.setTransformParent` |

The twelve commands of part 3 check nothing either (13.1). The last two rows are **implementation-defined**: the engine's own editor never lets a person edit a locked track, so its edit actions were never guarded, and the command layer guards only some of them. **Native rule:** a native client treats a lock as binding for every command. It must not issue a command that would add, remove or change a clip on a locked track, including through a linked clip or a ripple. Given such an envelope in a fixture, a conforming implementation still produces the engine's graph.

`track.closeGap` checks the lock of every **attached caption** in its affected linked set (12.7.5). Other commands' caption lock behaviour remains as recorded by their own sections and fixtures.

Track commands (`track.set`, `track.reorder`) may change a locked track itself. That is how a track is unlocked.

#### 12.2.3 Sync lock and ripple

A track is **sync-enabled** when it is not locked and its `syncLock` is not `false`. A ripple edit changes the tracks it edits directly (its **edited tracks**) and then keeps every other sync-enabled track in step, in stored track order, by one of two procedures. A track that is locked or has `syncLock: false` is left exactly as it is.

**Remove an interval `[a, b)` from a track.** For each clip on the track that shares a frame with the interval, in order of `from`:

| The clip                                   | What happens                                                                                                                   |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| lies inside (`from ≥ a` and `end ≤ b`)     | It is removed, with its transitions and keyframes.                                                                             |
| spans the interval (`from < a`, `end > b`) | It is split at `a`, then its right part is split at `b`. The middle part is removed. Two ids are drawn; the first is not kept. |
| starts before only (`from < a < end ≤ b`)  | It is split at `a` and the right part is removed. One id is drawn and not kept.                                                |
| ends after only (`a ≤ from < b < end`)     | It is split at `b` and the left part is removed. The left part keeps the clip's id, so **the surviving tail has a new id**.    |

Then every clip on the track with `from ≥ b` moves left by `b − a`. Several intervals are merged where they touch, sorted, and removed in order, each one measured after the earlier removals.

**Open a gap of `n` frames at frame `c` on a track.** Each clip that spans `c` is split at `c` (one id drawn each, in order of `from`). Then every clip on the track with `from ≥ c` moves right by `n`.

Each split here is the split of 12.2.5 applied to that clip **alone**. A clip with a `linkedGroupId` that is cut this way therefore loses it on both halves (fixture `clip.delete/ripple-linked-clip-cut-alone-loses-group`). The halves of a video and its sound cut at the same frames stay linked by the legacy link.

Fixtures: `clip.delete/ripple-sync-lock-cuts-head`, `…-cuts-middle`, `…-removes-covered`, `…-off`, `clip.delete/ripple-locked-track-untouched`, `clip.trimEnd/ripple-earlier`, `clip.trimEnd/ripple-later`, `clip.insert/sync-locked-track-opens-gap`.

#### 12.2.4 Source frames

Video, audio and composition clips are **media clips**: they carry a source window `[sourceStart, sourceEnd)` in source frames, inside `[0, sourceDuration)`. Stills, titles and every other type are not media clips for these rules, even though a still carries source fields (12.3.1): trimming and splitting a still changes only `from` and `durationInFrames`.

Two conversions are used. Both are computed in IEEE-754 double precision, in the order written. `fps` is `metadata.fps`, `sourceFps` is the clip's stored `sourceFps` (or `fps` when absent) and `speed` is the clip's `speed` (or 1):

```text
toSource(n)   = floor( ((n / fps) * sourceFps) * speed + 0.5 )     timeline frames -> source frames
toTimeline(s) = floor( ((s / sourceFps) * fps) / speed )           source frames -> timeline frames
```

`toSource` rounds to the nearest source frame with halves towards positive infinity, for negative `n` too. These are the engine's floating-point rules, not the exact rational rule of section 3.3. That rule applies only to payload values.

**Trim the start by `a` frames** (`a > 0` shortens): `from` and `sourceStart` grow, `durationInFrames` shrinks.

```text
from += a        durationInFrames -= a        sourceStart += toSource(a)     (media clips)
```

Limits: `durationInFrames − a ≥ 1`, and for a media clip `−a ≤ toTimeline(sourceStart)`.

**Trim the end by `a` frames** (`a > 0` lengthens):

```text
durationInFrames += a        sourceEnd = min(sourceDuration, max(sourceStart + 1, sourceEnd + toSource(a)))     (media clips)
```

Limits: `durationInFrames + a ≥ 1`, and for a media clip with a `sourceDuration`, `durationInFrames + a ≤ toTimeline(sourceDuration − sourceStart)`.

Every media clip this protocol places carries `sourceStart`, `sourceEnd` and `sourceDuration`. Older graphs may lack them: an absent `sourceStart` is 0; without a `sourceDuration` the `min` above is dropped; and for a clip with no `sourceEnd` the end trim writes `sourceEnd = sourceStart + toSource(new durationInFrames)`, within the same bounds.

A clip with `isReversed: true` follows mirrored rules that this protocol does not specify. **Native rule:** a native client must not trim, split, slip, slide, roll, retime or join a reversed clip.

#### 12.2.5 Splitting a clip

Splitting clip `c` at frame `s` (which `c` must span) gives two clips:

- The **left** half keeps `c`'s id and its place in `timeline.items`, with `durationInFrames = s − from`.
- The **right** half has a newly drawn id, `from = s` and the rest of the length. It is appended to `timeline.items`.
- Both get `originId = c.originId`, or `c.id` when `c` had none. Every other field is copied to both halves unchanged.
- For a media clip, with `L` and `R` the two lengths: the left half has `sourceStart` (written as `0` if it was absent) and `sourceEnd = sourceStart + toSource(L)`. The right half starts there and has `sourceEnd = sourceStart + toSource(L + R)`, computed from the original `sourceStart`. The original `sourceEnd` is not copied.
- A transition out of `c` (`leftClipId` = `c`) now leaves from the right half. A transition into `c` stays with the left half.

When several clips are split **together** (a linked group), the right halves are drawn in the clips' order in `timeline.items`. Then, if two or more of them had a `linkedGroupId`, two more ids are drawn: every left half gets the first as its `linkedGroupId` and every right half the second. If exactly one of them had a `linkedGroupId`, both of its halves lose it. Section 13.2.7 says what a split does with keyframes, effects and other animation.

A clip cannot be split inside a transition it takes part in. For a transition of `d` frames (`alignment`, which is 0.5 on every transition a command adds, 13.2.3), with `p = floor(d × alignment)`: the outgoing clip cannot be split in its last `p` frames, and the incoming clip cannot be split in its first `d − p` frames.

#### 12.2.6 Transition repair

Section 13.2.3 specifies transitions, and 13.4.1 the command that creates them. Part 2 commands never create one, but they move and resize the clips that transitions join. After a command, the engine **repairs** each transition whose outgoing clip (`leftClipId`, `L`) or incoming clip (`rightClipId`, `R`) the command **changed**. A transition that names no changed clip is not looked at, even if it would fail. Each command says which clips count as changed. With `E = end(L)`:

1. If `L` or `R` no longer exists, the transition is removed. Commands that delete clips remove their transitions first.
2. If the clips are on different tracks, it is removed.
3. If `|E − R.from| ≤ 1` the clips **meet**. Otherwise, if `R.from < E` they **overlap**. Otherwise (`R.from > E + 1`) the transition is removed.
4. If either clip is not a video, image or composition item, it is removed.
5. **Meet:** let `M` be the longest length the clips' handles allow (below). If `M ≤ 0` the transition is removed. If `durationInFrames > M` it becomes `M`.
6. **Overlap:** let `O = E − R.from`. If `O < durationInFrames`, the length becomes `max(2, O)` when that is shorter than both clips, and the transition is removed when it is not. Otherwise, if `durationInFrames` is not shorter than both clips, it becomes `max(2, min(L, R lengths) − 1)`.

Transitions that pass unchanged keep their order in `timeline.transitions`. Transitions whose length was changed are moved after them, in their own order. When the list becomes empty the key is removed.

`M` is the largest `d` from 1 to `min(L, R lengths) − 1` for which `d − floor(d × alignment)` frames fit in `L`'s tail handle and `floor(d × alignment)` frames fit in `R`'s head handle. The tail handle of a video or composition clip is `toTimeline(sourceDuration − sourceEnd)`, and its head handle is `toTimeline(sourceStart)`. An absent `sourceEnd` counts as `sourceDuration` and an absent `sourceDuration` as 0, so such a clip has no tail handle. A still has unlimited handles.

Some commands refuse an edit that would starve a transition instead of repairing it afterwards. For them a transition is **valid** between two clips when rules 2 to 4 keep it, its length is at most `min(L, R lengths) − 1`, and, when the clips meet, its two parts fit the handles as in the definition of `M`. Such a command is refused (`failed`) unless every transition it names is valid both before the edit and with the edited clips in place.

Rule 3 is **implementation-defined**: the overlap branch exists for projects made before transitions were cut-centred, and it accepts any incoming clip that starts before the outgoing clip ends, however far apart the clips now are. A transition therefore survives when its outgoing clip is moved later, or the clips swap places (fixtures `clip.move/transition-survives-outgoing-clip-moved-later`, `clip.reorder/transition-survives-out-of-order`), and is removed only when the incoming clip starts more than one frame after the outgoing clip ends (`clip.move/removes-transition`). **Native rule:** apply rules 1 to 6 literally. Do not remove a transition that they keep.

When both clips of a transition move in one command and end on one track, the transition's `trackId` becomes that track.

#### 12.2.7 In and out points

`timeline.inPoint` and `timeline.outPoint` are clamped to the timeline's extent. Let `last` be the greatest `end(c)` over all clips (0 with no clips) and `max = max(last, floor(10 × fps), 1)`:

- `inPoint` is clamped to `0..max` and `outPoint` to `1..max`.
- If both are set and `inPoint ≥ outPoint` after that: when `inPoint ≥ max` they become `max − 1` and `max`; otherwise `outPoint` becomes `min(max, inPoint + 1)`.

Loading a graph applies this (it is part of normal form, fixture `normal-form/in-out-clamped`). A command applies it again **each time `last` changes while the command runs**. For every command but one this equals clamping once to the final extent (fixture `clip.delete/clamps-in-out-points`). `clip.overwrite` first removes what it covers and then places its clip, so it clamps to the smaller extent in between (12.5.4). A command that does not change `last` leaves both points alone.

#### 12.2.8 Tracks: order and names

- `timeline.tracks` is always written in ascending `order`. Tracks with equal `order` keep their relative order.
- **Classic names.** A video track whose name is `V` followed by digits, or an audio track whose name is `A` followed by digits (either case), has a classic name. Classic names are **derived from position** and rewritten whenever a command writes the track list (every track command, and `clip.add`, `clip.insert` and `clip.overwrite` when they create an audio track), and on load. Among the video tracks with classic names, the one with the greatest `order` is `V1`, the next `V2`, and so on upwards. Among the audio tracks with classic names, the one with the least `order` is `A1`, the next `A2`, and so on downwards. A track with any other name keeps it and takes no number.
- Loading applies both rules (fixture `normal-form/tracks-sorted-and-renamed`).
- A track a command creates is `{ id, name, kind, height: 100, locked: false, syncLock: true, visible: true, muted: false, solo: false, volume: 0, order, items: [] }`. Its `id` is `track-` followed by a drawn id. Its first name is `V` or `A` followed by the smallest positive number no classic name of that kind uses, before the renumbering above.

### 12.3 Placing, deleting, moving and splitting

#### 12.3.1 `clip.add`

Places library media on a video track at its natural or a given length. Payload: `assetId`, `trackId`, `at`, optional `duration`, optional `kind`.

**Refusals, in order**

1. `trackId` names no track: `invalid`.
2. `at` is not a valid non-negative time: `invalid`.
3. `duration` is given and rounds to less than one frame: `invalid`.
4. `assetId` has no media record: `invalid`.
5. The record's `mimeType` is neither `image/*` nor `video/*`: `invalid`.
6. `kind` is given and is not the media's kind. A still accepts `image` and `photo`; a video accepts `video`: `invalid`.
7. The track's `kind` is `audio`: `invalid`. A track with no `kind` counts as a video track.
8. The media is a video and `duration` is longer than its natural length: `invalid`.
9. The place is taken (below): `failed`.

**Effect.** With `fps` the project rate as a number and `rate` the record's `fps`:

- The **natural length** is `round(record.duration × fps)` frames. When that is 0, it is `3 × fps` for a still and `fps` for a video, rounded to a whole frame. The clip's `durationInFrames` is `duration` in frames when given, else the natural length.
- A video whose record has an `audioCodec` also places a **linked audio clip** of the same `from` and length on the audio track with the least `order`. When the graph has no audio track, one is created first with `order = max(0, greatest order) + 1` (12.2.8).
- The items are appended to `timeline.items`, video (or still) first, then audio.

Fields of a placed item:

| Field                         | Value                                                                                                                           |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `id`, `originId`              | Drawn. The audio clip shares the video's `originId`.                                                                            |
| `linkedGroupId`               | Drawn, shared by the pair. Absent when no audio clip is placed.                                                                 |
| `type`                        | `video`, `image` or `audio`.                                                                                                    |
| `trackId`, `from`             | As placed. `durationInFrames` as above.                                                                                         |
| `label`                       | The record's `fileName`.                                                                                                        |
| `mediaId`                     | The asset id.                                                                                                                   |
| `src`                         | `""`.                                                                                                                           |
| `sourceFps`                   | `rate` rounded to three decimals (29.97002997 becomes 29.97). For a still (`rate` 0), `fps` rounded the same way.               |
| `sourceDuration`              | Video and audio: `max(1, round(record.duration × rate))`. Still: `3 × fps`, rounded to a whole frame.                           |
| `sourceStart`                 | `0`.                                                                                                                            |
| `sourceEnd`                   | `min(sourceDuration, round(durationInFrames × r / fps))`, with `r` the unrounded `rate` (for a still, `fps`).                   |
| `trimStart`, `trimEnd`        | `0`.                                                                                                                            |
| `sourceWidth`, `sourceHeight` | The record's `width` and `height` (video and still only; absent when 0).                                                        |
| `transform`                   | Video and still only: `{ x: 0, y: 0, width, height, rotation: 0 }`, the source fitted inside the canvas (12.6.3), each rounded. |

**Consequences**

- **Linked:** creates the linked pair above. Existing clips are not touched.
- **Locks:** not checked, for the video track or the audio track (12.2.2). Fixtures `clip.add/locked-video-track-is-not-checked`, `clip.add/locked-audio-track-is-not-checked`.
- **Sync lock:** none.
- **Overlap:** an item that would share a frame with a clip on its track is refused (`failed`). This holds for the audio clip too, so a free place on the video track can still be refused (`clip.add/rejects-taken-place-for-linked-sound`).
- **Transitions:** none.

**Draws:** the new audio track's id (only when one is created), `originId`, `linkedGroupId` (only for a video with sound), the video or still id, the audio id.

**Implementation-defined.** `clip.add` does not check that a video's rate has an exact reading (section 3.4). It places the clip, and every later command that converts source time on it (`clip.slip`, `clip.setSpeed`) is refused (fixtures `clip.add/inexact-source-rate-is-not-checked`, `clip.slip/rejects-inexact-source-rate`). **Native rule:** do not place such media.

#### 12.3.2 `clip.delete`

Removes clips, optionally closing the space they leave. Payload: `clipId` or `clipIds`, optional `ripple`.

**Refusals, in order**

1. Neither field names a clip: `clipIds` is absent and `clipId` is absent, or `clipIds` is empty, or a named id is not a string: `invalid`. When `clipIds` is an array, `clipId` is ignored.
2. A named clip does not exist: `invalid`.

**Effect.** The clips removed are the **linked set** of the named clips (12.2.1): the clips, their linked groups, and the attached captions of all of them. Call them `D`. Their transitions and keyframes are removed with them.

With `ripple: true`, further:

1. The **edited tracks** are the tracks of the clips of `D`. Each surviving clip `x` has a **base shift**: the summed length of the clips of `D` on `x`'s track that end at or before `x.from`.
2. For each surviving clip with a base shift above 0, every member `y` of its linked set moves left by that amount (the greatest, if several apply), **unless** `y` is on a track that is not edited and is sync-enabled. Those are moved by step 4 instead.
3. **Covered clips.** A surviving clip that does not move, and that a moved clip on its track would now share a frame with, is removed too, with its linked set. Covered clips add nothing to the edited tracks or to step 4's intervals.
4. Every sync-enabled track that is not an edited track has the intervals of the clips of `D` removed (12.2.3).

**Consequences**

- **Linked:** linked clips and attached captions are deleted with the clip. With ripple, linked clips of shifted clips move with them.
- **Locks:** not checked. A ripple removes and moves clips on locked edited tracks too (`clip.delete/locked-track-is-not-checked`, `clip.delete/ripple-locked-track-is-not-checked`). A locked track that is not edited is never rippled by sync lock, but a linked clip on it still moves by step 2 (`clip.delete/ripple-moves-linked-clips-on-locked-track`).
- **Sync lock:** with ripple, step 4. Without ripple, none.
- **Overlap:** without ripple, none can arise. With ripple, step 3 removes what would be overlapped. That is **implementation-defined**: it deletes a clip the person did not name (`clip.delete/ripple-unsynced-companion-covers`). **Native rule:** reproduce it.
- **Transitions:** transitions of removed clips are removed. With ripple, the changed clips are the moved clips and the clips step 4 cut or moved. The clips that now meet are **not** joined by the removed clip's transition (`clip.delete/ripple-removes-transition`).

**Draws:** none without ripple. With ripple, the ids of step 4's splits, track by track.

In and out points are clamped (12.2.7).

#### 12.3.3 `clip.move`

Moves a clip to a new start, and optionally to another track. Payload: `clipId`, `start`, optional `trackId`, optional `linkedSelectionEnabled`.

**Refusals, in order**

1. `start` is not a valid non-negative time: `invalid`.
2. `trackId` is given and is not a string, or `linkedSelectionEnabled` is given and is not a boolean: `invalid`.
3. `trackId` names no track: `invalid`. It names a locked track: `failed`. An empty `trackId` is treated as absent.
4. The named clip is on a locked track: `failed`.
5. A clip that would move would start before frame 0: `failed`.

**Effect.** The moving clips are the linked set of the named clip, computed with linked selection **on** unless `linkedSelectionEnabled` is `false`, **minus** every clip on a locked track. Each moves by `start − clip.from` frames. Only the named clip takes the new `trackId`.

**Consequences**

- **Linked:** linked clips and attached captions move by the same amount and keep their tracks. With `linkedSelectionEnabled: false` only the clip and its attached captions move.
- **Locks:** refusals 3 and 4. A linked clip or caption on a locked track is silently left behind (`clip.move/locked-companion-stays`).
- **Sync lock:** none.
- **Overlap:** **not checked. Implementation-defined.** The engine accepts a move onto a place that is taken and returns a graph that is not in normal form (`clip.move/overlap-is-not-checked`, marked `outsideNormalForm`). **Native rule:** a native client must refuse a move that would make any moving clip share a frame with a clip that does not move, on the track it ends on.
- **Transitions:** the moving clips are changed (12.2.6).

The engine does not check that the destination track's `kind` suits the clip (`clip.move/video-to-audio-track-is-not-checked`). **Native rule:** move visual clips to video tracks and audio clips to audio tracks only.

**Draws:** none.

#### 12.3.4 `clip.split`

Cuts clips at a time. Payload: `at`, optional `clipIds`.

**Refusals, in order**

1. `at` is not a valid non-negative time: `invalid`.
2. `clipIds` is given and is empty, is not an array, or holds a non-string: `invalid`. A named clip does not exist: `invalid`.
3. With `clipIds`: a clip to split, or a member of its linked group, does not span `at`, or would be split inside a transition (12.2.5): `invalid`.
4. Without `clipIds`: nothing was split: `invalid`.

**Effect.**

- **With `clipIds`:** the named clips are reduced to one per linked group (the first named). Each of these, with its whole linked group, is split together (12.2.5).
- **Without `clipIds`:** every clip that spans `at` is a candidate, in `timeline.items` order, reduced to one per linked group. Each is split together with its linked group, **if** every member of the group spans `at` and none is inside a transition there. A group that fails this is skipped without error (`clip.split/skips-clips-in-a-transition`).

**Consequences**

- **Linked:** a linked group is split together or not at all. Its halves form two new linked groups. A clip that is alone in its linked group loses the group (`clip.split/unlinked-clip-loses-own-group`). Attached captions are not split and stay attached to the left half, which keeps the id.
- **Locks:** not checked (`clip.split/locked-track-is-not-checked`).
- **Sync lock:** none.
- **Overlap:** none can arise.
- **Transitions:** remapped as 12.2.5 says. No repair runs.

**Draws:** for each group split, in order: the right halves' ids, then the two new `linkedGroupId`s when two or more of the clips had one.

The engine also reads a `linkedSelectionEnabled` field on this command. The catalogue does not list it and the server refuses it, so a native client never sends it. Splitting always uses linked groups.

### 12.4 Trimming and retiming

#### 12.4.1 `clip.trimStart` and `clip.trimEnd`

Move one edge of a clip. Payload: `clipId`, `start` (for `clip.trimStart`) or `end` (for `clip.trimEnd`), optional `ripple`.

**Refusals, in order**

1. The time is not valid or is negative: `invalid`.
2. `clip.trimStart`: `start ≥ end(c)`. `clip.trimEnd`: `end ≤ c.from`: `invalid`.
3. A limit below does not hold: `failed`.

A `start` equal to `c.from`, or an `end` equal to `end(c)`, is applied and changes nothing. That check comes before refusal 2.

**Effect without `ripple`.** Let `a = start − c.from` (trim the start by `a`) or `a = end − end(c)` (trim the end by `a`). The clip **and its synchronised clips** are each trimmed by `a` (12.2.4). Limits, for each of them:

- the source and length limits of 12.2.4;
- the edge may not pass the nearest edge of another clip on its track: an end may extend up to the next clip's `from`, a start back to the previous clip's `end`. Clips joined to it by a transition are ignored for this limit.

When the trim shortened the clips, each **attached caption** is cut to the part that still lies inside its clip, or removed when nothing does (`clip.trimStart/attached-captions-are-cut`, `clip.trimEnd/attached-captions-are-cut`).

**Effect with `ripple: true`.** The clip and its synchronised clips are the **trimmed clips**; their tracks are the edited tracks.

- `clip.trimEnd`: each trimmed clip's end is trimmed by `a`. The **shift** is `a`.
- `clip.trimStart`: each trimmed clip's start is trimmed by `a` and the clip is then moved back to its old `from`. So `from` is unchanged, the length changes by `−a` and `sourceStart` advances. The shift is `−a`.
- On each trimmed clip's track, every other clip with `from ≥` the trimmed clip's **old end**, and the incoming clip of any transition out of it, moves by the shift.
- Every sync-enabled track that is not edited follows (12.2.3). For a negative shift the interval `[old end + shift, old end)` is removed. For a positive shift a gap of `shift` frames is opened at the old end.

Limits with ripple: the source and length limits of 12.2.4 (the neighbour limit does not apply), and every transition that touches a trimmed clip or a clip that shifts must be valid (12.2.6). Attached captions are **not** cut by a ripple trim.

**Consequences**

- **Linked:** synchronised linked clips are trimmed with the clip. A linked clip that is not synchronised is not trimmed (`clip.trimEnd/unsynchronised-companion-stays`). With ripple, the linked clips of the clips that shift are **not** moved by the command. Only sync lock moves them (`clip.trimEnd/ripple-leaves-linked-clips-without-sync-lock`). That differs from `clip.delete` with ripple and is **implementation-defined**. **Native rule:** reproduce it.
- **Locks:** not checked, for the clip, its synchronised clips or the clips a ripple shifts (`clip.trimStart/locked-track-is-not-checked`, `clip.trimEnd/locked-companion-is-not-checked`).
- **Sync lock:** with ripple, as above. Without ripple, none.
- **Overlap:** none can arise, except that the outgoing clip of a transition may be extended over its incoming clip. Section 5 allows that overlap (`clip.trimEnd/into-transition-partner`).
- **Transitions:** without ripple the trimmed clips are changed, so a clip trimmed off its cut loses the transition (`clip.trimStart/removes-transition`, `clip.trimEnd/removes-transition`). With ripple the changed clips are the trimmed clips, every clip on their tracks that starts at or after a trimmed clip's `from`, and the clips sync lock cut or moved. A ripple keeps the clips at the cut, so the transition stays (`clip.trimEnd/ripple-keeps-transition`).

**Draws:** none without ripple. With ripple, the ids of the sync-lock splits.

In and out points are clamped (12.2.7).

#### 12.4.2 `clip.roll`

Moves the cut between a clip and the clip that follows it. Payload: `clipId` (the clip before the cut), `at` (the new time of the cut).

**Refusals, in order**

1. No clip on the same track has `from = end(c)`: `invalid`. The first such clip in `timeline.items` order is the **next clip**.
2. `at` is not a valid non-negative time: `invalid`.
3. `at ≤ c.from` or `at ≥ end(next)`: `invalid`.
4. A clip of the linked sets of the two clips is on a locked track: `failed`.
5. A limit below does not hold: `failed`.

`at = end(c)` is applied and changes nothing. That check comes before refusal 3.

**Effect.** With `d = at − end(c)`: `c`'s end is trimmed by `d` and the next clip's start is trimmed by `d` (12.2.4). If `c` has a synchronised linked clip and the next clip has one on the same track and of the same type, that pair is rolled by the same `d`. Limits: the source and length limits of 12.2.4 for each clip, and every transition that touches a rolled clip must be valid (12.2.6).

**Consequences**

- **Linked:** one synchronised counterpart pair follows, as above.
- **Locks:** refusal 4.
- **Sync lock:** none. The timeline's length does not change.
- **Overlap:** none can arise.
- **Transitions:** the rolled clips are changed. A transition at the cut stays when its handles allow (`clip.roll/keeps-transition`); a roll that would starve it is refused (`clip.roll/rejects-starved-transition`).

**Draws:** none.

#### 12.4.3 `clip.slip`

Moves a clip's source window without moving the clip. Payload: `clipId`, `delta` (signed, **source time**).

**Refusals, in order**

1. The clip is not a video, audio or composition item: `invalid`.
2. The clip has no `sourceEnd`: `invalid`.
3. `delta` is not a rational, or the clip's `sourceFps` has no exact reading (section 3.4): `invalid`.
4. A clip of the clip's linked set is on a locked track: `failed`.
5. A limit below does not hold: `failed`.

`delta` becomes `d` source frames by section 3.3 at the clip's `sourceFps` (the project rate when absent). `d = 0` is applied and changes nothing; that check comes before refusal 4.

**Effect.** The clip and each synchronised clip that has a `sourceEnd` get `sourceStart += d` and `sourceEnd += d`. Limits, for each of them: `sourceStart + d ≥ 0`; `sourceEnd + d ≤ sourceDuration` when it has one; and every transition that touches it must be valid (12.2.6).

**Consequences**

- **Linked:** synchronised linked clips slip with the clip.
- **Locks:** refusal 4, over the whole linked set, synchronised or not.
- **Sync lock:** none.
- **Overlap:** none.
- **Transitions:** the slipped clips are changed. A slip that would leave a transition without handle is refused (`clip.slip/rejects-transition-handle`).

**Draws:** none.

#### 12.4.4 `clip.slide`

Moves a clip between its neighbours, which take up the difference. Payload: `clipId`, `delta` (signed, sequence time).

**Refusals, in order**

1. `delta` is not a rational: `invalid`.
2. The clip has neither neighbour: `invalid`. The **left neighbour** is the first clip in `timeline.items` order on its track with `end = c.from`; the **right neighbour** the first with `from = end(c)`.
3. A clip of the linked sets of the clip and its neighbours is on a locked track: `failed`.
4. A limit below does not hold: `failed`.

`delta` becomes `d` frames at the project rate. `d = 0` is applied and changes nothing; that check comes before refusal 2.

**Effect.**

- The left neighbour's end is trimmed by `d` and the right neighbour's start is trimmed by `d` (12.2.4). The clip moves by `d`.
- **Source continuity.** If both neighbours exist, the clip is a media clip with a `sourceEnd`, and both pairs (left, clip) and (clip, right) are joinable (12.5.5), the clip's source window also moves by `toSource(d)`. That amount is **clamped**, never refused: it is cut back so that `sourceStart` stays at or above 0 and `sourceEnd` at or below `sourceDuration`. The three then stay one continuous run of their source (`clip.slide/split-chain-keeps-continuity`). Otherwise the clip's source window is unchanged (`clip.slide/between-unrelated-clips`).
- If the clip has a synchronised linked clip (the first other one), that clip slides by the same `d` between **its own** neighbours on its track, found the same way, and its source window moves by the same amount as the clip's. With no neighbour of its own it simply moves.

Limits, for the clip and for that linked clip: `from + d ≥ 0`; the source and length limits of 12.2.4 for each neighbour trim; the clip may not pass any other clip on its track; every transition that touches the clip or a neighbour must be valid (12.2.6); and the keyframe limit of 13.2.7 must hold.

**Consequences**

- **Linked:** one synchronised linked clip slides with the clip, with its own neighbours.
- **Locks:** refusal 3.
- **Sync lock:** none. The timeline's length does not change.
- **Overlap:** none can arise.
- **Transitions:** the clip, its neighbours, and the linked clip and its neighbours are changed.

**Draws:** none.

#### 12.4.5 `clip.setSpeed`

Sets a clip's playback speed by changing its length. Payload: `clipId`, `speed` (a `rate`: the factor, where 2 is twice as fast).

**Refusals, in order**

1. The clip is not a video, audio or composition item: `invalid`.
2. `speed` is not a rational with `num > 0`: `invalid`.
3. `speed < 1/10` or `speed > 16`, compared exactly: `invalid`.
4. The clip has no `sourceEnd`, or `sourceEnd − sourceStart < 1`: `invalid`.
5. The clip's `sourceFps` has no exact reading: `invalid`.
6. The new length rounds to less than one frame: `invalid`.
7. A clip of the clip's linked set is on a locked track: `failed`.
8. The clip could not take the length; a member of the clip's linked set (an attached caption included) that had the same `from` and length before does not have the new length; or two clips on a track of the linked set now share a frame: `failed`.

**Effect.** Let `span = sourceEnd − sourceStart`.

- The new length `D` is exact: `span / sourceRate / speed × projectRate`, rounded to the nearest frame with halves up, where `sourceRate` is the exact reading of `sourceFps` (the project rate when absent).
- The stored `speed` is **derived from `D`**, in doubles, in this order: `(span × fps) / (D × sourceFps)`, then clamped to 0.1..16. It is not the payload's value: 7/3 on a 60-frame clip gives `D = 26` and `speed = 2.3076923076923075`. On a 30000/1001 project `fps` is `29.97002997002997` and a stored `sourceFps` is `29.97`, so 4/3 gives `1.3333346666680002` (`clip.setSpeed/ntsc`). A native client must reproduce these doubles exactly.
- The clip and each synchronised clip get `durationInFrames = D` and the derived `speed`, each derived with its own `sourceFps`. `from`, `sourceStart` and `sourceEnd` do not change. `speed: 1` is written even on a clip that never had a speed (`clip.setSpeed/one-on-unretimed-clip`). Keyframes are rescaled (13.2.7).
- **Ripple.** With `Δ = D − old length`, when `Δ ≠ 0`: on each track that holds a retimed clip, every other clip with `from ≥` the clip's old end moves by `Δ`, and its whole linked set moves with it, wherever those clips are. The incoming clip of a transition out of a retimed clip moves the same way.

**Consequences**

- **Linked:** synchronised linked clips are retimed together. Linked clips of the clips that move follow them (`clip.setSpeed/linked-clips-of-moved-clips-follow`). The clip's own attached captions are neither retimed nor moved (`clip.setSpeed/attached-captions-stay`), and one with exactly the clip's start and length refuses the command by refusal 8 (`clip.setSpeed/rejects-caption-of-the-same-extent`).
- **Locks:** refusal 7 covers the clip's linked set. The clips the ripple moves are **not** checked (`clip.setSpeed/ripple-moves-clips-on-locked-tracks`).
- **Sync lock:** none. Sync-locked tracks do **not** follow this ripple (`clip.setSpeed/sync-locked-tracks-do-not-ripple`).
- **Overlap:** refusal 8, on the tracks of the clip's linked set only.
- **Transitions:** the retimed clips and the clips that moved are changed.

**Draws:** none.

**Implementation-defined.** A speed above 10 is accepted, but loading clamps `speed` to 0.1..10 (2.6), so the result is not in normal form (`clip.setSpeed/above-ten`, marked `outsideNormalForm`). **Native rule:** a native client must refuse a speed above 10.

In and out points are clamped (12.2.7).

### 12.5 Timeline edits

#### 12.5.1 `clip.push`

Moves a clip and everything after it, on every track. Payload: `clipId`, `delta` (signed, sequence time).

**Refusals, in order**

1. `delta` is not a rational: `invalid`.
2. A moving clip is on a locked track: `failed`.
3. A moving clip would start before frame 0: `failed`.
4. A clip did not move as asked, or two clips on a track that holds a moving clip now share a frame: `failed`.

`delta` becomes `d` frames at the project rate. `d = 0` is applied and changes nothing; that check comes before refusal 2.

**Effect.** The moving clips are **every clip on every track** with `from ≥ c.from`. Each moves by `d`.

**Consequences**

- **Linked:** none. A linked clip moves only if it starts at or after the named clip.
- **Locks:** refusal 2.
- **Sync lock:** none. Tracks move whatever their `syncLock` (`clip.push/all-tracks`).
- **Overlap:** refusal 4. A pull may use free space but may not run into a clip that does not move.
- **Transitions:** the moving clips are changed (`clip.push/breaks-transition`).

**Draws:** none. In and out points are clamped (12.2.7).

#### 12.5.2 `clip.reorder`

Gives a clip a new position among the clips of its track and re-flows the track. Payload: `trackId`, `clipId`, `index`.

**Refusals, in order**

1. The clip is not on the track: `invalid`.
2. The track is locked: `failed`.
3. `index` is not an integer: `invalid`. It is below 0 or not below the number of clips on the track: `invalid`.
4. A linked clip that would move is on another, locked track: `failed`.
5. A clip that would move would start before frame 0: `failed`.
6. A clip did not move as asked, or two clips on a track that holds a moved clip now share a frame: `failed`.

**Effect.** Order the track's clips by `from`, take the named clip out and put it back at `index`. The track then **re-flows**: its clips are laid end to end in the new order, starting at the `from` of the clip that was first before the command. Gaps between the track's clips close, even when the order did not change (`clip.reorder/closes-gaps`). Then, for each clip of the track that the re-flow moves, in the new order, every member of its linked set that has not been given a position yet gets one: its own re-flow shift if it is a clip of the track that the re-flow moves, otherwise the shift of the clip that brought it. So a linked clip on another track follows the first of its linked clips in the new order.

**Consequences**

- **Linked:** linked clips and attached captions follow by the same amount (`clip.reorder/linked-follow`).
- **Locks:** refusals 2 and 4.
- **Sync lock:** none.
- **Overlap:** refusal 6 (`clip.reorder/rejects-companion-overlap`).
- **Transitions:** the moved clips are changed. Because of rule 3 of 12.2.6 a transition survives when its clips swap places (`clip.reorder/transition-survives-out-of-order`) and is removed when its incoming clip lands after its outgoing clip's end (`clip.reorder/removes-transition`).

**Draws:** none.

#### 12.5.3 `clip.insert`

Places a marked range of library media at a time and pushes everything from there on to make room. Payload: `assetId`, `trackId`, `at`, `sourceIn`, `sourceOut`.

**Refusals, in order** (shared with `clip.overwrite`)

1. `assetId` has no media record, or its `mimeType` is neither `image/*` nor `video/*`: `invalid`.
2. `trackId` names no track, or an audio track: `invalid`.
3. The track is locked: `failed`.
4. `at` is not a valid non-negative time: `invalid`.
5. `sourceIn` or `sourceOut` is not a rational, or `sourceIn` is negative: `invalid`.
6. `sourceOut − sourceIn`, computed exactly, is not positive, or is less than one project frame after rounding: `invalid`.
7. For a video: its rate has no exact reading; or `sourceOut` in source frames is past `max(1, round(record.duration × rate))`; or the range is less than one source frame: `invalid`.
8. For a video with sound: every audio track is locked: `failed`.

and for `clip.insert` only:

9. A clip that spans `at` on a destination track has a linked group whose members do not have the same `from` and `durationInFrames`, or a linked member that would be cut or moved is locked: `failed`. Validate every affected original group before cutting or moving any member.
10. Later clips could not make room, any two clips anywhere on the timeline now share a frame, or a placed clip did not land at `at`: `failed`.

**The placed clips** (shared with `clip.overwrite`). The fields are those of `clip.add` (12.3.1), except:

- `durationInFrames` is `sourceOut − sourceIn` in project frames (section 3.3).
- For a video and its sound, `sourceStart` and `sourceEnd` are `sourceIn` and `sourceOut` in source frames (section 3.3 at the source's exact rate). For a still the range gives only the length.
- The linked sound goes on the first audio track, in stored order, that is **not locked**. When the graph has no audio track, one is created as in `clip.add`.

**Effect.** The **destination tracks** are the tracks of the placed clips.

1. Every clip on a destination track that spans `at` is split there, together with its linked group (12.2.5), one group per clip in `timeline.items` order.
2. Every clip on a destination track with `from ≥ at` moves right by the placed length. So does each member of their linked sets that starts at or after `at` and is on a track that is not a destination, not sync-enabled and not locked.
3. Every sync-enabled track that is not a destination opens the same gap at `at` (12.2.3).
4. The placed clips are appended to `timeline.items`.

**Consequences**

- **Linked:** an aligned linked group is cut together (refusal 9). Linked clips follow their clip: by sync lock on a sync-enabled track, by step 2 on a track without sync lock (`clip.insert/companion-follows-without-sync-lock`). A locked affected companion refuses the complete edit before any cut or move.
- **Locks:** refusals 3, 8 and 9. A locked track elsewhere is not rippled and does not refuse the edit (`clip.insert/locked-track-elsewhere-is-not-rippled`). A locked affected companion refuses, including the historical `clip.insert/cuts-linked-clip-on-locked-track` refusal fixture.
- **Sync lock:** step 3 (`clip.insert/sync-locked-track-opens-gap`, `clip.insert/sync-lock-off`).
- **Overlap:** refusal 10.
- **Transitions:** the clips step 2 moved and the clips sync lock cut or moved in step 3 are changed, then the placed clips. The left halves of step 1's cuts are not changed. A transition at a cut that the insert opens is removed (`clip.insert/breaks-transition`).

**Draws:** the new audio track's id (when created), `originId`, `linkedGroupId` (video with sound), the video or still id, the audio id, then step 1's draws, then step 3's.

#### 12.5.4 `clip.overwrite`

Places a marked range of library media at a time, replacing whatever it covers. Payload and refusals 1 to 8: as `clip.insert`. Further:

9. A covered clip could not be cut, or two clips on a destination track still share a frame: `failed`.

**Effect.** The placed clips cover `[at, at + length)` on the destination tracks. Before mutation, examine every original linked group with a destination member that shares a frame with this interval, including a member wholly covered by it. Every linked member must be on an unlocked destination track and have the same `from` and `durationInFrames`. Otherwise refuse as `failed`; no track, clip, transition or history state is published. Unrelated locked tracks do not refuse. A clip touching only a boundary is unaffected.

1. Split groups crossing the start boundary, per original group in `timeline.items` anchor order. Apply the split bookkeeping of 12.2.5 separately to each group.
2. Split groups crossing the end boundary in the resulting `timeline.items` anchor order, again with bookkeeping per group.
3. Remove all destination parts wholly inside the interval with linked selection **off**, then append the placed clips. Repair transitions after removal and placement.

Each surviving temporal segment has an independent linked group: head, replacement and tail are separate aligned audio/video pairs. Incoming transitions stay with the left split segment; outgoing transitions remap to the right segment. Do not combine unrelated original groups into one bookkeeping call. The historical `clip.overwrite/transition-stays-with-the-id` fixture now records outgoing remapping.

**Consequences**

- **Linked:** partial linked edits refuse before mutation, including fully covered members whose companions are on an unwritten destination (`clip.overwrite/leaves-linked-clips-on-other-tracks` is now a refusal fixture). Attached captions follow the clip's **id**: when the part that keeps the id is removed, every caption attached to the clip is removed, even one that lies over a surviving part (`clip.overwrite/attached-captions`).
- **Locks:** refusals 3 and 8.
- **Sync lock:** none. Nothing ripples.
- **Overlap:** refusal 9. The command exists to replace what overlaps.
- **Transitions:** transitions of removed parts are removed. Every clip on a destination track is changed, then the placed clips.

**Draws:** the placed clips' draws as in `clip.insert`; then all start-boundary groups followed by all end-boundary groups, in the anchor order above. Within each group draw one right-half id per member, followed by the left/right linked-group ids of 12.2.5. Covered parts and their group ids may consume draws that do not survive removal. No draws from refused batches are published.

**Implementation-defined.** Removing the covered part of the timeline's last clip shortens the timeline before the new clip lengthens it again, and in and out points are clamped in between (12.2.7). They can end up clamped to an extent the timeline no longer has (`clip.overwrite/clamps-in-out-points-mid-edit`). **Native rule:** clamp the points to the extent after step 3 and before the placed clips are appended, then again to the final extent.

#### 12.5.5 `clip.join`

Joins contiguous parts of one source back into one clip. Payload: `clipIds`.

Two clips are **joinable**, left then right, when all of these hold: they have the same `originId`; the same track; the same `mediaId` (or, for compositions, `compositionId`), which is present; `|end(left) − right.from| ≤ 1`; the same speed; and the source continues: `|leftSourceEnd − right.sourceStart| ≤ 0.5`, where `leftSourceEnd` is `left.sourceEnd`, or `left.sourceStart + left.durationInFrames × speed` when it has none, and an absent `sourceStart` is 0.

**Refusals, in order**

1. `clipIds` is not an array of strings, or names fewer than two different clips: `invalid`.
2. A named clip does not exist: `invalid`.
3. The clips, ordered by `from`, are not joinable pair by pair: `invalid`.
4. A clip of the linked set of the named clips is on a locked track: `failed`.
5. The parts did not join, or a member of the joined clip's linked group does not have its length: `failed`.

**Effect.** The first clip (by `from`) absorbs the others one at a time. It keeps its id, its place in `timeline.items` and all its fields, with `durationInFrames = end(last) − first.from`, and `sourceEnd` and `trimEnd` taken from the last part. The other parts are removed, with their keyframes. At each step, if the two clips have synchronised linked clips on one track and of one type, that pair is joined the same way.

**Consequences**

- **Linked:** linked parts are joined with their clips, or the join is refused (`clip.join/rejects-unsynchronised-linked-clips`).
- **Locks:** refusal 4.
- **Sync lock:** none.
- **Overlap:** none can arise.
- **Transitions:** a transition that named a removed part now names the joined clip. A transition between two joined parts is removed (`clip.join/removes-transition`). The joined clips are changed.

**Draws:** none.

**Implementation-defined.** A still carries the source fields `clip.add` gave it, and a split copies them to both halves, so the halves of a split still never pass the source-continuity test and cannot be joined (`clip.join/rejects-still-parts`). **Native rule:** do not offer join for stills.

### 12.6 Links and clip properties

#### 12.6.1 `clip.setLink`

Links or unlinks clips. Payload: `clipIds`, `linked`.

**Refusals, in order**

1. `clipIds` is empty, is not an array, or holds a non-string: `invalid`.
2. `linked` is not a boolean: `invalid`.
3. A named clip does not exist: `invalid`.
4. `linked: true` with fewer than two different clips: `invalid`.
5. `linked: true` and the named clips' linked groups together are exactly one existing linked group: `failed`.

**Effect.**

- **Link:** every member of the named clips' linked groups gets one newly drawn `linkedGroupId`. A video among them loses `embeddedAudioMuted`.
- **Unlink:** every member of the named clips' linked groups that has a `linkedGroupId` gets **its own id** as its `linkedGroupId`, so it is alone in its group. A video whose group held an audio clip gets `embeddedAudioMuted: true`. Naming one clip of a group unlinks the whole group. Clips with no `linkedGroupId` are unchanged, and a legacy link (12.2.1) cannot be removed by this command.

**Consequences**

- **Linked:** this command is what defines linked groups.
- **Locks:** not checked (`clip.setLink/locked-track-is-not-checked`).
- **Sync lock, Overlap, Transitions:** none.

**Draws:** one id for a link. None for an unlink.

**Implementation-defined.** The engine links any clips, not only a video and its own sound (`clip.setLink/link-unrelated-clips`), and merges whole groups (`clip.setLink/link-merges-groups`). **Native rule:** link only a video clip with an audio clip of the same `mediaId`, `from`, length and source window.

#### 12.6.2 `clip.update`

Changes a clip's name, title properties, gain or transform. Payload: `clipId`, `patch`.

| `patch` field | Applies to      | Writes                                                                                                                                                                              |
| ------------- | --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`        | any clip        | `label`.                                                                                                                                                                            |
| `text`        | titles (`text`) | `text`. The `label` is unchanged.                                                                                                                                                   |
| `position`    | titles          | Two letters. The first is `t`, `m` or `b` and writes `verticalAlign` `top`, `middle` or `bottom`. The second is `l`, `c` or `r` and writes `textAlign` `left`, `center` or `right`. |
| `style`       | titles          | The fields of the named title style (14.3.2).                                                                                                                                       |
| `animation`   | titles          | `textMotion`, from the named title animation (14.3.3).                                                                                                                              |
| `volume`      | video, audio    | `volume`, the clip's gain in dB, as given.                                                                                                                                          |
| `transform`   | any clip        | As `clip.setTransform` (12.6.3), applied after the other fields.                                                                                                                    |
| `muted`       | video, audio    | Boolean clip `muted`, independent of track/parent mute and separated-video `embeddedAudioMuted` ownership. False resets only this clip control.                                     |

**Refusals, in order**

1. `patch` is not an object: `invalid`.
2. `patch` has a field the table does not list: `invalid`.
3. `name` is not a string: `invalid`.
4. `text`, `style`, `position` or `animation` on a clip that is not a title: `invalid`.
5. `text` is not a string; `style` names no title style; `position` is not one of the nine positions; `animation` names no title animation: `invalid`.
6. `volume` on a clip that is not video or audio, or `volume` is not a finite number: `invalid`.
7. `muted` on a clip that is not video or audio, or `muted` is not a boolean: `invalid`. A track locked against a mute edit: `failed`.
8. `transform` is not an object, or fails a `clip.setTransform` check: `invalid`.

An empty `patch` is applied and changes nothing.

**Consequences**

- **Linked:** none. Only the named clip changes; its linked clips are not renamed or re-gained (`clip.update/name`).
- **Locks:** not checked (`clip.update/locked-track-is-not-checked`).
- **Sync lock, Overlap, Transitions:** none.

**Draws:** none.

Fixtures `clip.update/style-bold`, `…/style-minimal`, `…/style-lower-third` and `…/animation` record what three styles and one animation write. Sections 14.3.2 and 14.3.3 specify the whole vocabulary.

**Implementation-defined.** `volume` is stored as given, but loading clamps it to −60..12 (2.6), so a value outside that range gives a graph that is not in normal form (`clip.update/volume-is-not-clamped`, marked `outsideNormalForm`). **Native rule:** refuse a `volume` outside −60..12.

#### 12.6.3 `clip.setTransform`

Sets a clip's position, scale, rotation and opacity. Payload: `clipId`, `transform` with any of `x`, `y`, `scale`, `rotation`, `opacity`.

**Refusals, in order**

1. `transform` is not an object: `invalid`.
2. It has a field other than those five: `invalid`.
3. `x`, `y`, `rotation` or `opacity` is not a finite number: `invalid`.
4. `opacity` is below 0 or above 1: `invalid`.
5. `scale` is not a finite number above 0: `invalid`.
6. It changes nothing (it is empty): `invalid`.

**Effect.** A clip with no `transform` object first gets an empty one. Then `x`, `y`, `rotation` and `opacity` are written as given, and `scale` writes `width` and `height`:

```text
fit    = min(canvasWidth / sourceWidth, canvasHeight / sourceHeight)
width  = (sourceWidth × fit) × scale
height = (sourceHeight × fit) × scale
```

computed in doubles in that order, without rounding. The source size is the clip's `sourceWidth` and `sourceHeight` for a video or still (the media record's size when the clip has none), `compositionWidth` and `compositionHeight` for a composition, and the canvas size for anything else. Other transform fields are kept.

**Consequences**

- **Linked:** none. Only the named clip changes.
- **Locks:** not checked (`clip.setTransform/locked-track-is-not-checked`).
- **Sync lock, Overlap, Transitions:** none.

**Draws:** none.

**Implementation-defined.**

- `rotation` is stored as given, but loading reduces it to 0..360 (2.6), so a value outside that range gives a graph that is not in normal form (`clip.setTransform/rotation-is-not-reduced`, marked `outsideNormalForm`). **Native rule:** reduce `rotation` to 0..360 before sending.
- An audio clip accepts a transform, which nothing reads (`clip.setTransform/audio-clip-is-not-checked`). **Native rule:** do not send one for an audio clip.

Keyframes on transform properties are specified in 13.2.5. They do not change the stored `transform`.

#### 12.6.4 `clip.setTransformParent`

Attaches a clip to a parent clip so that it follows the parent's transform, or detaches it. Payload: `clipId`, optional `parentId` (a clip id, or `null` or absent to detach).

**Refusals, in order**

1. `parentId` is present and is neither a string nor `null`: `invalid`.
2. `parentId` names no clip: `invalid`.
3. Any of these: `failed`.
   - The child, or the parent, is an audio or adjustment item.
   - The parent is the child.
   - The parent depends on the child: following transform parents and property links (`propertyLinks`, 13.2.4) from the parent leads back to the child.
   - The child already links its position, scale or rotation (`propertyLinks`, 13.2.4) to the parent or to one of the parent's own parents.
   - **The request changes nothing:** the child's `transformParent.parentItemId` is already `parentId`, or a detach is asked for a child whose `transformParent` has no `parentItemId` or that has no `transformParent`.

**Effect.** The child's `transformParent` becomes:

```text
{ parentItemId, parentReference, childLocalReference, childWorldReference }
```

Each reference is `{ x, y, width, height, rotation }`: a pose at the child's first frame (`child.from`).

- `childLocalReference` is the child's own transform: its stored `transform`, with `x`, `y` and `rotation` 0 and the fitted size of 12.6.3 where a field is absent.
- `childWorldReference` is the child's pose on the canvas at that frame. For a child with no `transformParent` it equals `childLocalReference`.
- `parentReference` is the parent's pose on the canvas at that frame, found the same way.
- A detach writes the same object without `parentItemId` and `parentReference`. The `transformParent` object stays; it now only pins the child's pose.

**Consequences**

- **Linked:** none.
- **Locks:** not checked (`clip.setTransformParent/locked-track-is-not-checked`).
- **Sync lock, Overlap, Transitions:** none.

**Draws:** none.

**Implementation-defined.**

- A request that changes nothing is refused as `failed`, unlike every other command in this part (`clip.setTransformParent/same-parent`, `…/detach-unparented`). **Native rule:** do not send one.
- For a child or parent that is keyframed, driven by an expression or a modifier, or already has a `transformParent`, the poses are the resolved, composed transforms at that frame. Their computation uses floating-point matrix arithmetic with rotations. It is engine arithmetic (13.1), and fixtures `clip.setTransformParent/detach`, `…/reparent` and `…/animated-parent` are marked so. **Native rule:** attach only clips that have none of those, and do not detach, unless the implementation reproduces the marked fixtures bit for bit.

### 12.7 Tracks

#### 12.7.1 `track.add`

Adds an empty track. Payload: `kind`, optional `index`, optional `name`.

**Refusals:** `kind` is not `video` or `audio`; `index` is not an integer, is below 0 or is above the number of tracks; `name` is not a string. All `invalid`.

**Effect.** The new track is created as 12.2.8 says. With the tracks sorted by `order`:

| `index`               | `order` of the new track                                                                  |
| --------------------- | ----------------------------------------------------------------------------------------- |
| absent, `kind: video` | `min(0, least order) − 1`: above every track.                                             |
| absent, `kind: audio` | `max(0, greatest order) + 1`: below every track.                                          |
| `0`                   | The first track's `order − 1`.                                                            |
| the number of tracks  | The last track's `order + 1`.                                                             |
| between               | The midpoint of the `order`s of the tracks at `index − 1` and `index`. May be a fraction. |

A non-empty `name` replaces the first name. Then the list is sorted and classic names are renumbered (12.2.8). Adding a video track below `V1` therefore renames `V1` to `V2` (`track.add/index-between`).

**Consequences:** Linked, Locks, Sync lock, Overlap and Transitions: none. No clip changes.

**Draws:** one id; the track's `id` is `track-` followed by it.

**Implementation-defined.** A `name` of the classic form is not kept: it is replaced by the position's name (`track.add/classic-name-is-renumbered`). **Native rule:** do not send a classic name.

#### 12.7.2 `track.remove`

Removes a track and its clips. Payload: `trackId`.

**Refusals, in order**

1. The track is locked: `failed`.
2. It is the only track: `invalid`.

**Effect.** The track's clips are removed with linked selection **off**, with their attached captions, transitions and keyframes. The track is removed and classic names are renumbered (12.2.8).

**Consequences**

- **Linked:** linked clips on other tracks stay and keep their `linkedGroupId` (`track.remove/with-clips`).
- **Locks:** refusal 1.
- **Sync lock:** none. Nothing ripples.
- **Overlap:** none.
- **Transitions:** transitions of the removed clips are removed.

**Draws:** none. In and out points are clamped (12.2.7).

#### 12.7.3 `track.reorder`

Moves a track to a new position. Payload: `trackId`, `index`.

**Refusals:** `index` is not an integer, is below 0, or is not below the number of tracks. All `invalid`.

**Effect.** Order the tracks by `order`, take the track out and put it back at `index`. The tracks then take, in their new order, the **same set of `order` values** the list had, in ascending order. Classic names are renumbered (12.2.8). A track already at `index` is applied and changes nothing.

**Consequences:** Linked, Sync lock, Overlap and Transitions: none. No clip changes. **Locks:** a locked track may be reordered (`track.reorder/locked-track`).

**Draws:** none.

#### 12.7.4 `track.set`

Changes a track's properties. Payload: `trackId`, `patch` with any of `name`, `muted`, `locked`, `solo`, `visible`, `syncLock`, `gain`.

**Refusals, in order**

1. `patch` is not an object: `invalid`.
2. It has a field other than those seven: `invalid`.
3. It is empty: `invalid`.
4. `name` is not a string, is blank, or is longer than 80 characters: `invalid`.
5. `muted`, `locked`, `solo`, `visible` or `syncLock` is not a boolean: `invalid`.
6. `gain` is not a finite number from −60 to 12: `invalid`.
7. A value was not applied: `failed`.

**Effect.** The flags are written as given. `gain` writes `volume` (dB). `name` writes `name`, and classic names are then renumbered (12.2.8).

**Consequences:** Linked, Sync lock, Overlap and Transitions: none. No clip changes. **Locks:** a locked track may be changed, and unlocked (`track.set/unlock`).

**Draws:** none.

**Implementation-defined.** Because classic names are derived from position, a `name` of the track's own classic form that is not the position's name is renumbered away and the command is refused by refusal 7 (`track.set/rejects-classic-name`). The position's own name is accepted (`track.set/classic-name-of-position`), and so is a name of the other kind's form (`track.set/other-kinds-classic-name`). **Native rule:** do not send a classic name.

#### 12.7.5 `track.closeGap`

Closes one gap on a track, or all of them. Payload: `trackId`, optional `at`.

A **gap** on a track is a run of free frames that ends where a clip starts: the space before the first clip, or between two clips. The space after the last clip is not a gap.

**Refusals, in order**

1. The track is locked: `failed`.
2. Without `at`: any clip or attached caption in the expanded linked set of the track's clips is on a locked track: `failed`.
3. With `at`: `at` is not a valid non-negative time, or no gap holds that frame: `invalid`. After identifying the later clips, any item in their expanded linked/caption set is on a locked track: `failed`.
4. An intended linked/caption position is negative: `failed`, before the engine can clamp it to zero.
5. With `at`: sync-lock propagation removes, splits or changes any affected linked item's data other than `from`: `failed`. The canonical adapter never reconstructs a source window.
6. A linked item cannot reach its exact intended position while retaining all other fields, or two items overlap on an affected track: `failed`. Exact touching is permitted.
7. A target-track clip did not move as asked: `failed`.

**Effect with `at`.** Let the gap be `[a, b)`. Capture the original items and expand every target-track clip with `from ≥ b` to its linked group and attached captions. Each affected item's intended `from` is its captured original `from − (b − a)`. Run the pinned action once: target clips move left, and every other sync-enabled track has `[a, b)` removed (12.2.3). If each captured linked item survives with all non-position fields unchanged, correct only surviving items not already at their intended absolute position, then repair their transitions. A companion already shifted by sync lock is never shifted twice. Unrelated sync-lock splitting/removal retains the pinned engine's behaviour.

**Effect without `at`.** The track's clips are packed from frame 0 in order of `from`: each clip moves left to the end of the one before it. Each clip that moves takes its linked set and attached captions with it, by the greatest shift of any member of its linked group. Check intended positions before movement and companion-track overlap after movement. Other tracks are not rippled.

**Consequences**

- **Linked:** clips and attached captions follow in both forms, including on tracks with `syncLock: false`.
- **Locks:** the expanded linked/caption set is checked in both forms; a lock cannot silently strand a companion.
- **Sync lock:** with `at`, unrelated clips on other sync-enabled tracks may be **cut or removed** (`track.closeGap/at-removes-interval-from-sync-locked-tracks`). A destructive change to a captured linked item refuses the entire batch. Without `at`, none.
- **Overlap:** refused on linked/caption tracks in both forms and on affected sync-lock tracks with `at`; exact touching is valid.
- **Transitions:** use the existing repair for moved, cut and corrected clips; source data is not reconstructed.

**Canonical adapter versus raw engine.** The pinned upstream single-gap action does not expand links, and its movement normalizer clamps negative starts. These are raw action behaviours, not permission for a native client to strand a linked companion or coerce its position. **Native rule:** reproduce the canonical adapter's linked shifts and atomic refusals above. A refusal publishes no graph and records no history; the original graph, item order and media authority remain intact.

**Fixture provenance and qualification.** The existing case ID `track.closeGap/at-leaves-linked-clips-without-sync-lock` is retained as a historical input label from the earlier adapter contract; its recorded answer is not current qualification after this correction. Existing recorded answers must be regenerated by the real canonical-adapter replay, never edited by hand. New FL-94 cases carry authored `admission` requirements and `expect: null` until hosted `GRAPH_CONFORMANCE_WRITE=1` produces their complete graphs, digests and refusals. Both ordinary engine replay and the independent reference/schema checks must pass after importing the genuine output. This section does not claim qualification of the refused destructive linked interval cases or the complete FL-94 interaction matrix.

**Draws:** with `at`, the ids of the sync-lock splits. Without `at`, none. In and out points are clamped (12.2.7).

### 12.8 Markers and music

Markers are `timeline.markers`, in the order they were added. The list is not sorted by frame, two markers may share a frame, and the key is absent when the list is empty. Marker commands change nothing else: Linked, Locks, Sync lock, Overlap and Transitions are all **none** for the three of them.

#### 12.8.1 `marker.add`

Payload: `at`, optional `colour`, optional `name`.

**Refusals, in order:** `at` is not a valid non-negative time; `colour` is not a string, or is not `#` and six hex digits (either case); `name` is not a string, or is longer than 120 characters. All `invalid`.

**Effect.** Appends `{ id, frame, color, label }`: `frame` is `at` in frames, `color` is `colour` as given or `#3B82F6`, and `label` is `name`. An empty or absent `name` stores no `label`. The frame is not limited to the timeline's extent.

**Draws:** the marker's id.

#### 12.8.2 `marker.update`

Payload: `markerId`, `patch` with any of `name`, `colour`, `at`.

**Refusals, in order:** `markerId` names no marker; `patch` is not an object; it has another field; `name` is not a string or is longer than 120 characters; `colour` is not `#` and six hex digits; `at` is not a valid non-negative time; the patch is empty. All `invalid`.

**Effect.** `name` replaces `label` (an empty name removes it), `colour` replaces `color` as given, and `at` replaces `frame`. The marker keeps its place in the list.

**Draws:** none.

#### 12.8.3 `marker.remove`

Payload: `markerId`. **Refusal:** it names no marker: `invalid`. **Effect:** the marker is removed; the others keep their order. **Draws:** none.

#### 12.8.4 `music.add`

`music.add` is an engine command that is **always refused** as `failed` at this revision, before it reads its payload: the bundled music catalogue is rights-blocked (FL-86), so no `musicId` resolves. It changes nothing, and so has no linked, lock, sync-lock, overlap or transition consequence. **Native rule:** do not offer bundled music and never record `music.add` in a save. Fixtures `music.add/rejects-always`, `music.add/rejects-before-reading-payload`.

This section gives the mutation rules of the 12 commands of FL-308 (NAPI-019), the clip and track audio commands of FL-103 (13.9 and 13.10), the graph fields they write, and the rule for the fields that no engine command writes at this revision (13.8).

| Commands                                                                                  | Section |
| ----------------------------------------------------------------------------------------- | ------- |
| `effect.add`, `effect.remove`                                                             | 13.3    |
| `clip.setTransition`                                                                      | 13.4    |
| `keyframe.add`, `keyframe.remove`, `keyframe.update`, `keyframe.setEasing`                | 13.5    |
| `property.setExpression`, `property.setModifier`, `property.bakeModifier`                 | 13.6    |
| `text.setMotion`, `clip.setKenBurns`                                                      | 13.7    |
| Fields with no command: `effect.update`, `effect.reorder`, `clip.setBlendMode` and others | 13.8    |
| `clip.setAudio`                                                                           | 13.9    |
| `track.setAudio`                                                                          | 13.10   |

Every command has fixtures named `<command>/<case>` in `studio/graph-conformance-v1.json`, both applied and rejected. Cases of part 2 commands on animated clips (13.2.7) are named after the part 2 command. Where this prose and a fixture differ, the fixture is right and this page has a defect.

### 13.1 How to read the rules

- Section 12.1 applies: the refusals common to every command, the order of refusals, and "applied and changes nothing".
- The five consequences of part 2 are the same for all twelve commands and are not repeated. **Linked:** none; only the named clip changes. **Locks:** not checked by any of the twelve. That is implementation-defined, and the native rule of 12.2.2 holds: a native client treats a lock as binding. Each command has a `…/locked-track-is-not-checked` fixture. **Sync lock** and **Overlap:** none; no clip moves. **Transitions:** only `clip.setTransition` writes them, and no repair runs. The keyframe commands read them (13.2.3).
- The server checks the top-level fields of a payload (7.1). It does not read inside a payload object (`transition`, `value`, `modifier`, `motion`, `kenBurns`, `bezier`, `spring`). A field inside such an object that these rules do not name is ignored or dropped, as each command says.
- "A number in a..b" includes both ends. "Finite number" rules out every value that is not a JSON number.
- **Engine arithmetic.** A few answers hold values that the engine computes with floating-point sines, cosines, arctangents, or keyframe interpolation. IEEE 754 fixes the result of `+`, `−`, `×`, `÷` and of rounding, so every other value on this page is reproducible bit for bit. It does not fix those functions, so this protocol does not specify these values. The fixtures mark such a case `"engineArithmetic": true` (section 10). **Native rule:** a native client must not offer an edit of this kind unless it reproduces every marked fixture bit for bit. Otherwise it refuses the edit and leaves it to the web editor. The edits are: `property.bakeModifier` when it writes keyframes (13.6.3), and `clip.setTransformParent` on a clip that is animated or already parented (13.2.7).

### 13.2 Shared rules

#### 13.2.1 The parameter catalogue

| `directEdits`       | The graph fields that no engine command writes, with the section that gives their rule (13.8).                                                                                                                        |
| `contentSha256`     | The SHA-256 of the canonical JSON (section 6) of the catalogue without this key.                                                                                                                                      |

Parameter types are `number` (with `min`, `max` and `step`), `boolean`, `select` (one of `options`), `color` (`#rrggbb` or `#rrggbbaa`), `text` and `json` (a string). A transition's `color` parameter is an array of three numbers (`valueFormat: "rgb-array"`).

The catalogue is a clean-room file. It carries ids, names, types, numbers and option values. It carries no display label, no description and no shader source: a native client names its own controls. What a parameter does to the picture is the renderer's contract, which section 18 gives.

**Drift.** `studio/adapters/web/test/graph-parameters.test.ts` rebuilds the catalogue from the registries of the prepared engine in the Studio engine workflow and fails on any difference. `GRAPH_PARAMETERS_WRITE=1 node studio/tools/adapter.mjs test` regenerates it. The engine-free check (section 10) re-derives `contentSha256`, so a hand edit fails where the engine is not built.

#### 13.2.2 Effect stacks

A clip's `effects` is its effect stack, drawn in array order. Each entry is:

```text
{ id, effect: { type: "gpu-effect", gpuEffectType, params }, enabled }
```

- `id` is unique on the clip. `gpuEffectType` is an effect `id` of the catalogue. `enabled: false` leaves the effect in the stack and out of the picture.
- `params` maps parameter names to numbers, booleans and strings. A parameter that is absent is drawn at its catalogue default.
- Audio clips have no stack. Every other clip type may have one.
- A clip that never had an effect has no `effects` field. A clip whose effects were all removed keeps an empty list.
- Fields of an entry that this page does not name (the web editor writes `audioPulse` on some) must be preserved.

#### 13.2.3 Transitions

`timeline.transitions` holds one entry for each cut that has a transition:

| Field                                     | Meaning                                                                                    |
| ----------------------------------------- | ------------------------------------------------------------------------------------------ |
| `id`                                      | Drawn when the transition is added.                                                        |
| `type`                                    | Always `"crossfade"`.                                                                      |
| `leftClipId`                              | The **outgoing** clip: the clip before the cut.                                            |
| `rightClipId`                             | The **incoming** clip: the clip after the cut.                                             |
| `trackId`                                 | The track of both clips.                                                                   |
| `durationInFrames`                        | Its length `d`, at least 1.                                                                |
| `presentation`                            | A transition `id` of the catalogue.                                                        |
| `timing`                                  | `linear`, `ease-in`, `ease-out`, `ease-in-out` or `cubic-bezier`. Commands write `linear`. |
| `alignment`                               | A number in 0..1: where the transition sits on the cut. Commands write `0.5`.              |
| `direction`                               | Optional. One of the presentation's `directions`.                                          |
| `bezierPoints`                            | Optional. `{ x1, y1, x2, y2 }` for `timing: "cubic-bezier"`.                               |
| `properties`                              | Optional. Values of the presentation's `parameters`, by name.                              |
| `presetId`, `createdAt`, `lastModifiedAt` | Optional. Written by editor features outside this protocol. Preserve them.                 |

A clip has at most one transition out of it and at most one into it. The clips must be video, still or composition items on one track.

**The two parts.** With `p = floor(d × alignment)`, a transition takes the last `p` frames of the outgoing clip and the first `d − p` frames of the incoming clip. Those frames are the clip's **transition regions**. While the outgoing clip plays its region, the incoming clip shows `p` frames from before its start: its **head handle**. While the incoming clip plays its region, the outgoing clip shows `d − p` frames from after its end: its **tail handle**. Section 12.2.6 defines the handles, the longest length `M` they allow, and when a transition is **valid**.

**Regions and keyframes.** No keyframe may be placed in, or moved into, a transition region of its clip (13.5). A transition may be added over keyframes that are already there. They stay (fixture `clip.setTransition/over-existing-keyframes`), can still be given a new value or easing, and can be removed. A clip cannot be split inside a region (12.2.5).

When a clip's two regions together are longer than the clip, the engine shrinks both in proportion. That cannot happen with an alignment of 0.5. It is **implementation-defined**. **Native rule:** a native client never changes `alignment` (13.8.5), so it never meets this case.

#### 13.2.4 Keyframes

`timeline.keyframes` holds one **entry** for each animated clip, in the order the clips were first animated:

```text
{ itemId, animationVersion: 2, properties, vectorProperties, separatedVectorProperties, propertyLinks, expressions }
```

| Field                       | Contents                                                                                                                       |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `itemId`                    | The clip.                                                                                                                      |
| `animationVersion`          | `2`.                                                                                                                           |
| `properties`                | Always present. One **group** `{ property, keyframes }` for each scalar property, in the order the properties were first used. |
| `vectorProperties`          | Present only when not empty. One group for each vector property.                                                               |
| `expressions`               | Present only when not empty. `{ type: "expression", targetProperty, source, enabled }` (13.6.1).                               |
| `propertyLinks`             | Present only when not empty. Links to a property of another clip. No command writes them. Preserve them.                       |
| `separatedVectorProperties` | Present only when not empty. Vector properties shown as two scalar ones. No command writes it. Preserve it.                    |

A scalar keyframe is `{ id, frame, value, easing }`, plus `easingConfig` for a bezier or a spring (13.2.6). When the engine writes a graph it keeps **only these five fields** of a scalar keyframe. A vector keyframe is `{ id, frame, value: { x, y }, easing }` plus, optionally, `easingConfig`, `temporalEase` and `spatial` (13.5.3). Its other fields are kept.

- `frame` counts from the clip's first frame: frame 0 is `from`. It is **not** a sequence frame. A payload `at` is a sequence time. It is converted as section 3.3 says and must satisfy `from ≤ at < from + durationInFrames`. Then `frame = at − from`.
- The keyframes of a group are in ascending `frame` order, one per frame.
- An entry or a group may be empty. An entry **holds animation** when a scalar or vector group has a keyframe, or when `expressions`, `propertyLinks` or `separatedVectorProperties` has an element. An empty group is not animation.
- **The sweep.** Three kinds of edit remove **every** entry in the list that holds no animation, whichever clip it belongs to: removing a vector keyframe (13.5.2), clearing an expression (13.6.1), and any command that removes a clip. No other edit removes an entry. So removing the last **scalar** keyframe of a clip leaves its entry behind, with an empty group, until one of those edits sweeps it. This is **implementation-defined**. Fixtures `keyframe.remove/scalar-last-keeps-entry`, `…/scalar-removal-does-not-sweep`, `…/vector-removal-sweeps-empty-entries`, `property.setExpression/clear-sweeps-empty-entries`, `clip.delete/sweeps-empty-keyframe-entries`. **Native rule:** reproduce it.
- `animationVersion: 2` is written on every entry a command creates, and on an existing entry by every command that adds a keyframe (`keyframe.add`, `clip.setKenBurns`, `property.bakeModifier`), by `property.setExpression` with an expression, and by `keyframe.update` and `keyframe.setEasing` on a vector property. Every graph this protocol's commands produce therefore has it on every entry.

#### 13.2.5 Animatable properties

`properties` in the catalogue lists the names. A keyframe on a scalar property holds a number:

| Properties                                                                                                                                | Applies to                                                                           |
| ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `x`, `y`, `width`, `height`, `anchorX`, `anchorY`, `rotation`, `opacity`, `cornerRadius`                                                  | The clip's `transform` field of the same name.                                       |
| `cropLeft`, `cropRight`, `cropTop`, `cropBottom`, `cropSoftness`                                                                          | The clip's crop.                                                                     |
| `volume`                                                                                                                                  | The clip's gain in dB.                                                               |
| `textStyleScale`, `fontSize`, `lineHeight`, `textPadding`, `backgroundRadius`, `textShadowOffsetX`, `textShadowOffsetY`, `textShadowBlur` | Titles.                                                                              |
| `strokeWidth`, `trimPathStart`, `trimPathEnd`, `trimPathOffset`, `taperStartWidth`, `taperEndWidth`, `taperStartLength`, `taperEndLength` | Shapes.                                                                              |
| `effect:<gpuEffectType>:<effect id>:<parameter>`                                                                                          | A parameter of one effect of the clip's stack that the catalogue marks `animatable`. |

A keyframe on a **vector** property holds `{ x, y }` and lives in `vectorProperties`:

| Property   | Value                                                                                          |
| ---------- | ---------------------------------------------------------------------------------------------- |
| `position` | `x` and `y` of the transform.                                                                  |
| `scale`    | Percent of the clip's own `width` and `height`: `{ x: 100, y: 100 }` leaves the size as it is. |
| `anchor`   | `anchorX` and `anchorY` of the transform.                                                      |

The engine does not check that a scalar property name is in the list, that the clip's type has the property, or that a value is within the property's range (fixtures `keyframe.add/property-is-not-checked`, `…/property-of-another-clip-type-is-not-checked`, `…/value-range-is-not-checked`). This is **implementation-defined**. **Native rule:** a native client writes only the names above, only on a clip type that has the property, with values in the property's range. It animates a pair either as its vector property or as its two scalar properties, never both. The graph editor of the web also writes `pathVertex:<n>:<component>` properties for pen paths. Preserve them.

#### 13.2.6 Easing

A keyframe's easing shapes the motion **from that keyframe to the next** one of its group.

| `easing`       | Parameters (`easingConfig`)                                                                                                      |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `linear`       | None.                                                                                                                            |
| `ease-in`      | None.                                                                                                                            |
| `ease-out`     | None.                                                                                                                            |
| `ease-in-out`  | None.                                                                                                                            |
| `hold`         | None. The value stays until the next keyframe.                                                                                   |
| `cubic-bezier` | `{ type: "cubic-bezier", bezier: { x1, y1, x2, y2 } }`. `x1` and `x2` are numbers in 0..1. `y1` and `y2` are any finite numbers. |
| `spring`       | `{ type: "spring", spring: { tension, friction, mass } }`: `tension` in 0..500, `friction` in 0..100, `mass` in 0.1..10.         |

The spring defaults are tension `170`, friction `26` and mass `1`. The catalogue's `easing.bezierDefault` (`0.42, 0, 0.58, 1`) is what the web editor offers first; no command writes it by itself.

`easingConfig` is present exactly when a command stored parameters, and its `type` equals the keyframe's `easing`. `keyframe.add` can store `cubic-bezier` or `spring` with no `easingConfig` (13.5.1). **Native rule:** set a bezier or a spring with `keyframe.setEasing`, which always stores the parameters.

A vector keyframe may also carry:

- `temporalEase: { in, out }`: velocity handles. Each is `{ speed, influence }`, with `influence` a percentage in 0.1..100. Either may be absent.
- `spatial: { inTangent, outTangent, continuous }` (position only): the path's tangents at the keyframe, each `{ x, y }`. `continuous: true` records that the tangents mirror each other.

#### 13.2.7 What part 2 commands do with effects and animation

Part 2 left these open. Effects, modifiers, text motion and blend mode are fields of the clip, so they follow the rule of 12.2.5: a split copies them to both halves, **with the same ids**. Keyframes are not fields of the clip:

| Command                                                    | Keyframes and expressions                                                                                                                                                                                                                                        |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `clip.split`                                               | The left half keeps the clip's id, so it keeps the **whole** entry, including keyframes past its new end. The right half has no entry (`clip.split/animation-stays-with-the-left-half`).                                                                         |
| `clip.trimStart`, `clip.trimEnd`, `clip.roll`, `clip.slip` | Unchanged. Frames still count from the clip's start, so trimming the start shifts the animation against the picture, and a keyframe past the new end stays in the graph (`clip.trimStart/keyframes-do-not-shift`, `clip.trimEnd/keyframes-beyond-the-end-stay`). |
| `clip.move`, `clip.push`, `clip.reorder`, `track.closeGap` | Unchanged: keyframes are relative to the clip.                                                                                                                                                                                                                   |
| `clip.setSpeed`                                            | Rescaled, for the clip and each synchronised clip (below).                                                                                                                                                                                                       |
| `clip.slide`                                               | Unchanged, but scalar keyframes limit the slide (below).                                                                                                                                                                                                         |
| `clip.join`                                                | The joined clip keeps the left clip's entry and fields. The right clip's entry, effects and modifiers go with it (`clip.join/right-clip-animation-is-dropped`).                                                                                                  |
| `clip.delete`, `track.remove`, and every removal           | The entries of removed clips are removed, and the sweep of 13.2.4 runs.                                                                                                                                                                                          |
| Ripple and overwrite cuts (12.2.3, 12.5.4)                 | The part that keeps the clip's id keeps the entry. A surviving tail under a **new id** has none: its animation is lost (`clip.delete/ripple-cut-tail-loses-animation`). Its effects and modifiers are copied. **Implementation-defined; reproduce.**             |

**Rescaling (`clip.setSpeed`).** With `old` and `new` the clip's lengths before and after, in doubles:

```text
frame' = min( new − 1, max( 0, round( frame × (new / old) ) ) )        round: nearest, halves towards positive infinity
```

Every scalar and vector keyframe of the entry is rescaled. When two keyframes of a group land on one frame, the one whose old frame was **later** stays and the other is removed. The group is then sorted by frame. Fixtures `clip.setSpeed/keyframes-are-rescaled`, `…/rescaled-keyframes-collide`, `…/keyframes-stretch`.

**The slide limit (`clip.slide`).** Take the slid clip, its two neighbours, and the synchronised linked clip with its own neighbours. For each, take its **scalar** keyframes that are inside the clip (`0 ≤ frame < durationInFrames`) and outside its transition regions before the slide. After the slide each of them must still be inside its clip and outside its transition regions, or the command is refused (`failed`). Vector keyframes are not looked at; that is **implementation-defined** (`clip.slide/vector-keyframes-are-not-checked`). **Native rule:** reproduce both. `clip.roll` and the trims make no such check (`clip.roll/keyframes-are-not-checked`).

**Transform parents (`clip.setTransformParent`, 12.6.4).** When the child or the parent has a keyframes entry or a modifier, or the child or the parent already has a `transformParent`, the poses are the clips' resolved poses at the child's first frame, composed through rotations. They are **engine arithmetic** (13.1). Fixtures `clip.setTransformParent/animated-parent`, `…/detach` and `…/reparent` are marked so.

### 13.3 Effects

#### 13.3.1 `effect.add`

Adds one effect to a clip's stack. Payload: `clipId`, `effect`, optional `params`, optional `index`.

**Refusals, in order**

1. `effect` is missing, or is not an effect `id` of the catalogue: `invalid`.
2. `params` is present and is not an object (an array is not one): `invalid`. A `null` is read as absent.
3. `index` is present and is not a number: `invalid`. A `null` is not read as absent.
4. `index` is not a whole number from 0 to the length of the stack: `invalid`.

**Effect.** The entry `{ id, effect: { type: "gpu-effect", gpuEffectType: effect, params }, enabled: true }` is inserted at `index`, or appended when there is none. `params` is stored **exactly as sent**, and as `{}` when absent: defaults are not filled in, and names, types and ranges are not checked.

An audio clip takes no effects: the command is applied and changes nothing (`effect.add/audio-clip-changes-nothing`).

**Draws:** the effect's `id`. It is drawn for an audio clip too, and not kept.

**Implementation-defined.** `params` is not checked (`effect.add/params-are-not-checked`). **Native rule:** send every parameter of the catalogue entry, each at its default or the chosen value, of the catalogue's type and inside its range (`effect.add/full-defaults`), and nothing else. Do not send `effect.add` for an audio clip.

#### 13.3.2 `effect.remove`

Removes one effect. Payload: `clipId`, `effectId`.

**Refusal:** `effectId` is missing or names no effect of this clip: `invalid`.

**Effect.** The entry is removed. The others keep their order and ids. An empty stack stays as `effects: []`.

**Draws:** none.

**Implementation-defined.** Keyframes on the removed effect's parameters (`effect:…:<effect id>:…`) are left in the graph (`effect.remove/keeps-parameter-keyframes`). **Native rule:** reproduce it. A native client that wants them gone removes them with `keyframe.remove` first.

### 13.4 Transitions

#### 13.4.1 `clip.setTransition`

Adds, changes or removes the transition **out of** a clip. Payload: `clipId` (the outgoing clip) and `transition`: `{ type, duration }`, or `null` to remove.

The catalogue of commands describes this command by the cut before a clip. The engine reads `clipId` as the clip **before** the cut. That reading is the protocol.

**Refusals, in order**

1. `transition` is absent, or is neither an object nor `null`: `invalid`.
2. `type` is not a string: `invalid`.
3. `type` is neither one of the five aliases nor a transition `id` of the catalogue: `invalid`.
4. `duration` is not a valid non-negative time, or rounds to less than one frame: `invalid`.
5. The clip has a transition out of it, and the new length is not valid for its two clips (12.2.6, read with the transition's stored `alignment`): `failed`. See the exception below.
6. The clip has none, and no clip follows it on its track: `invalid`.
7. The clip has none, and the two clips cannot share one (below): `failed`.

**The presentation.** `type` is a catalogue transition `id`, or one of the aliases: `Cross dissolve` (`dissolve`), `Dip to black` (`dipToColorDissolve`), `Wipe` (`wipe`), `Slide` (`slide`) and `Zoom` (`lensWarpZoom`).

**Remove (`transition: null`).** The transition whose `leftClipId` is the clip is removed. When there is none, the command is applied and changes nothing. The transition **into** a clip is not touched (`clip.setTransition/remove-reads-outgoing-side-only`).

**Change.** When the clip has a transition out of it, its `durationInFrames` and `presentation` are replaced. Its `id` and every other field stay, including `direction`, `timing`, `alignment`, `bezierPoints` and `properties`, even where the new presentation has no use for them (`clip.setTransition/update-keeps-other-fields`).

**Add.** Otherwise the **next clip** is the first clip on the same track, in order of `from`, with `from ≥ end(clip) − 1`. With `n` the requested length in frames:

1. `most = min(clip length, next clip length) − 1`. When `most < 1`, refusal 7.
2. `d = max(1, min(n, most))`.
3. When the clips meet (`|end(clip) − next.from| ≤ 1`): let `M` be the longest length the handles allow at alignment 0.5 (12.2.6). When `M < 1`, refusal 7. Otherwise `d = min(d, M)`.
4. The transition must be valid at length `d` (12.2.6), or refusal 7. This is what refuses clips that do not meet and clips that are not video, still or composition items.
5. The entry `{ id, leftClipId, rightClipId, trackId, type: "crossfade", durationInFrames: d, presentation, timing: "linear", alignment: 0.5 }` is appended to `timeline.transitions`.

**Draws:** the transition's `id` when one is added. None for a change or a removal.

**Implementation-defined.**

- A **new** transition that is too long is silently shortened, to the clips (`…/adds-clamped-to-clip-length`) and to the handles (`…/adds-clamped-to-handles`). A **change** that is too long is refused (`…/rejects-update-longer-than-clips`, `…/rejects-update-beyond-handles`). **Native rule:** reproduce both. Ask only for lengths that fit.
- A change that asks for the length the transition already has is not checked. When that length is not valid, the command is applied and writes nothing, not even the presentation (`…/update-same-length-is-not-checked`). No command produces such a transition. **Native rule:** reproduce it.
- The catalogue's `editorDuration` is what the web editor offers. The command does not enforce it (`…/adds-half-frame-rounds-up` is one frame long). **Native rule:** offer lengths inside it.
- Other fields of `transition` (`direction`, `alignment`, `timing`, `properties`) are ignored (`…/other-fields-are-ignored`). See 13.8.5.

### 13.5 Keyframes

Section 13.2.4 defines entries, groups and frames. In this section a **region** is a transition region of the clip (13.2.3), and "the keyframe" is found in the group of the named `property`: a vector group when `property` is `position`, `scale` or `anchor`, a scalar group otherwise. A `keyframeId` that is not in that group is `invalid`.

#### 13.5.1 `keyframe.add`

Adds a keyframe, or replaces the one on that frame. Payload: `clipId`, `property`, `at`, `value`, optional `easing`.

**Refusals, in order, for a scalar property**

1. `at` is not a valid non-negative time: `invalid`.
2. `value` is not an object whose `value` is a finite number: `invalid`.
3. `easing` is present and is not a string: `invalid`.
4. `at` is outside the clip: `invalid`.
5. The frame is in a region: `failed`.

**Refusals, in order, for a vector property**

1. `at` is not a valid non-negative time: `invalid`.
2. `at` is outside the clip: `invalid`.
3. `easing` is present and is not one of the seven easing types: `invalid`.
4. `value` is not an object with finite `x` and `y` (each within ±1e9): `invalid`.
5. The frame is in a region: `failed`.

**Effect.**

- The clip's entry is created at the end of `timeline.keyframes` when it has none. The property's group is created at the end of the entry's groups when it has none.
- When the group has **no keyframe on the frame**, `{ id, frame, value, easing }` is inserted in frame order. `easing` is `linear` when absent. A scalar `value` is `value.value`. A vector `value` is `{ x, y }`; other fields of it are dropped.
- When the group **has a keyframe on the frame**, that keyframe keeps its `id` and takes the new `value` and `easing` (`linear` when absent). Its `easingConfig` is removed, and a vector keyframe also loses `temporalEase` and `spatial` (`keyframe.add/same-frame-replaces-parameters`, `…/vector-same-frame-drops-handles`).

**Draws:** one id. It is the new keyframe's `id`, and it is not kept when a keyframe was replaced.

**Implementation-defined.**

- A scalar `property` and its value are not checked (13.2.5).
- A scalar `easing` is stored as sent: any string is accepted, where a vector property checks it. No fixture records an unknown easing, because its graph breaks the schema. **Native rule:** send one of the seven types, or none.
- `cubic-bezier` and `spring` are stored without parameters (`keyframe.add/easing-without-parameters`). **Native rule:** add the keyframe, then send `keyframe.setEasing`.
- A keyframe that a transition later covered cannot be replaced by `keyframe.add` (`…/rejects-replace-inside-transition-region`), though `keyframe.update` can give it a value.

#### 13.5.2 `keyframe.remove`

Removes keyframes of one property. Payload: `clipId`, `property`, `keyframeIds`.

**Refusals, in order**

1. `keyframeIds` is not a non-empty array of strings: `invalid`.
2. One of the ids is not in the group: `invalid`. Nothing is removed.

**Effect.** The keyframes are removed. An id listed twice is removed once. The group stays, empty when its last keyframe went. Regions are not looked at. For a **vector** property the sweep of 13.2.4 then runs. For a scalar property it does not.

**Draws:** none.

#### 13.5.3 `keyframe.update`

Moves or revalues one keyframe, or sets a vector keyframe's handles. Payload: `clipId`, `property`, `keyframeId`, and any of `at`, `value`, `temporalEase`, `spatial`.

**Refusals, in order**

1. Scalar property: `temporalEase` or `spatial` is present, even as `null`: `invalid`.
2. `keyframeId` is missing or not in the group: `invalid`.
3. `at` is present and is not a valid non-negative time (a `null` is not one), is outside the clip, or names a frame another keyframe of the group is on: `invalid`.
4. `value` is present and is not `{ value: finite number }` (scalar) or `{ x, y }` with finite numbers within ±1e9 (vector): `invalid`.
5. Vector property, `temporalEase` present and not `null`: it is not an object, has neither `in` nor `out`, or a handle is not `{ speed, influence }` with `speed` finite within ±1e9 and `influence` in 0.1..100: `invalid`.
6. Vector property, `spatial` present: the property is not `position` (this holds for `null` too); or, when not `null`, it is not an object, `continuous` is not a boolean, a tangent is not `{ x, y }`, the tangents are incomplete, or `continuous` tangents do not mirror each other (below): `invalid`.
7. Nothing was asked for: `invalid`.
8. `at` names a frame in a region, other than the frame the keyframe is on: `failed`.

**Effect.**

- `at` sets `frame`, and the group is sorted by frame again. `value` sets the value. Easing and its parameters are kept.
- `temporalEase` replaces the keyframe's handles **whole** with `{ in, out }`, each `{ speed, influence }` and present only when sent. `null` removes the field.
- `spatial` replaces the tangents with `{ inTangent, outTangent }`, plus `continuous: true` when it was sent as `true`. With `continuous: true` and only one tangent, the other is its mirror image (`{ −x, −y }`). Without `continuous`, both tangents are required. With `continuous: true` and both, they must mirror each other within 1e-9 in each coordinate. `null` removes the field.
- Fields of the handle objects that these rules do not name are dropped.

**Draws:** none.

**Implementation-defined.** When `at` names the frame the keyframe is already on, and that frame is in a region, **nothing** is written: a `value` sent with it is dropped and the command is still applied (`keyframe.update/own-frame-inside-transition-drops-the-value`). Without `at`, the same keyframe takes the value (`…/inside-transition-may-be-revalued`). **Native rule:** do not send `at` unless the keyframe moves.

#### 13.5.4 `keyframe.setEasing`

Sets the easing of keyframes of one property. Payload: `clipId`, `property`, `keyframeIds`, `easing`, optional `bezier`, optional `spring`.

**Refusals, in order**

1. `keyframeIds` is not a non-empty array of strings: `invalid`.
2. One of the ids is not in the group: `invalid`.
3. `easing` is missing or is not one of the seven types: `invalid`.
4. `cubic-bezier`: `bezier` does not have four finite numbers `x1`, `y1`, `x2`, `y2`, or `x1` or `x2` is outside 0..1: `invalid`.
5. `spring`: after the defaults are filled in, `tension`, `friction` or `mass` is not a number in its range (13.2.6): `invalid`.
6. Any other easing: `bezier` or `spring` is present, even as `null`: `invalid`.

**Effect.** Each named keyframe gets the `easing`, and its `easingConfig` is replaced:

- `cubic-bezier`: `{ type, bezier: { x1, y1, x2, y2 } }`. Other fields of `bezier` are dropped.
- `spring`: `{ type, spring }`, where `spring` is the defaults overlaid with the fields sent. A `null` or absent `spring` gives the defaults.
- Any other easing: `easingConfig` is removed.

Frame, value, `temporalEase` and `spatial` are kept. Regions are not looked at.

**Draws:** none.

**Implementation-defined.** A `bezier` sent with `spring`, and a `spring` sent with `cubic-bezier`, are ignored, where a plain easing refuses both (`keyframe.setEasing/spring-ignores-bezier`, `…/bezier-ignores-spring`). Fields of `spring` other than the three are stored (`…/extra-spring-fields-are-kept`). **Native rule:** send `bezier` only with `cubic-bezier`, `spring` only with `spring`, and only the named fields.

### 13.6 Expressions and procedural motion

#### 13.6.1 `property.setExpression`

Sets or clears the expression of one property. Payload: `clipId`, `property`, `expression` (a string, or `null` to clear).

**Refusals, in order**

1. `property` is not one of the catalogue's `properties.expression`: `invalid`. Those are the transform and shape properties of 13.2.5 and the three vector properties. Crop, `volume`, text and effect properties carry no expression.
2. `expression` is absent, is not a string, or is blank: `invalid`.
3. The expression has an error (below): `invalid`.
4. The expression gives a number for a vector property, or a vector for a scalar one: `invalid`.

**The language.** An expression is one arithmetic formula:

```text
expression     = additive
additive       = multiplicative { ("+" | "-") multiplicative }
multiplicative = unary { ("*" | "/") unary }
unary          = { "+" | "-" } primary
primary        = number | "(" additive ")" | "[" additive "," additive "]" | name | call
name           = "value" | "preValue" | "frame" | "time"
call           = function "(" [ additive { "," additive } ] ")" | "prop" "(" string "," string ")"
function       = "abs" | "sin" | "cos" | "min" | "max" | "clamp" | "lerp"
```

- A **number** is a run of digits with at most one dot, which may come first or last (`.5`, `5.`). There is no exponent form. It must be finite as a double.
- A **string** is in single or double quotes. A backslash takes the next character as it is.
- A name or function starts with a letter or `_` and goes on with letters, digits and `_`. White space between tokens is skipped. Any other character is an error.
- A value is a **number** or a **vector** `[x, y]`. The two parts of a vector literal must be numbers.
- `value` and `preValue` are the property's value before the expression. `frame` is the sequence frame and `time` is `frame / fps`. `prop("<clip id>", "<property>")` is a property of another clip; the property must be one of `properties.expression`.
- `+ − × ÷` work on two numbers, on two vectors part by part, and on a number with a vector by applying the number to both parts.
- `abs`, `sin`, `cos` take one argument. `min` and `max` take two or more. `clamp(v, low, high)` takes three and is `min(max(v, low), high)`. `lerp(a, b, t)` takes three, and `t` must be a number.
- Limits: at most 2048 UTF-16 code units, at most 512 tokens, and nesting at most 64 deep, where a number inside `n` pairs of parentheses is `n + 1` deep.

**The check.** The command reads the expression **once, left to right, computing as it reads**, with stand-in values: `value` and `preValue` are `1` (or `[1, 1]` for a vector property), `frame` and `time` are `0`, and `prop(…)` is `1`, or `[1, 1]` for a vector property. The clip id inside `prop` is not looked up.

1. The tokens are read first. A bad character, a bad number, an unterminated string or a broken limit is an **error**.
2. While reading: a missing or extra token, an unknown name or function, a wrong number of arguments, a vector where a number is required, and an unknown property in `prop` are **errors**.
3. A division whose divisor is `0`, or a vector with a `0` part, **stops the reading**. It is not an error: it is a fault of one frame, and the expression is accepted without the kind check of refusal 4. A final result that is not finite is accepted the same way.

**Effect.**

- **Set.** `{ type: "expression", targetProperty, source, enabled: true }` is put at the **end** of the entry's `expressions`, after the entry's expression for the same property, if any, is removed. `source` is the string exactly as sent. The entry is created when the clip has none.
- **Clear.** The property's expression is removed. Then the sweep of 13.2.4 runs, even when there was nothing to remove.

**Draws:** none.

**Implementation-defined.**

- Reading stops at the first division by zero, so an error after it is not found (`property.setExpression/error-after-division-by-zero-is-not-checked`), and the kind is not checked (`…/kind-after-division-by-zero-is-not-checked`). **Native rule:** a native client sends only expressions that are free of errors and of the right kind when read to the end. Given such an envelope in a fixture, it reproduces the engine.
- An audio clip accepts an expression (`…/audio-clip-is-not-checked`). **Native rule:** do not send one.

#### 13.6.2 `property.setModifier`

Attaches a procedural modifier to a clip, or removes the modifiers that drive a property. Payload: `clipId`, `property`, `modifier` (an object, or `null` to remove).

A clip's `motionModifiers` is a list of:

```text
{ version: 2, id, type, enabled, amplitude, frequency, phaseFrames, seed, channelGains }
```

| `type`         | Channels it drives           |
| -------------- | ---------------------------- |
| `float-drift`  | `x`, `y`, `rotation`         |
| `breath-pulse` | `width`, `height`, `opacity` |
| `micro-shake`  | `x`, `y`, `rotation`         |
| `sway`         | `rotation`                   |
| `spin`         | `rotation`                   |

`channelGains` is optional. It maps a channel (`x`, `y`, `width`, `height`, `rotation`, `opacity`) to a gain in 0..2. A channel with no gain has gain 1. A modifier **drives** a property when the property is one of its type's channels and its gain for it is above 0. A clip has at most one modifier of each type.

**Refusals, in order, for a modifier**

1. `modifier` is absent or is not an object: `invalid`.
2. `type` is not one of the five: `invalid`.
3. `amplitude` is not a number in 0..2: `invalid`.
4. `frequency` (Hz) is not a number in 0.01..30: `invalid`.
5. `phaseFrames` is present and is not a number in 0..1 000 000: `invalid`.
6. `seed` is present and is not a number within ±1 000 000: `invalid`.
7. `enabled` is present and is not a boolean: `invalid`.
8. `channelGains` is present and is not an object, names a channel outside the six, or holds a gain outside 0..2: `invalid`.
9. The modifier does not drive `property`: `invalid`.

**Effect.** The stored modifier has `version: 2`; the `id` sent, or a drawn one when `id` is absent or empty; `enabled` (`true` unless `false` was sent); `amplitude`, `frequency` and `seed` (default `1`) as sent; `phaseFrames` (default `0`) rounded to a whole frame, halves up; and `channelGains` as sent, only when sent. The clip's modifier of the same `type`, if any, is removed, and the new one is put at the **end** of the list.

**Remove (`modifier: null`).** Every modifier of the clip that drives `property` is removed, of any type, enabled or not. When none does: `invalid`. An empty list stays as `motionModifiers: []`.

**Draws:** the modifier's `id`, only when the payload gives none.

**Implementation-defined.** A gain for a channel the type does not drive is stored (`property.setModifier/gain-of-another-type-is-kept`). An audio clip accepts a modifier (`…/audio-clip-is-not-checked`). **Native rule:** send gains only for the type's channels, and no modifier for an audio clip.

#### 13.6.3 `property.bakeModifier`

Turns a clip's procedural motion into keyframes. Payload: `clipId`, `property`, `modifierId`.

**Refusals, in order**

1. `modifierId` is missing or names no modifier of the clip: `invalid`.
2. The modifier has `enabled: false`: `invalid`.
3. The modifier does not drive `property`: `invalid`.
4. A baked keyframe would fall in a region: `failed`.

**Effect.** The bake is of the **whole clip**, not of the one modifier: every enabled modifier is baked together, and **every** modifier of the clip, disabled ones included, is then removed (`motionModifiers: []`).

- The **baked properties** are the channels driven by the enabled modifiers with `amplitude > 0`, in the order of the modifiers and of each type's channels.
- The **sampled frames** are frame 0, the last frame (`durationInFrames − 1`), and every `step` frames from 0, where `step` is the least, over those modifiers, of `max(1, round(fps / max(0.01, frequency × n)))`, with `n = 1` for `micro-shake` and `6` for the others.
- The existing groups of the baked properties are removed. For each sampled frame, in order, and each baked property, a keyframe `{ id, frame, value, easing: "linear" }` is added (13.5.1). `value` is the property's value at that frame with the clip's keyframes and modifiers applied.
- When no enabled modifier has `amplitude > 0`, or the clip is one frame long, no keyframe is written and no group is removed. The modifiers are still removed (`property.bakeModifier/zero-amplitude`, `…/one-frame-clip-bakes-nothing`).

**Draws:** one id that is not kept, then one id for each keyframe in the order written.

**Engine arithmetic.** The baked values are engine arithmetic (13.1): the fixtures that write keyframes are marked. **Native rule:** a native client does not bake unless it reproduces them. It may always apply the two cases that write no keyframe, and must refuse as the engine does.

**Implementation-defined.** The engine finds a blocked keyframe by counting the clip's scalar keyframes after the bake. Keyframes of properties the bake does not replace can therefore hide the block, and the command is then applied with the blocked keyframes missing. No fixture records it. **Native rule:** refuse (`failed`) whenever a sampled frame is in a region.

### 13.7 Text motion and Ken Burns

#### 13.7.1 `text.setMotion`

Sets or clears a title's text motion. Payload: `clipId`, `motion` (an object, or `null` to clear).

`motion` has up to three **slots**, `in`, `out` and `loop`. A slot is:

| Field            | Stored as                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------- |
| `presetId`       | Required. A preset of that slot in the catalogue's `textMotion`.                            |
| `durationFrames` | A finite number, rounded (halves up), at least 1. Default `12`.                             |
| `offsetFrames`   | A finite number, rounded, at least 0. **Stored only when above 0.**                         |
| `staggerFrames`  | A finite number, rounded, at least 0. Default `0`.                                          |
| `intensity`      | A finite number, clamped to 0..2. Default `1`.                                              |
| `order`          | `forward`, `backward`, `center` or `random`. Anything else is `forward`.                    |
| `easing`         | `linear`, `ease-in`, `ease-out`, `ease-in-out` or `overshoot`. Anything else is `ease-out`. |
| `seed`           | A finite number, rounded. Default `0`.                                                      |
| `unit`           | `character`, `word`, `line` or `whole-clip`. **Stored only when it is one of these.**       |

**Refusals, in order**

1. The clip is not a title (`type: "text"`): `invalid`. This holds for `null` too.
2. `motion` is absent or is not an object: `invalid`.
3. `motion` has no slot, or a field other than the three slots: `invalid`.
4. A slot that is present is not an object with a `presetId` of that slot: `invalid`.

**Effect.** The clip's `textMotion` is replaced **whole** by the slots sent, each normalised as the table says. Slots not sent are removed. Values that are not finite numbers take the default. Fields of a slot outside the table are dropped. `null` removes `textMotion`.

**Draws:** none.

Out-of-range values are normalised, not refused (`text.setMotion/values-are-normalised`). **Native rule:** send values that are already normal, so that the graph holds what was sent.

#### 13.7.2 `clip.setKenBurns`

Sets or clears the move of a still: a pan and zoom from one region of the photo to another. Payload: `clipId`, `kenBurns`: `{ from, to }`, or `null` to clear.

A **region** here is `{ x, y, w, h }` in fractions of the photo: its top-left corner and its size. The move is recorded on the clip as `frameleafKenBurns: { from, to, keyframeIds }`, and realised as eight scalar keyframes that the record lists.

**Refusals, in order**

1. The clip is not a still (`type: "image"`): `invalid`. This holds for `null` too.
2. `kenBurns` is absent or is not an object: `invalid`.
3. For `from`, then `to`: it is not an object; one of `x`, `y`, `w`, `h` is not a number in 0..1; `w < 0.2` or `h < 0.2`; `|w − h| > 1e-9`; `x + w > 1 + 1e-9` or `y + h > 1 + 1e-9`: `invalid`.
4. The clip already animates its position or size: a keyframe of `x`, `y`, `width` or `height` that the clip's record does not list, or any keyframe of the vector properties `position` or `scale`: `invalid`.
5. A keyframe of the move would fall in a region of a transition: `failed`.

**Effect.**

1. Every keyframe the clip's record lists is removed, from whichever scalar group it is in. The groups stay.
2. For `null`: the record is removed, and that is all. The four groups stay, empty (`clip.setKenBurns/clears`).
3. The **base** is the clip's stored `transform`: `x` and `y` (0 when absent) and `width` and `height` (the fitted size of 12.6.3 when absent). Rotation plays no part.
4. For each of `from` and `to`, in doubles and in this order:

   ```text
   width  = base.width / w
   height = base.height / h
   x      = base.x + (0.5 − (rx + w / 2)) × width
   y      = base.y + (0.5 − (ry + h / 2)) × height
   ```

   where `rx` and `ry` are the region's `x` and `y`.

5. Eight keyframes are added as `keyframe.add` adds them (13.5.1), all `linear`: for `x`, `y`, `width`, `height` in that order, one at frame `0` with the `from` value and one at frame `max(1, durationInFrames − 1)` with the `to` value.
6. The record becomes `{ from, to, keyframeIds }`, with `from` and `to` holding only `x`, `y`, `w` and `h`, and the eight ids in the order written.

**Draws:** the eight keyframe ids, in the order written.

**Implementation-defined.** On a one-frame clip the second keyframe of each pair is at frame 1, outside the clip. **Native rule:** do not offer a move for a one-frame clip.

### 13.8 Fields that no command writes

Some graph fields have no engine command at this revision: the engine refuses their catalogue command as `not-implemented` (8.2), or the catalogue has none. The web editor writes them from its own controls. This section says how a native edit of them must look. The catalogue lists them under `directEdits`.

A **direct edit** changes only the fields its rule names, to values its rule allows, in a graph in normal form. Every graph that follows these rules is in normal form: the engine returns it unchanged (fixture `normal-form/direct-edit-fields-are-kept`). A direct edit is saved like any other graph. The save's `commands` carries **no envelope** for it, because the web engine would refuse that envelope and the rule of 8.2 stands: a native client never records a `not-implemented` command. A native client records a direct edit in its session history like a command (section 9).

A field not listed here, of a command the engine does not implement, stays under the rule of 8.2: a native client must not change it.

#### 13.8.1 Effect parameters (`effect.update`)

A native client may replace values in `effects[].effect.params` of an existing entry. Each value must be of the catalogue parameter's type: a `number` inside `min..max`, a `boolean`, one of a `select`'s `options`, a `color` string, or a string for `text` and `json`. The entry's `id`, `gpuEffectType`, `enabled` and place in the stack do not change. It must not add a name the catalogue does not list for that effect, and it should leave no catalogue parameter out.

#### 13.8.2 Effect order (`effect.reorder`)

A native client may move an entry to another place in its clip's `effects` array. Every entry keeps its `id` and contents, and none is added or removed. Keyframes of effect parameters name the effect by `id`, so they follow.

#### 13.8.3 Effect on and off

A native client may set `effects[].enabled` to `true` or `false`. No catalogue command exists for it.

#### 13.8.4 Blend mode (`clip.setBlendMode`)

A native client may set a visual clip's `blendMode` to a blend mode `id` of the catalogue. An absent `blendMode` means `normal`; to return to it, write `"normal"`. A shape with `isMask: true` is always `normal`: loading rewrites its blend mode, so a native client must not give it another. The opacity that the catalogue command also carries is `transform.opacity`, which `clip.setTransform` sets (12.6.3): use that command.

#### 13.8.5 Transition settings

A native client may set, on an existing transition:

- `direction`: one of the `directions` of its presentation in the catalogue. Remove the field when the presentation has none.
- `timing`: one of the presentation's `timings`. With `cubic-bezier`, also `bezierPoints: { x1, y1, x2, y2 }`, with `x1` and `x2` in 0..1.
- `properties`: values of the presentation's `parameters`, by name. A `number` inside its range; a `color` as an array of three numbers.

It must not change `alignment`, `type`, the clip ids or `trackId`. **Implementation-defined:** no command reads or writes an alignment other than 0.5, and the engine's rules for other alignments (handles, regions, repair) are exercised only by graphs made elsewhere. `durationInFrames` and `presentation` are set with `clip.setTransition`.

### 13.9 `clip.setAudio`

This command edits the named audio or video clip through the same `updateItem` action as the editor's audio controls. It writes supplied gain, fade and pitch fields, and replaces the EQ stage when `eq` is supplied:

- `volume`: a finite number in −60..12 dB, stored as the clip's static `volume`.
- `fadeIn` and `fadeOut`: exact rational durations in 0..5 seconds, the range of the editor's sliders. Store `num / den` as `audioFadeIn` and `audioFadeOut`, respectively. These are seconds, including durations shorter than one video frame; do not round them to frames. A zero duration resets the fade. Fades may overlap or exceed a short clip, as the editor permits.

- `muted`: a boolean, stored as the clip's `muted`. Omission preserves it; false resets the clip control. Missing and false are audible unless an independent track/parent/ownership rule suppresses sound.
- `pitchSemitones`: an integer in −12..12, stored as `audioPitchSemitones`.
- `pitchCents`: an integer in −100..100, stored as `audioPitchCents`. Effective pitch is semitones + cents / 100. Zero resets either field; changing one preserves the other. Playback and export use the existing pitch paths, with their existing channel/latency admission limits.
- `eq`: an object with the settings below, replacing the clip's known EQ fields as an editor EQ preset does. Omitted settings take their defaults. An empty object resets the stage to flat defaults. `null` clears all known `audioEq*` fields. Omitted `eq` preserves the current stage.

EQ setting names are stored with `audioEq` prefixed and the first letter capitalized. `enabled` is a boolean; omission clears `audioEqEnabled` so the engine's enabled-by-default behavior applies. Other `*Enabled` settings are booleans. All numeric settings must be finite. Gain (`outputGainDb`, every band's `*GainDb`, and legacy `midGainDb`) is in −20..20 dB, Q in 0.3..10.3, and cut slope is 6, 12, 18 or 24 dB/octave. Unknown settings, wrong types, out-of-range values and contradictory cut aliases are invalid, rather than silently clamped.

| Band prefix | Default enabled/type | Frequency domain and default (Hz) | Default Q |
| ----------- | -------------------- | --------------------------------- | --------- |
| `band1`     | false / high-pass    | 20..399; 30                       | 1.1       |
| `low`       | true / low-shelf     | 20..22000; 120                    | 2.3       |
| `lowMid`    | true / peaking       | 20..22000; 400                    | 1.1       |
| `highMid`   | true / peaking       | 20..22000; 1600                   | 1.1       |
| `high`      | true / high-shelf    | 20..22000; 2800                   | 2.3       |
| `band6`     | false / low-pass     | 1400..22000; 22000                | 1.1       |

Each band has `Enabled`, `Type`, `FrequencyHz`, `GainDb` (default 0) and `Q`. Band 1 and band 6 also have `SlopeDbPerOct` (default 12). Types for band 1 are low-shelf, peaking, high-shelf and high-pass; for band 6, low-pass, low-shelf, peaking and high-shelf; for the inner bands, low-shelf, peaking, high-shelf and notch. `outputGainDb` and legacy `midGainDb` default to 0.

The legacy `lowCut` and `highCut` prefixes each have `Enabled`, `FrequencyHz` and `SlopeDbPerOct`, with the corresponding outer band's defaults and domains. When no field of an outer band is supplied, its enabled/frequency/slope come from the legacy cut and its type is high-pass (band 1) or low-pass (band 6). When any outer-band field is supplied, that band's settings take precedence. The stored cut enabled value is outer-band enabled AND its type is the cut type; its frequency and slope mirror the outer band. Every explicitly supplied alias must equal that resolved value. The engine's existing resolver and preset mapper supply the defaults and stored fields; these rules do not add DSP.

Require at least one of these fields. Reject an unknown field, malformed or out-of-range value, missing clip or other clip type as `invalid`. A clip on a locked track is refused as `failed`. Clip mute is combined with track/parent mute in preview and export; resetting it never clears those states. A video's `embeddedAudioMuted` and linked-audio ownership still suppress embedded sound independently, including when the owning audio clip is muted. Neither ownership nor gain is rewritten to implement mute. Muted clips do not contribute meter/scrub audio or duck other clips; transition and nested audio retain the same control.

Leave omitted gain/fade/pitch/mute fields, volume keyframes, fade curves, source windows, channels, linked companions, tracks and the master/monitor controls unchanged. EQ replacement changes only known clip EQ fields; unknown extension fields survive. The command addresses one clip; it does not expand linked selection. Existing volume keyframes continue to override static gain during playback. Save, reopen, undo and redo use the usual graph and host history rules (sections 7 and 9).

### 13.10 `track.setAudio`

Payload: `trackId`, optional `gainDb`, `eq`, `pan` and `gainEnvelope`. This command edits one media track with the existing `setTracks` action. It never expands linked selection or rewrites clips.

- `gainDb`: a finite number in −60..12 dB, stored as track `volume`. Zero resets gain; omission preserves it. This is the same static gain as `track.set.patch.gain` (12.7.4), consumed alongside clip gain by preview and export.
- `eq`: a complete track EQ stage using exactly the names, types, ranges, defaults and legacy-cut alias rules of 13.9. Store the resolved settings directly in track `audioEq`, with the supplied `enabled` value (omission uses the enabled default). An object replaces the previous stage, `{}` resets to flat defaults, and `null` clears `audioEq`. Omitted `eq` preserves the current stage. Preview and export append track EQ before clip EQ; this command adds no signal processing.

- `pan`: a finite number in −1..1, stored as track `pan`. Negative moves toward left, positive toward right. Omission preserves it; zero bypasses pan and restores the original source plane handling. Preview and both PCM export mixers apply the Web Audio StereoPanner law after EQ, in leaf-track then inner-to-outer wrapper order. Active pan requires an admitted mono or stereo source and produces stereo output. Preview decodes source channel count before playing active pan; unknown or unsupported layouts remain silent. Export retains its matching source-plane admission and refuses active pan on multichannel sources before publishing a mix. Pan disables packet passthrough.

Require at least one of `gainDb`, `pan`, `eq` and `gainEnvelope`. Reject unknown payload fields, malformed values, an absent track or an organizational `isGroup` track as `invalid`. Gain and EQ validate before pan. A locked media track is refused as `failed`. A refused batch publishes no partial edits.

Leave all other tracks, clip fields, source windows, linked ownership, keyframes, master controls, mute/solo/visibility and track metadata unchanged. Track mute remains the separate existing `track.set.patch.muted` operation; this command accepts no mute field. Optional `gainEnvelope` follows section 14.7 point admission, linear dB interpolation, endpoint hold and omission/empty clearing rules, stored on the addressed track in its owning sequence frame domain. An active curve replaces that track's static gain; clip, inner/outer track stages, master and monitor remain independent. Static fader commands change only the fallback; transient fader preview is a multiplier relative to effective automation and never changes persisted points. Root modulo is evaluated before each independent nested owner map. Selected export ranges preserve absolute root sample origin. Keep-time retimes points with the existing rational nearest-frame rule and refuses collapsed points; keep-frames preserves them, including envelope-only empty tracks. A separate track-stage revision and ACK fences curve/map/static/mute/history replacement even when transport generation stays unchanged. Loading, stale/failed/unacknowledged or unsupported maps are silent; finite scheduling is not repeated-loop authority. Uniform gain preserves admitted source channels. Active audible curves refuse original-byte smart copy and encoded packet passthrough. Project master automation remains section 14.7. Save, reopen, undo and redo use the existing graph and host history rules (sections 7 and 9).

Composition audio keeps ascending half-open source bounds and positive speed magnitude. A containing wrapper mirrors its child window and composes media direction by XOR; a leaf's own media reversal does not reverse its timeline-authored fade or volume keyframes. Evaluate those functions at the original owning-sequence coordinate, with each ancestor wrapper's direction included. Reverse gain begins at the continuous exclusive endpoint `H`, while reversed PCM begins with the last valid decoded sample below `H`. Intersect decoded packet presentation timestamps with the requested range on every channel before reversing or stretching samples. Track gain uses the resampled contribution's output clock and absolute root origin, and master gain is applied once. Reversed or retimed media keeps the existing full-PCM export selection; a double reversal may use windows only when every existing window-admission condition passes. Native entered-child `SET_TRACKS` uses child history and persistence; this does not add a canonical child-target field to `track.setAudio`. Child compound transitions and browser audible/continuous qualification remain separate from this mapping contract.

This section gives the mutation rules of the 8 commands of FL-309 (NAPI-020), the master-bus gain/mute command of FL-103 (14.7), and the title styles and animations that `clip.update` shares with `title.add`. Section 8.3 lists every graph-changing command with its status.

| `sequence.setSettings`, `project.applyTemplate`                       | 14.5, 14.6 |

### 14.1 How to read the rules

- Sections 12.1 and 13.1 apply.
- No command of this part checks a lock. That is implementation-defined, and the native rule of 12.2.2 holds: a native client treats a lock as binding. `composition.add`, `clip.group`, `clip.ungroup` and `title.add` each have a `…/locked-track-is-not-checked` fixture.
- The parameter catalogue (13.2.1) gained four keys for this part: `titleStyles`, `titleAnimations`, `textMotion.defaults` and `project`.
- **Settling on load.** Three commands of this part can write a graph that is one load short of normal form (14.2.3). The fixtures mark such a case `"settlesOnLoad": true`.
- **Pose composition is still engine arithmetic.** Part 4 completes the rules that part 2 deferred to it: the title styles and animations of `clip.update` (14.3.2, 14.3.3) and clips inside a composition (14.2.1). It does **not** specify the composed pose of a clip that is animated or already parented. That pose comes from floating-point matrix arithmetic with sines, cosines and arctangents, which cannot be fixed to the last bit from observable behaviour (13.1). The rule of 12.6.4 therefore stands unchanged: a native client must not detach a clip, or attach one that is animated or already parented, unless it reproduces the fixtures marked `engineArithmetic` bit for bit.

### 14.2 Compositions and groups

#### 14.2.1 The stored composition

`timeline.compositions` holds the project's compositions. A composition is a small timeline of its own, and a clip that shows it is a **composition clip** (`type: "composition"`, with its `compositionId`).

| Field                            | Contents                                                                                                                                                                 |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `id`, `name`                     |                                                                                                                                                                          |
| `editorKind`                     | `sequence` (made by `composition.add`) or `composite-2d` (a **group**, made by `clip.group`).                                                                            |
| `items`                          | Its clips, as in 2.4, with `from` counted from the composition's first frame.                                                                                            |
| `tracks`                         | Its tracks, in ascending `order`. Unlike a track of the main timeline, each lists in `items` **a copy of every clip of `items` that is on it**, in the order of `items`. |
| `transitions`, `keyframes`       | Present only when not empty. As 13.2.3 and 13.2.4, for the composition's own clips.                                                                                      |
| `fps`, `width`, `height`         | The composition's own rate (a number) and canvas.                                                                                                                        |
| `durationInFrames`               | Its length in its own frames.                                                                                                                                            |
| `backgroundColor`                | Present only when the project had one when the composition was made.                                                                                                     |
| `compositionControls`            | Present only when the composition publishes controls (14.4.1).                                                                                                           |
| `markers`, `inPoint`, `outPoint` | Present only when set. No command of this protocol writes them.                                                                                                          |

A composition clip carries `compositionId`, `compositionWidth`, `compositionHeight`, and a source window in the composition's frames: `sourceStart`, `sourceEnd`, `sourceDuration`, `sourceFps` (the composition's `fps`) and `speed`. A composition with sound also has a **sound clip**: an `audio` item with the same `compositionId` and source window, linked to the composition clip by a shared `linkedGroupId`.

Commands address clips of the main timeline only (12.1). No command of this protocol changes a clip inside a composition, except by retiming the composition (14.6.1). `timeline.topLevelSequenceIds` lists compositions the web editor shows as tabs; no command writes it, and an id that names no `sequence` composition is dropped when the graph is written.

Loading gives every track of a composition `syncLock: true` when it has none.

#### 14.2.2 Gathering clips

`composition.add` and `clip.group` do the same thing with a different `editorKind`. Given the named clips:

1. **The gathered clips** are the named clips and every member of their linked groups (12.2.1), plus, for a composition clip or a sound clip among them, its companion. They are taken in `timeline.items` order.
2. `start` is their least `from`, and `length` is their greatest `end` minus `start`.
3. **Tracks.** The tracks that hold a gathered clip are taken in ascending `order`. For each, a track is made for the composition: `{ id, name, kind, height, locked: false, visible, muted, solo, volume, color, order, items }`, where `id` is drawn, `order` is its position (0, 1, …), `kind` is the source track's `kind` (when it has none: `audio` if every gathered clip on it is an audio item, else `video`), and the other fields are copied from the source track. It has **no `syncLock`** (14.2.3).
4. **Clips.** Each gathered clip is copied into the composition with a drawn `id`, `from − start`, and the `trackId` of its new track. Every other field is copied, `linkedGroupId` and `originId` included.
5. The composition's `id` is drawn.
6. **Transitions** whose two clips are both gathered are copied with a drawn `id` and the new clip and track ids. **Keyframes** entries of gathered clips are copied with the new `itemId`; keyframe ids do not change.
7. The composition is `{ id, name, editorKind, items, tracks, transitions, keyframes, fps, width, height, durationInFrames: length, backgroundColor }`, with the project's `fps`, canvas and background colour. It is appended to `timeline.compositions`.
8. **Whether it has a picture and sound.** It has a **picture** when a gathered clip is not an audio item. It has **sound** when one of its clips on an audible track carries sound. A track is audible when it is not `muted` and, if any of the composition's tracks is `solo`, is `solo` itself, and otherwise is not hidden (`visible: false`). A clip carries sound when it is: an audio item with a `mediaId`; a video with a `mediaId`, without `embeddedAudioMuted`, and with no linked audio clip among the composition's clips; a sound clip of a composition that has sound; or a composition clip with no sound clip of its own, of a composition that has sound.
9. **Where the clips go.** The composition clip goes on the gathered **non-audio** clips' track with the greatest `order`. The sound clip goes on the gathered **audio** clips' track with the greatest `order`; when no audio clip was gathered, on the audio track nearest below the composition clip's track (the audio track with the least `order` above its own; with no composition clip, the audio track with the greatest `order`); and when there is none, on a new audio track (12.2.8) just below that track (the midpoint to the next track's `order`, or `order + 1`).
10. The gathered clips are removed, with every transition that touches one and their keyframes entries. Every keyframes entry that holds no animation is swept too (13.2.4).
11. When the composition has both a picture and sound, a `linkedGroupId` is drawn for the pair. Then the composition clip is appended to `timeline.items`, and after it the sound clip:

```text
{ id, type: "composition", trackId, from: start, durationInFrames: length, label: name, compositionId, linkedGroupId,
  compositionWidth, compositionHeight, transform: { x: 0, y: 0, rotation: 0, opacity: 1 },
  sourceStart: 0, sourceEnd: length, sourceDuration: length, sourceFps: fps, speed: 1 }

{ id, type: "audio", trackId, from: start, durationInFrames: length, label: name, compositionId, linkedGroupId, src: "",
  sourceStart: 0, sourceEnd: length, sourceDuration: length, sourceFps: fps, speed: 1 }
```

**Draws, in order:** one id for each composition track; one for each copied clip; the composition's id; one for each copied transition; the new audio track's id, when one is made; the `linkedGroupId`, when there is one; the composition clip's id; the sound clip's id.

**Implementation-defined.**

- The clips are gathered where they are and **nothing is checked for overlap**. When a clip that stays on the composition clip's track lies inside `start … start + length`, or the sound clip lands on a clip, the result is not in normal form (`composition.add/leaves-a-clip-between`, `composition.add/covers-a-clip-on-its-track`, marked `outsideNormalForm`). **Native rule:** refuse to gather clips when the composition clip or the sound clip would share a frame with a clip that stays.
- A video with a `mediaId` counts as carrying sound even when its media has none, so a composition of silent videos gets a sound clip (`composition.add/two-clips`). **Native rule:** reproduce it.
- For a composition clip or sound clip that is trimmed or retimed, "has sound" is decided through its window. This protocol does not specify that case. **Native rule:** do not gather a trimmed or retimed composition clip.

#### 14.2.3 Settling on load

The graph `composition.add` and `clip.group` write has composition tracks without `syncLock`, which the next load adds (14.2.1). `clip.ungroup` can leave a stray list in a new track, which the next load empties (14.2.6). Nothing a person made changes, and one load reaches normal form. This is **implementation-defined**.

A fixture marked `settlesOnLoad` records the engine's graph and digest as usual, and `settled`: the digest and envelope digest of the graph after one load. The settled graph is the engine's graph with two changes:

- every track of every composition that has no `syncLock` gets `syncLock: true`;
- every track of the main timeline has `items: []`.

**Native rule.** A native client writes the **settled** graph: it is the normal form, and it is what the web engine itself holds after its next edit. Its digest must equal the fixture's `settled.digest`. A native client that receives an unsettled graph reads it as settled. This is the one exception to the rule of 2.6 that a graph outside normal form is opened read-only.

#### 14.2.4 `composition.add`

Gathers clips into a new `sequence` composition. Payload: `name`, `clipIds`.

**Refusals, in order**

1. `name` is missing or empty: `invalid`.
2. `clipIds` is not a non-empty array of strings: `invalid`. The command catalogue marks it optional; the engine requires it.
3. One of the ids names no clip of the main timeline: `invalid`.
4. `trackId` or `at` is present: `invalid`. The composition clip always goes where its clips were.

**Effect.** 14.2.2 with `editorKind: "sequence"`. An id listed twice is gathered once.

#### 14.2.5 `clip.group`

Gathers clips into a group. Payload: `clipIds`, optional `name`.

**Refusals, in order**

1. `clipIds` is not a non-empty array of strings: `invalid`.
2. One of the ids names no clip: `invalid`.
3. `name` is present and is not a string: `invalid`.

**Effect.** 14.2.2 with `editorKind: "composite-2d"` and the `name`, or `Group` when it is absent. An empty `name` is kept as it is. A group is one clip on the timeline: it can be moved, trimmed, animated and grouped again like any other.

#### 14.2.6 `clip.ungroup`

Takes a group apart and puts its clips back. Payload: `groupId` (the composition clip).

**Refusals, in order**

1. `groupId` is missing or names no clip: `invalid`.
2. The clip is not a composition clip of a `composite-2d` composition: `invalid`. A composition made by `composition.add` is not a group.

**Effect.** With `W` the composition clip and `S` its sound clip, if it has one:

1. **Tracks.** The composition's tracks are taken in ascending `order` and split into video and audio tracks (by `kind`, or as in 14.2.2 step 3). For the video tracks the **anchor** is `W`'s track. For the audio tracks it is `S`'s track; without `S`, the audio track nearest below `W`'s track; and without one, a new audio track (12.2.8) just below it. Its id is drawn, but the track is written only if step 2 makes a track too.
2. In each of the two lists, the **last** track maps to the anchor. Each earlier one, from the last backwards, maps to the nearest track above the anchor of the same kind that is not yet used and on which none of its clips, placed at `W.from + from`, would share a frame with a clip that is already there. When there is none, a track is made: a copy of the composition's track with a drawn `id` (a plain id, without `track-`), that `kind`, and `order = anchor order − 0.01 × (its distance from the last)`. The track list is then written as 12.2.8 says, so classic names are renumbered.
3. **Clips.** Each clip of the composition comes back through the window `W` shows. With `ws` and `we` `W`'s `sourceStart` and `sourceEnd`, and `shown(s) = floor(((s / W.sourceFps) × fps) / W.speed)` in doubles: the clip's part inside `ws … we` is kept (a clip wholly outside is dropped). Its `from` is `W.from + shown(max(from, ws) − ws)`, its length is the difference of the two `shown` values (at least 1), its `speed` is its own (or 1) times `W.speed`, and its `trackId` is the mapped track. A video, audio or composition clip has `sourceStart` written as its own (or 0) plus the frames cut from its start, and its `sourceEnd`, when it has one, less the frames cut from its end (at least `sourceStart + 1`). Frames cut are converted as `round((n / composition fps) × sourceFps × speed)`, with the clip's own `sourceFps` (or the composition's `fps`) and `speed`. It gets a drawn `id`. For a group that was never trimmed or retimed this is: `from + W.from`, the same length and source window, and `speed: 1` written on every clip.
4. `W` and `S` are removed, with the transitions that touch them. The restored clips are appended to `timeline.items` in the composition's order.
5. The composition's transitions between two restored clips are appended with drawn ids and repaired (12.2.6). Its keyframes entries are appended with the new `itemId`s.
6. The composition is removed, unless another clip of the project still shows it. Its published controls go with it; overrides on the group were never written into its clips.

**Draws, in order:** the new audio anchor track, when one is made (it is drawn even when it is not kept); each new track of step 2; each restored clip; each restored transition.

**Implementation-defined.**

- A track made in step 2 is a copy of the composition's track, so it lists that track's clips in `items` until the next load empties it. The graph settles on load (14.2.3; `clip.ungroup/makes-a-track-when-the-old-one-is-taken`). **Native rule:** write `items: []`.
- A keyframes entry of the group itself is not removed: it stays in the graph, naming a clip that is gone (`clip.ungroup/animated-group`). **Native rule:** reproduce it. A native client that wants it gone removes the group's keyframes first.
- Every restored clip gets `speed: 1`, titles and stills included (`clip.ungroup/round-trip`). **Native rule:** reproduce it.
- The id of an audio anchor track is drawn even when the track is not written, which moves every later draw by one. **Native rule:** reproduce the draw. A group whose own audio clips would land on a track that was not written is outside this protocol: do not ungroup it.

### 14.3 Titles

#### 14.3.1 `title.add`

Adds a title. Payload: `text`, `at`, optional `duration`, `style`, `position`, `animation`.

**Refusals, in order**

1. `text` is missing or empty: `invalid`.
2. `at` is not a valid non-negative time: `invalid`.
3. `duration` is present and is not a valid time, or rounds to less than one frame: `invalid`.
4. The project has no video track: `invalid`.
5. `style`, `position` or `animation` is present and is not a string: `invalid`.
6. `style` names no title style (14.3.2): `invalid`.
7. `position` is not one of the nine positions (12.6.2): `invalid`.
8. `animation` names no title animation (14.3.3): `invalid`.

**Effect.**

- The title is `{ id, type: "text", trackId, from, durationInFrames, label, text, color: "#ffffff", fontSize: 80 }`. `durationInFrames` is `duration` in frames, or three seconds at the project rate (section 3.3). `label` is the first 64 UTF-16 code units of `text`.
- Then, in this order, `style` writes its fields (14.3.2), `position` writes `verticalAlign` and `textAlign` (12.6.2), and `animation` writes `textMotion` (14.3.3). An empty string for any of the three is read as absent.
- **The track** is the first track in stored order that is a video track: the top layer.
- **The place.** When the title would share a frame with a clip on that track, it starts later. Go through the track's clips in order of `from`, with `cursor = from`: a clip that ends at or before `cursor` is passed; the search stops at a clip that starts at or after `cursor + durationInFrames`; any other clip sets `cursor` to its end. The title starts at `cursor` (`title.add/moves-past-taken-place`, `…/fits-in-a-gap`, `…/too-long-for-the-gap`).
- The title is appended to `timeline.items`.

**Draws:** the title's `id`.

#### 14.3.2 Title styles

A `style` (of `title.add` and of the `clip.update` patch) is one of:

- `Minimal` or `plain`: writes `fontWeight: "medium"` and nothing else.
- `Bold` or `bold`: writes `fontWeight: "bold"` and nothing else.
- a preset `id` of the catalogue's `titleStyles.presets`, or one of the aliases `Serif` (`quote`), `Outline` (`outline-pill`), `Lower third` (`lower-third`) and `Caption bar` (`badge`).

A preset writes every field of its `fields` in the catalogue, and `fontSize`:

```text
step     = clamp( round( canvas height × heightFactor ), min, max )      heightFactor, min, max: titleStyles.sizes[fontSize.size]
fontSize = round( step × fontSize.multiplier )                           round: nearest, halves towards positive infinity
```

computed in doubles. The canvas height is the project's (`metadata.height`). A preset also **removes** `backgroundColor`, `textShadow` and `stroke` from the title when its `fields` do not have them. So a preset replaces the look of an earlier preset whole, while `Minimal` and `Bold` change the weight and leave the rest (`clip.update/style-replaces-style`, `…/style-bold-keeps-preset-fields`). A later change of the canvas does not resize a title.

`text` and `label` are not changed by a style. In `clip.update` an empty `style` is refused (`invalid`); `title.add` reads it as absent (`title.add/empty-style-is-ignored`).

#### 14.3.3 Title animations

An `animation` is an alias of the catalogue's `titleAnimations.aliases`, which names an `in` and sometimes an `out` preset (`Fade`, `Rise`, `Typewriter`, `Slide`), or the `id` of an `in` preset of `textMotion`, which gives an `in` slot alone.

It writes the title's `textMotion` **whole**: each slot is the preset's entry in `textMotion.defaults`, plus `presetId` and `seed: 0`. A `loop` slot the title had is removed (`clip.update/animation-replaces-motion`). These defaults are the presets' own; `text.setMotion` has its own rules for the values it stores (13.7.1). In `clip.update` an empty `animation` is refused (`invalid`); `title.add` reads it as absent.

### 14.4 Published controls

A group can publish **controls**: named values of its clips that each of its composition clips may override.

#### 14.4.1 `composition.setPublishedControls`

Sets the controls a group publishes. Payload: `compositionId`, `controls`: a list of `{ id, name, targetItemId, property, defaultValue }`.

| `property`          | The target must be                                | Kind    |
| ------------------- | ------------------------------------------------- | ------- |
| `text.text`         | A title without `textSpans`.                      | `text`  |
| `text.color`        | A title without `textSpans`.                      | `color` |
| `shape.fillColor`   | A shape whose `fillType` is not `linear`.         | `color` |
| `shape.strokeColor` | A shape with `strokeEnabled` and a `strokeColor`. | `color` |

**Refusals, in order**

1. `compositionId` is missing or names no composition: `invalid`.
2. The composition is not a group (`composite-2d`): `invalid`.
3. `controls` is not an array, or one of its entries is not an object: `invalid`.
4. A control has no `name` (a string that is not blank), its `id` is a blank string, its `targetItemId` names no clip **of the composition**, its `property` is not in the table or does not fit the target, its `id` repeats an earlier control's, or it drives the same property of the same clip as an earlier one: `invalid`.

**Effect.** The composition's `compositionControls` becomes `{ version: 1, controls }`, with each control `{ id, name, targetItemId, property, kind, defaultValue }`:

- `id` is the one sent, or a drawn one when it is absent or empty. `id`, `name` and `targetItemId` are stored with surrounding white space removed.
- `kind` follows the property. A `kind` in the payload is ignored, as is every other field.
- `defaultValue` is the string sent, or else the target's present value of that property.

An empty list removes `compositionControls`. Clips are not changed.

**Draws:** one id for each control sent without one, in list order.

#### 14.4.2 `composition.setControlOverrides`

Sets the control values of one composition clip. Payload: `compositionClipId`, `overrides`: an object from control `id` to a string.

**Refusals, in order**

1. `compositionClipId` is missing or names no clip: `invalid`.
2. The clip is not a composition clip: `invalid`.
3. `overrides` is not an object (an array is not one): `invalid`.
4. For each key in turn: it is not the `id` of a control its composition publishes; its value is not a string, or is longer than 2000 UTF-16 code units; or the control is a `color` and the value, with surrounding white space removed, is not a colour (below): `invalid`.

A **colour** is `#` and 3, 4, 6 or 8 hex digits, or `rgb(…)`, `rgba(…)`, `hsl(…)` or `hsla(…)` whose contents are digits, `.`, `,`, `%`, `/`, `+`, `-` and white space. Letter case does not matter.

**Effect.** The clip's `compositionControlOverrides` becomes `overrides`, exactly as sent (a colour keeps its white space). An empty object removes the field. The composition and its clips are not changed: the override is applied when the clip is drawn.

**Draws:** none.

### 14.5 Carrying frames to another rate

A rate change under `keep-time` (14.6) carries every frame number of a timeline from the old rate to the new one, so that each clip keeps its time in seconds.

#### 14.5.1 The rounding

With the old rate `a` and the new rate `b` as exact fractions (the stored `fps` number read as in section 3.2, step 2), a frame count `n` becomes:

```text
carry(n) = sign(n) × floor( (2 · |n| · b.num · a.den + b.den · a.num) / (2 · b.den · a.num) )
```

in exact integers: the nearest frame to `n × b / a`, with exact halves **away from zero**. This is not the rule of section 3.3, which rounds a payload time to the nearest frame with halves towards positive infinity for both signs. The two agree for every count that is not negative. They differ for a negative half: `carry(−3)` from 30 to 25 is `−3`, where the rule of 3.3 would give `−2`. Few stored counts can be negative (a modifier's `phaseFrames`, a text motion's `offsetFrames`), but the rule is the same for all. `vectors.retime` in the fixtures lists worked cases: `frame`, `from`, `to` and `scaled`.

**Native rule:** use `carry` for every stored frame count a retime moves, and the rule of 3.3 for every payload time. After a rate change, later envelopes of the batch convert their payload times at the new rate (7.2).

#### 14.5.2 What is carried

For the main timeline, or for one composition, with its clips, transitions, keyframes and markers:

| Value                                                           | Becomes                                                                                         |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| A clip's `from`                                                 | `carry(from)`.                                                                                  |
| A clip's `durationInFrames`                                     | `max(1, carry(from + durationInFrames) − carry(from))`. The **end** is carried, not the length. |
| `phaseFrames` of each modifier                                  | `carry`.                                                                                        |
| `durationFrames` of each text motion slot                       | `max(1, carry)`.                                                                                |
| `staggerFrames`, and `offsetFrames` when present                | `carry`.                                                                                        |
| A transition's `durationInFrames`                               | `max(1, carry)`.                                                                                |
| A keyframe's `frame`                                            | `carry`, with the collision rule below.                                                         |
| `timeOffsetFrames` of a property link (`propertyLinks`, 13.2.4) | `carry`.                                                                                        |
| A marker's `frame`, `inPoint`, `outPoint`                       | `carry`.                                                                                        |
| `timeline.currentFrame`                                         | `carry`. It is the one view field a command changes.                                            |
| A composition's `durationInFrames`                              | `max(1, carry)`.                                                                                |

**Source frames stay.** A clip's `sourceStart`, `sourceEnd`, `sourceDuration`, `sourceFps` and `speed` are counted in the source's own frames and do not change, with two exceptions:

- A clip that has a source field (`sourceStart`, `sourceEnd`, `sourceDuration`, `trimStart`, `trimEnd`, `offset`) but no `sourceFps` gets `sourceFps` = the old rate. Composition clips and sound clips are excepted.
- A clip with a `sourceEnd` whose new length reads more source than its window holds has its window extended. With `need = round((new length / new fps) × sourceFps × speed)` in doubles (halves up; an absent `speed` is 1, an absent `sourceStart` is `trimStart` or 0): when `need > sourceEnd − sourceStart`, `sourceEnd` becomes `max(sourceEnd, min(sourceStart + need, sourceDuration))`, the `min` dropped when the clip has no `sourceDuration`. Composition clips and sound clips are excepted.

**Keyframes that collide.** The keyframes of a group are taken in frame order. One whose carried frame equals the carried frame of the last one kept is **dropped**, unless it is the last keyframe of the group, in which case it **replaces** the one kept. This differs from the rule of `clip.setSpeed` (13.2.7), where the later keyframe always wins. Fixture `sequence.setSettings/keep-time-to-25`.

**Reversed clips, motion layers and audio pulses** follow rules this protocol does not specify. **Native rule:** do not retime a timeline that holds one.

#### 14.5.3 Clips that land on each other

Carrying two ends separately can make a clip one frame longer than the space before the next clip. After the carry, clips are moved later until none collides. The procedure works with the clips' positions **before** the carry (`old`) and after (`new`), and a shift per clip that starts at 0:

1. **Find a collision.** Take the tracks in the order they first appear in the clip list, and on each track the clips in order of old `from` (ties in list order). Keep a **previous** clip. A clip **collides** when it did not overlap the previous clip before (`old from ≥ previous old end`) and now starts before the previous clip's new end (`new from + shift < previous new end + its shift`). The collision is by `previous new end − (new from + shift)` frames. Otherwise the clip becomes the previous clip, unless it lay wholly inside the previous clip before (`old end < previous old end`).
2. With no collision, each clip's `from` is `new from + shift`, and the procedure ends.
3. **What moves.** Start from the colliding clip. When its track is sync-enabled (12.2.3), also start from every clip on another sync-enabled track with the same old `from`. From each start, take its **run**: the clip and the clips after it on its track, as long as each began at or before the furthest old end reached so far. Every clip of a run brings the members of its `linkedGroupId`, each with its own run. If the clip it collided with is among them, keep only the clips whose old `from` is not before the colliding clip's.
4. Add the collision's frames to the shift of every clip that moves, and go back to step 1.

The fixtures cover it (`sequence.setSettings/keep-time-linked-chain`, `…/keep-time-busy-timeline`, `…/keep-time-to-24`).

### 14.6 Settings

#### 14.6.1 `sequence.setSettings`

Sets the canvas and the rate of the main timeline or of one composition. Payload: `sequenceId`, and any of `fps`, `width`, `height`, with an optional `timing`.

`sequenceId` is `main` for the main timeline, whose canvas and rate are the project's `metadata`, or the `id` of a composition.

**Refusals, in order**

1. `sequenceId` is missing: `invalid`.
2. `fps` is present and is not a project rate: `invalid`. A project rate is a rational with a positive numerator that equals one of the catalogue's `project.rates` (24, 25, 30, 50, 60, 120, 240) or `project.ntscRates` (24000/1001, 30000/1001, 60000/1001, 120000/1001). The engine reads a pair that is not reduced; the server refuses one (3.1).
3. `width` is present and is not a whole number from 320 to 7680, or `height` is present and is not a whole number from 240 to 4320: `invalid`. Odd sizes are accepted.
4. None of `fps`, `width` and `height` is present: `invalid`.
5. `timing` is present and is neither `keep-time` nor `keep-frames`: `invalid`.
6. `sequenceId` is not `main` and names no composition: `invalid`.
7. The rate changes, the timeline **has content**, and `timing` is absent: `invalid`.
8. A composition's rate changes with `keep-frames` while a clip of the project shows it: `invalid`.

The rate **changes** when the new rate is not the same exact fraction as the stored one. A timeline **has content** when it has a clip, a marker, an in point or an out point. A composition also needs a `timing` when a clip of the project shows it, even when it is empty.

**Effect on the main timeline.**

- `width` and `height` are written to `metadata`. Clips keep their transforms, and titles their font size.
- `fps` is written as `metadata.frameRate` (the exact pair) and `metadata.fps` (its float, 3.2).
- With a rate change and `keep-time`, when the main timeline has content, that content is carried (14.5), `timeline.currentFrame` included. The compositions are **not**: each keeps its own rate, and the composition clips that show one keep their source windows.
- With `keep-frames`, no frame number changes: everything plays faster or slower.
- In and out points are then clamped as on load (12.2.7), at the new rate.

**Effect on a composition.**

- `width`, `height` and `fps` are written on the composition. Its composition clips keep `compositionWidth` and `compositionHeight`.
- With a rate change and `keep-time`, the composition's content is carried (14.5), its `durationInFrames` included. Then every clip of the project that shows it, on the main timeline and inside any composition, has `sourceStart`, `sourceEnd`, `sourceDuration`, `trimStart`, `trimEnd` and `offset` carried, where present, and `sourceFps` set to the new rate where present. Its place and length on its own timeline do not change.

A `timing` with no rate change is ignored. **Draws:** none.

**Implementation-defined.**

- `240` is accepted, but loading reads a rate above 120 as 120 and retimes nothing. The result is not in normal form (`sequence.setSettings/rate-240-is-not-kept`, marked `outsideNormalForm`). **Native rule:** refuse a rate above 120.
- Changing the canvas does not move, scale or re-fit any clip. **Native rule:** reproduce it.

#### 14.6.2 `project.applyTemplate`

Sets the project's canvas and rate from a template. Payload: `templateId`, optional `timing`.

**Refusals, in order**

1. `templateId` is missing or is not the `id` of one of the catalogue's `project.templates`: `invalid`.
2. `timing` is present and is neither `keep-time` nor `keep-frames`: `invalid`.
3. The template's rate differs from the project's, the main timeline has content, and `timing` is absent: `invalid`.

**Effect.** As `sequence.setSettings` on `main` with the template's `fps`, `width` and `height`. Nothing else is written. All six templates are 30 frames per second at this revision. **Draws:** none.

### 14.7 `project.setMasterAudio`

Sets the persisted project master bus. Payload: `gainDb`, `muted` and/or `gainEnvelope`.
The optional envelope is an array of at most 4096 `{ id, at, gainDb }` points.
`at` is a nonnegative rational time admitted on an exact project frame. IDs are
nonempty strings of at most 128 characters; IDs and normalized frame times must
be unique. Points are stored in ascending frame order as `{ id, frame, gainDb }`.
Only linear interpolation in finite decibels from -60 to 12 is admitted; extra
fields/easing are refused. A nonempty curve overrides static gain, with the first
and last values held outside its endpoints. An omitted curve preserves it; an
empty curve clears it to static fallback. Master mute preserves the curve.

The curve is project-global: the same point frames apply in every independently
opened/exported root sequence's own frame domain. Nested samples receive the
outer root master once. A standalone sequence starts at its own frame zero.
Main project rate/template keep-time retimes the authored point frames with the
existing exact frame-ratio rounding rule and refuses collapsed point times;
keep-frames preserves them. Changing a different root's rate preserves the global
point frames. Device monitor volume never participates in exports.
Preview gain is evaluated by a once-only root AudioWorklet for each output sample,
from an immutable root/context/generation epoch. For audio time `t`, anchor time
`a`, anchor frame `F`, exact cadence `num/den` and signed rate `r`, the root frame
is `F + (t-a)*r*num/den`. A loop with inclusive bounds `L..U` uses
`L + positiveModulo(frame-L, U-L+1)`. Every admitted input channel receives the
same master gain; mute is independent. Whole epoch replacement is acknowledged;
loading, failed and unacknowledged root stages are silent. Retired roots and
contexts disconnect. Gain does not need animation-frame messages to repeat loops.
Source playback/restart continuity and browser audible behavior remain separate
qualification gates; gain authority alone does not certify them. Export PCM uses
absolute root sample time, including the selected range's root frame origin.
Encoded packet passthrough and original-byte smart copy refuse an active curve.

The monitor/device `volume` and `muted` controls are separate transient playback
state and never change through this command.

**Refusals, in order**

1. A payload key is not `gainDb`, `muted`, `gainEnvelope` or `ducking`: `invalid`.
2. `gainDb` is present and is not a finite number from -60 to 12 dB: `invalid`.
3. `muted` is present and is not a boolean: `invalid`.
4. `ducking` is present and is not a boolean: `invalid`. Either boolean is
   refused as `not-implemented`: the engine has no project-wide ducking switch.
   Per-clip sidechain settings are preserved.
5. A supplied envelope violates the point/count/time/ID/gain rules above: `invalid`.
6. None of `gainDb`, `muted` or `gainEnvelope` is present: `invalid`.

**Effect.** Write a supplied `gainDb` to `timeline.masterBusDb`, and a supplied
`muted` to `timeline.masterBusMuted`. An omitted field keeps its value.
Hydration initializes gain from the incoming timeline, or 0 dB when absent,
even when the project has no saved tracks. Incoming bus EQ survives default-track
initialization; an absent timeline clears the previous project's EQ.
`busAudioEq`, tracks, clips, channel layouts and all other graph fields remain
unchanged. Preview and export consume these same persisted master fields.
Undo/redo use host graph history (section 9). No ids or timestamps are written.
A refusal records no graph and applies none of the batch. **Draws:** none.

The fixtures cover combined gain/mute, each field alone, both gain endpoints,
invalid payloads, unsupported ducking and an atomic rejected batch.

## 15. `captions.set` (FL-111)

**Payload:** `{ captions: Array<{ id?: string, start: Rational, end: Rational, text: string }> }`.
It replaces the captions of the main sequence. The bridge still requires the
`transcriptionWorker` capability, an editable session, the current lease and
revision. This command applies supplied text; it does not run an inference job.

**Admission (`invalid`).** Only `captions` is accepted at the payload level,
and only `id`, `start`, `end`, `text` on each non-null object. A supplied id is
a nonempty string, unique in this set. Occupied ids include main and all retained
composition items (4.1); an existing id may name only a main sequence text item
with `textRole: "caption"`. Text is nonblank and excludes
U+0000–U+0008, U+000B–U+000C, U+000E–U+001F and U+007F. Start and end are safe
integer rationals with positive denominators, start is nonnegative and end is
strictly later. Round each endpoint independently to frames using section 4;
the resulting duration must be at least one frame. Sum the UTF-8 byte lengths
of each compact JSON `{ id?, start: { num, den }, end: { num, den }, text }`;
the set must fit 4 MiB, matching inline subtitle import admission. The existing
whole-graph size limit still applies when saving. Sort cues stably by start
frame. Overlapping cues are supported; never shift a cue to remove an overlap.

**Effect.** Refuse as `failed` if a caption text item, subtitle segment, or
item with enabled `transcriptCaptions` that would change is on a locked track.
Remove main caption text items whose ids are absent and all main subtitle
segments. Removal cascades their keyframes and transitions, without expanding
to linked media. Disable main items' enabled `transcriptCaptions`, retaining
their cues and provenance. An empty list stops here; existing tracks remain.
Nested compositions and ordinary titles remain unchanged.

For each sorted cue, keep its existing caption track if the new interval does
not overlap any non-caption item or previously placed cue on it. Otherwise
use the first compatible visible, unlocked, non-group video track in ascending
order containing only old caption items or nothing, with no overlap against
already planned items. If none fits, create a classic video track as in 12.7.1,
with order one below `min(0, existing orders)`. This separate-track placement
keeps overlapping cue times unchanged when loading the graph.

A matching caption id retains styling, source metadata, keyframes and unknown
fields; write `from`, `durationInFrames`, `trackId`, `text`, and a label of the
first 64 UTF-16 code units. When text changes, clear `textSpans` and
`textLayoutDrafts` so stale styled content does not override it. New items have
`type: "text"`, `textRole: "caption"` and no invented `captionSource`. Use the
standard caption preset: Inter semibold normal, no underline, white, background
`rgba(0, 0, 0, 0.55)`, radius 4, centered/middle, line height 1.15, letter spacing
0, padding 12, shadow `{ offsetX: 0, offsetY: 2, blur: 6, color: "rgba(0, 0, 0, 0.6)" }`.
For canvas width W and height H, font size is `max(8, round(0.04H))`;
transform is `{ x: 0, y: round(0.36H), width: round(0.7W), height: round(0.16H), rotation: 0, opacity: 1 }`.

**Draws:** mint each needed track first, as `track-` plus the next UUID. A new
caption without an id draws the next UUID, retrying a collision with an
incoming explicit id or a preexisting item id anywhere in the graph. Other ids
are unchanged. No timestamp or model provenance is written. Host history makes the replacement
undoable (section 9); a refusal records no graph and applies none of the batch.

### 15.1 Producing captions (FL-348; Whisper on the server, owner decision 2026-10-09)

`captions.set` applies cues; it does not make them. The web editor can still make them in the browser, on the Whisper and Parakeet models listed by `GET /studio/resources` under the `transcript` producer. The server makes them with Whisper on the machine-learning service, as a job any client can ask for:

- **Submit.** `POST /studio/projects/{id}/transcriptions` with `{ clipId, language, destinationId }`. Owner only. `clipId` names a video or audio clip on the main timeline of the head revision; a reversed clip is refused. `language` is a BCP 47 tag (`en`, `pt-BR`) or `auto` to detect it. `destinationId` names an ML destination explicitly (never inferred), as the catalogue's `job.enqueueTranscription` does: this server's own ML container or a home-network worker that is allowed and serves the Studio AI workload (`transcriptionWorker` in `GET /ml-destinations/capabilities`). A Frameleaf Cloud destination is refused. The answer, `201`, is the job `{ id, status }`.
- **Follow.** The job is a media operation of kind `studio_transcription`, so Activity follows it: `GET /media-operations/{id}` gives `status` and `progress` (the share of the clip's audio transcribed so far), and `POST /media-operations/{id}/cancel` stops it. A worker that cannot transcribe (no Whisper runtime, or the model is not on its model source) fails the job with `errorCode: "studio_transcription_unavailable"` and no automatic retry.
- **What it reads and keeps.** The job reads the clip's source window (12.2.4) from the original: from `sourceStart` for the clip's timeline length times its speed. It extracts that audio as 16 kHz mono PCM, sends it only to the named destination, and deletes it once the job settles. Only the cues are kept, as the job's result.
- **Result.** `GET /studio/projects/{id}/transcriptions/{transcriptionId}` answers `{ id, projectId, clipId, revision, language, destinationId, status, progress, error, result }`. `result` is null until the job completes, then `{ language, languageProbability, model, cues: [{ start, end, text }], words: [{ start, end, text, cue }] }`. `start` and `end` are exact rationals in seconds on the sequence, already offset by the clip's `from` and divided by its speed: a time `t` seconds into the source window is `from / fps + t / speed`. Cues are clamped to the clip, at least one frame long once rounded as section 4 rounds them, and split at word boundaries to at most 84 characters and 7 seconds. `words` gives each word's timing and the index of its cue. The job never edits the graph: the client sends `cues` unchanged as the `captions.set` payload (they carry only `start`, `end` and `text`), so undo, history and the lease apply as usual. If the head revision moved on since the job's `revision`, the cue times still describe that revision's clip.

**The model.** The ML service serves the `transcribe` task (`POST /transcribe`, model `frameleaf-transcribe`) with faster-whisper on CTranslate2. `frameleaf-transcribe` is the worker's own choice: Whisper large-v3-turbo when it has a CUDA GPU and Whisper small otherwise, unless its administrator sets `MACHINE_LEARNING_TRANSCRIPTION_MODEL` to `whisper-large-v3-turbo` or `whisper-small`. Both are MIT-licensed OpenAI Whisper weights as CTranslate2 conversions, downloaded on first use from the model source (`frameleaf/whisper-large-v3-turbo` and `frameleaf/whisper-small` on `models.frameleaf.cloud` by default) and pinned by SHA-256. Its stream is newline-delimited JSON: one `info` line (`model`, `language`, `languageProbability`, `duration`), one `segment` line per segment (`start`, `end`, `text`, `words`) as it is decoded, then `done`, or `error`.

## 16. `lottie.update` (FL-105)

**Payload:** `{ clipId, colors?, text?, slots? }`. It updates an existing main
Lottie item. Missing clips and other item types are refused as `invalid`; a
locked owning track is refused as `failed`. No other payload fields are admitted.
At least one map must be supplied. Each must be a non-null JSON object, not an
array, with nonempty keys. Color values are exactly `#rrggbb` hex strings (either
letter case); text values are strings, including empty strings. Value slots
contain finite numbers or exactly two finite numbers `[x, y]`.

Each supplied map replaces the corresponding `colorOverrides`, `textOverrides`
or `slotOverrides` field. An empty map removes that field, matching the inspector
reset. Omitted maps retain their previous contents. Validate all maps before one
item update and one history entry. A rejected batch restores the original graph
and history; the input graph is never mutated. Reopen, idempotent replay, undo
and redo follow the existing rules in sections 7 and 9. There are no identity
or timestamp draws.

Keys address the existing renderer representation: ordinal colors (`c0`, etc.),
text layer indices (`"0"`, etc.) or color/text slots (`s:<id>`), and native value
slot ids. The command does not fetch animation data or infer which keys exist
inside it. The existing renderer ignores unaddressed keys; this command preserves
those supplied maps. It leaves source, animation/theme selection, timing,
transforms, media ownership, linked clips and other graph fields unchanged.
Theme selection is not part of this canonical payload. Actual animated pixels,
native slot rendering and bundle round-trip output require separate qualification.

## 17. Masks and relinking (FL-348)

Both commands change only the named main-timeline clips. They draw no ids, write no clock, and a refusal leaves the graph and history untouched. Fixtures are named `clip.setMask/<case>` and `clip.relink/<case>` (story FL-348). The web editor's own mask controls write exactly the fields of 17.1, and its drafts report each shape whose mask fields changed as one `clip.setMask` in the revision summary.

### 17.1 `clip.setMask`

**Payload:** `{ clipId, mask }`. A mask in this graph is a `shape` item with `isMask: true`: it masks the tracks below it. `mask` is `null` (remove the mask) or an object with any of:

| Field     | Type                        | Writes                                                                 |
| --------- | --------------------------- | ---------------------------------------------------------------------- |
| `type`    | `"clip"` or `"alpha"`       | `maskType`. `clip` is a hard edge, `alpha` a soft one.                 |
| `feather` | number, 0..100              | `maskFeather`, in pixels.                                              |
| `opacity` | number, 0..100              | `maskOpacity`, the matte strength in percent.                          |
| `invert`  | boolean                     | `maskInvert`.                                                          |
| `path`    | array of 3 to 1000 vertices | `pathVertices`. Only on a shape whose `shapeType` is `path` (the pen). |

A vertex is `{ position: [x, y], inHandle: [x, y], outHandle: [x, y], tangentMode? }`: finite numbers, positions normalised 0..1 to the shape's box and handles relative to the vertex. `tangentMode` is `corner`, `smooth`, `continuous` or `broken`. When it is absent, write `corner` if all four handle numbers are 0 and `smooth` otherwise, as loading does. Write each vertex with its four keys only.

**Refusals, in order**

1. A payload field other than `clipId` and `mask`: `invalid`.
2. `clipId` missing or empty; no such clip: `invalid`.
3. The clip is not a `shape`: `invalid`.
4. `mask` absent (send `null` to remove), or neither `null` nor a plain object: `invalid`.
5. The clip's track is locked: `failed`.
6. A `mask` field not in the table; then a bad `path` (not a path shape, wrong vertex count, a vertex that is not an object, has another key, a pair that is not two finite numbers, an unknown tangent mode); then `type`, `feather`, `opacity`, `invert` out of their types: `invalid`.

**Effect.**

- `mask: null` on a shape that is not a mask changes nothing. On a mask it writes `isMask: false` and removes `blendMode`, `maskType`, `maskFeather`, `maskOpacity`, `maskInvert` and `pathClosed`. Loading then gives a path shape `pathClosed: true` again (2.6).
- An object starts from the current values: on a mask, `maskType ?? "clip"`, `maskFeather ?? 10`, `maskOpacity ?? 100`, `maskInvert ?? false`; on a shape that is not yet a mask, `clip`, 0, 100 and `false`. Given fields replace them. When `type` changes and `feather` is not given, the feather becomes 0 for `clip`, and for `alpha` the current feather if it is above 0, else 10.
- It writes `isMask: true`, `blendMode: "normal"` and all four mask fields. A shape that was not a mask also gets `pathClosed: true`. A `path` replaces `pathVertices`. `mask: {}` turns a shape into a hard clip mask with the defaults.
- Nothing else changes: the shape's transform, keyframes, fill and stroke stay as they are. Size and place the mask with `clip.setTransform` (12.6.3).

**Not covered.** There is no command that creates a shape. A native client masks a shape that is already in the graph (a pen path, a rectangle or an ellipse made in the web editor).

### 17.2 `clip.relink`

**Payload:** `{ clipId, assetId }`. Points a placed library clip at another library asset, as the web editor's relink of a missing clip does.

**Targets.** The named clip and its synchronised linked clips (12.2.1) that hold the same `mediaId`. A clip on the same linked group that was trimmed apart keeps its media.

**Refusals, in order**

1. A payload field other than `clipId` and `assetId`: `invalid`.
2. `clipId` missing or no such clip; `assetId` missing: `invalid`.
3. The clip is not a `video`, `audio` or `image` with a `mediaId` (generated media, titles, shapes and compositions are refused): `invalid`.
4. `assetId` has no media record in the session (3.5): `invalid`. A record that is neither `image/*` nor `video/*`: `invalid`.
5. A target `image` needs an image, a `video` needs a video, and an `audio` needs a video whose record has `audioCodec`: `invalid`.
6. A target on a locked track: `failed`.
7. When the asset differs, a target whose source window does not fit the new asset (below): `failed`.

**Effect.** When `assetId` already is the clip's `mediaId`, nothing changes. Otherwise each target, in `timeline.items` order, gets:

- `mediaId: assetId` and `label` = the record's `fileName`; `thumbnailUrl` and `waveformData` are removed.
- On a `video` or `image` target, when the record's width and height are both above 0: `sourceWidth` and `sourceHeight`. The `transform` is not refitted.
- On a `video` or `audio` target, with `rate = round3(record.fps || project fps)` (round to three decimals, as `clip.add` does) and `previous = sourceFps ?? project fps`: `sourceFps = rate`, `sourceDuration = max(1, round(record.duration × rate))`, and the source window carried to the new rate. When `rate` equals `previous` the window is unchanged. Otherwise `sourceStart = round(sourceStart × rate / previous)` and `sourceEnd = round(sourceEnd × rate / previous)`, each computed in IEEE double precision in that order, with `round` as ECMAScript `Math.round`. The window must satisfy `sourceStart < sourceEnd <= sourceDuration`, or the batch is refused (rule 7).
- `from`, `durationInFrames`, `speed`, `trimStart`/`trimEnd`, links, effects and keyframes are unchanged. An `image` target keeps its source fields.

**Media records.** The record is the one 3.5 describes. The server's `GET /studio/assets/{id}/media-facts` gives a native client the exact frame rate and whether the original has an audio track (FL-348), so its records agree with the web host's probe.

### 17.3 `media.relink` (FL-105)

**Payload:** `{ mediaId, assetId }`. The replacement must be an admitted source supplied to the command runtime. On an isolated copy, change each matching reader in Main and every composition to that identity. Preserve clip ids, links, placement, duration, source ranges, transforms, selection and unrelated graph fields. Image readers need image bytes; Lottie readers need animation bytes with matching frame rate and valid existing segments; video readers need video; audio readers need audio or a video with an audio track. Refuse missing metadata, incompatible kinds, differing source frame rates, or a replacement too short for any existing source range as `invalid`; never clamp cuts. Update source dimensions and duration, and remove cached visual and audio URLs, thumbnail, waveform, transcript and reverse-conform fields. Legacy trim and offset bounds remain guarded. Admission never changes an existing import's checksum or owner.

The web host refuses canonical relink while the editor reports unsubmitted edits. Its portable Relink File and missing-media Restore controls capture the complete live graph, including pending edits, instead. Actual selected bytes are hashed: matching an admitted import checksum restores that immutable identity and its metadata; different bytes receive a new admitted identity, including equal name/size/mtime selections. The existing leased compare-and-swap save must acknowledge the complete graph before live source publication or success. The source admission itself remains externally non-undoable (`undoable: false`); graph history preserves earlier references and the editor's source bindings in Main, sequences and navigation stashes. Old shared caches and admitted imports remain intact.

Cancellation changes nothing. Admission, command or save failure keeps the previous live graph. An ambiguous save is reconciled by reading the current origin once, without retrying the rejected replacement. If the outcome cannot be established, guard editing until explicit reload. Fence project/account/mount transitions during every await, including A–B–A and unmount. Local CPU conformance verifies graph rules; browser render/save/reopen, network durability and worker output need separate qualification.

## 18. Rendering effects and transitions

This protocol says which effects and transitions a graph may name, and with which parameters (13.2.1). What they draw is specified in `studio/spec/`, the render spec, which is part of the native-app contract on the same terms as this page: a clean-room specification written by reading the engine, with no engine source text, versioned with the same engine pin.

| Path                              | What it is                                                                                                                                                                                                                     |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `studio/spec/README.md`           | The shared rules: coordinates, sampling, the SDR and linear HDR domains, alpha, the hash and noise functions, colour helpers, the effect clock, parameter sanitising, the transition progress curve and the transition routes. |
| `studio/spec/effects/<id>.md`     | One page per effect of the catalogue (54): parameters and their internal meaning, the per-pixel definition, edges, alpha, and SDR and HDR behaviour.                                                                           |
| `studio/spec/transitions/<id>.md` | One page per transition of the catalogue (44): parameters, progress curve, geometry and blend.                                                                                                                                 |
| `studio/spec/hdr.md`              | HDR and colour management (H1 to H17): the `colorManagement` record, when a project is HDR, the working space, PQ, HLG and SDR sources, the SDR tone map, HDR delivery and refusals.                                           |
| `studio/spec/index.json`          | Every id with its page, whether it is fully specified, what is not specifiable, and its golden counts.                                                                                                                         |
| `studio/spec/goldens/*.json`      | Small deterministic inputs rendered through the real engine, with measured tolerances, and the progress-curve table.                                                                                                           |

**Native rules.**

- A native client renders an effect or transition so that it passes every `pixel` and `edge` golden case of its id under the comparison rule of the render spec, and every `statistical` case by its mean bound.
- An HDR project renders only the 16 effects the render spec lists for linear HDR, and no transition. When a frame needs anything else, a native client refuses to render that frame, as the engine does, and does not substitute an SDR render.
- Where a page marks behaviour as not specifiable (platform font rasterisation of ASCII glyphs, for one), a native client draws its closest equivalent and must still pass the goldens that page names as binding.

**Drift.** `studio/tools/render-goldens.browser.mjs` renders every golden case through the prepared engine and fails when one leaves its tolerance; `--write` regenerates the goldens. Font-atlas ASCII cases check the actual platform atlas against an independent rasterization and compare the complete frame to a prose-derived CPU reference within the same tolerance; stored Mac outputs remain platform snapshots. `studio/tools/render-goldens.test.mjs` checks coverage, the inputs, the progress curve and the clean-room rule without the engine. When an effect or transition changes, change its page and regenerate the goldens in the same change.
