# Studio graph protocol v1

This page specifies the Studio project graph. The native Frameleaf apps for iPad and Android tablets edit Studio projects from this page alone, and must produce exactly the graph, and the same `digest`, that the web Studio engine produces for the same edit.

It is a clean-room specification. It was written by reading the engine, and it describes behaviour only: it contains no engine source text. The engine is an adapted build of Freecut (MIT, see `studio/notices/freecut.txt`), pinned at revision `4d62e8082c5eb387a96275bcbd323d28f6e41a62`. The protocol is versioned with that pin. A change of engine revision is a new protocol version unless the conformance fixtures still pass unchanged.

Machine-readable files sit beside the other Studio contracts:

| File                                    | What it is                                                                                                                                           |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `studio/graph-schema-v1.json`           | JSON Schema (2020-12) of a graph in normal form, and of the media record an edit reads.                                                              |
| `studio/graph-conformance-v1.json`      | Conformance fixtures generated by running the real engine: inputs, expected graphs, digests, id draws, rejections, history scripts and test vectors. |
| `studio/frameleaf-studio-commands.json` | The command catalogue (ids, payload field types, scopes). This page gives the commands their graph meaning.                                          |

Where the engine's behaviour is accidental or inconsistent, this page says **implementation-defined** and gives the rule a native client must follow. It never invents semantics the engine does not have.

The page is delivered in four parts:

| Part | Story             | Covers                                                                          |
| ---- | ----------------- | ------------------------------------------------------------------------------- |
| 1    | FL-306 (NAPI-017) | The document, units, ids, ordering, digests, batches, undo/redo, fixtures.      |
| 2    | FL-307 (NAPI-018) | Mutation rules for clips, timeline edits, tracks and markers.                   |
| 3    | FL-308 (NAPI-019) | Effects, transitions, keyframes, easing, blends and parameter schemas.          |
| 4    | FL-309 (NAPI-020) | Compositions, titles, sequence and project settings, and full command coverage. |

## 1. Where the graph lives

A Studio project's head revision carries an **envelope** (OpenAPI `StudioProjectEnvelopeDto`):

| Field            | Value                                                                                        |
| ---------------- | -------------------------------------------------------------------------------------------- |
| `schemaVersion`  | `1`. The server accepts exactly this value.                                                  |
| `engine`         | `"freecut"`.                                                                                 |
| `engineRevision` | The pinned engine revision above, as a string.                                               |
| `graph`          | The graph this page specifies. The server stores it byte for byte and never reads inside it. |

A save (`StudioProjectSaveDto`) sends the envelope, the head it was built on (`expectedRevision`), a `requestKey`, and the `commands` that produced it (section 8). The server checks the envelope's four fields, the graph's size, and each command envelope against the catalogue. It does **not** re-run the engine, so a native client is trusted to produce the graph this page describes. The conformance fixtures are how a client proves that it does.

## 2. The graph document

A graph is one JSON object: Freecut's project document. `studio/graph-schema-v1.json` is its schema in normal form. This section names the parts and the rules the schema cannot express.

### 2.1 Top level (the project)

| Field                    | Type   | Notes                                                                                |
| ------------------------ | ------ | ------------------------------------------------------------------------------------ |
| `id`                     | string | The engine's project id. It is not the server's Studio project id and never changes. |
| `name`, `description`    | string | Display only.                                                                        |
| `createdAt`, `updatedAt` | number | Milliseconds. Commands never change them (section 4.3).                              |
| `duration`               | number | Commands never change it.                                                            |
| `schemaVersion`          | `15`   | The engine's document version. See 2.6 for older values.                             |
| `metadata`               | object | Canvas and frame rate (2.2).                                                         |
| `timeline`               | object | The main timeline (2.3). Absent only on a graph that has never been opened.          |
| anything else            | any    | Preserved unchanged by every command (2.5).                                          |

### 2.2 `metadata`

| Field             | Type           | Notes                                                                                                                             |
| ----------------- | -------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `width`, `height` | integer        | Canvas size in pixels.                                                                                                            |
| `fps`             | number         | The engine's frame rate as a float: exactly `frameRate.num / frameRate.den`.                                                      |
| `frameRate`       | `{ num, den }` | The exact frame rate (section 3). Always present in normal form.                                                                  |
| `backgroundColor` | `#rrggbb`      | Optional.                                                                                                                         |
| `colorManagement` | object         | Optional. Absent means an SDR project. Its contents are owned by the managed-colour work (FL-97) and are opaque to this protocol. |

### 2.3 `timeline`

| Field                                         | Type           | Notes                                                                           |
| --------------------------------------------- | -------------- | ------------------------------------------------------------------------------- |
| `tracks`                                      | array of track | In stored order; compositing order comes from each track's `order` (section 5). |
| `items`                                       | array of item  | Every clip of the main timeline, on every track (2.4).                          |
| `masterBusDb`                                 | number         | Project master gain in dB. `0` by default.                                      |
| `masterBusMuted`                              | boolean        | `false` by default.                                                             |
| `busAudioEq`                                  | object         | Optional.                                                                       |
| `currentFrame`, `zoomLevel`, `scrollPosition` | number         | View state the engine writes back as it read it. Commands do not change them.   |
| `inPoint`, `outPoint`                         | integer frame  | Optional.                                                                       |
| `markers`                                     | array          | Present only when non-empty.                                                    |
| `transitions`                                 | array          | Present only when non-empty.                                                    |
| `keyframes`                                   | array          | Present only when non-empty. One entry per animated item.                       |
| `compositions`                                | array          | Present only when non-empty. Sub-sequences and Compose groups (part 4).         |
| `topLevelSequenceIds`                         | array of id    | Present only when non-empty. Composition ids shown as timeline tabs.            |

The timeline object is closed: the engine rebuilds it from its stores, so a field not listed here is **dropped** on the next edit. Native clients must not add timeline fields.

**Track.** `id`, `name`, `kind` (`video` or `audio`), `height`, `locked`, `syncLock`, `visible`, `muted`, `solo`, `volume` (track gain in dB, −60 to 12), `order`, and `items`, which is always an empty array in a stored graph (items live in `timeline.items`). In normal form `height` is always `100`: it is a local view preference that the engine resets on load. Optional fields: `audioEq`, `color`, `parentTrackId`, `isGroup`, `isCollapsed`.

**Marker.** `{ id, frame, color }`, plus `label` only when it is non-empty. A marker added without a colour gets `#3B82F6`.

### 2.4 Items

Every item has `id`, `trackId`, `from` (first frame, integer, at least 0), `durationInFrames` (integer, at least 1), `label` and `type`. The types are:

| `type`               | Required beyond the common fields                        | Notes                                                                                       |
| -------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `video`              | `sourceStart`, `sourceEnd`, `sourceFps`, `mediaId`       | Library media. `src` is stored as `""`.                                                     |
| `audio`              | `sourceStart`, `sourceEnd`, `sourceFps`, `mediaId`       | A video's linked sound, or audio media.                                                     |
| `image`              | `mediaId`                                                | A still.                                                                                    |
| `text`               | `text`, `color`                                          | A title or caption.                                                                         |
| `shape`              | `shapeType`                                              |                                                                                             |
| `composition`        | `compositionId`, `compositionWidth`, `compositionHeight` | An instance of a composition (part 4).                                                      |
| `adjustment`         |                                                          | Applies its effects to the tracks above it.                                                 |
| `controller`         | `controllerKind: "null"`, `transform`                    | A null object.                                                                              |
| `lottie`, `subtitle` |                                                          | Produced only by editor features outside this protocol's commands. Preserve them unchanged. |

Source fields of a media clip are integer frames counted at `sourceFps`, the source's own rate, not the project's (section 3.4): `sourceStart`, `sourceEnd` and `sourceDuration`. `trimStart` and `trimEnd` are legacy counters. They are written as `0` when a clip is placed and must be preserved as found.

Common optional fields: `originId` (lineage shared by the parts of a split clip), `linkedGroupId` (shared by linked audio and video), `transform`, `crop`, `cornerPin`, `effects`, `blendMode`, `volume`, fades, audio EQ fields, `speed`, `motionModifiers`, `motionLayers` and `transformParent`. Parts 2 to 4 specify the commands that write them. The schema lists their types and ranges.

`generatedId` replaces `mediaId` on an item that shows Frameleaf-generated media (for example a reversed conform). Such an item never carries `mediaId`, `src`, `audioSrc`, `thumbnailUrl`, `waveformData` or any `reverseConform*` field in a stored graph.

### 2.5 Unknown fields

- Fields of the project object and of items that this page does not know survive every command unchanged. A native client must carry them through without reordering or rewriting them.
- Unknown fields of the `timeline` object are dropped (2.3). Treat the timeline as closed.
- Key order inside objects does not matter. Array order does (section 6).

Fixture `normal-form/unknown-fields` shows both cases.

### 2.6 Normal form

The engine does not apply a command to the stored graph directly. It loads the graph, normalising it, applies the command, then serialises its state back. Every graph the engine writes is therefore in **normal form**, and normal form is a fixed point: applying an empty batch to it returns it byte for byte. Every applied fixture records this as `fixedPoint: true`.

Loading normalises as follows:

- `schemaVersion` below 15 is migrated to 15.
- `metadata.frameRate` is written from `fps` when absent (section 3.2).
- Each track gets `height: 100`, and `syncLock: true`, `volume: 0`, `locked`, `visible`, `muted` and `solo` (false) when absent. `volume` is clamped to −60..12. `kind` other than `video`/`audio` is removed. Layer-group tracks (`isGroup`) are flattened away.
- Each item's `from` is rounded to a whole frame (at least 0) and `durationInFrames` to a whole frame (at least 1).
- `speed` is clamped to 0.1..10, `volume` to −60..12, and fades to at least 0.
- `transform.rotation` is reduced to 0..360, `transform.opacity` is clamped to 0..1, and `transform.cornerRadius` to at least 0.
- Overlapping items on one track are repaired by pushing the later one to the end of the earlier one, unless a transition joins them.
- Empty `transitions`, `keyframes` and `markers` arrays are removed.

Fixture `normal-form/normalises-a-hand-written-graph` shows each rule.

**Native rule.** A native client edits only graphs in normal form, which is every graph the web engine or a conforming native client has saved. It must not write a graph that is not in normal form. If it receives a graph whose `schemaVersion` is not `15`, or which lacks `metadata.frameRate`, it must open it read-only and ask the person to open it once on the web. Version migrations are implementation-defined, and this protocol does not specify them.

## 3. Time, duration and rate

### 3.1 Two representations

- **Command payloads** carry exact rational seconds: `{ "num": integer, "den": integer }`, with `den > 0`. The catalogue types `time`, `duration` and `rate` are all this shape. A `time` is an instant on the sequence, a `duration` is a length or a signed delta, and a `rate` is frames per second or a speed factor.
- **The graph** stores integer frames at the project rate (`from`, `durationInFrames`, keyframe `frame`, marker `frame`, transition `durationInFrames`), and integer source frames at the clip's `sourceFps`.

Rationals sent to the server must be **reduced**: the greatest common divisor of `num` and `den` is 1, so zero is `{ "num": 0, "den": 1 }`. Both must be safe integers (magnitude below 2^53). The engine accepts unreduced pairs, but the server refuses them, so a native client always reduces.

### 3.2 The project rate

The exact project rate is `metadata.frameRate`. The engine reads it from `metadata` as follows:

1. If `frameRate` is present and `frameRate.num / frameRate.den` equals `fps` (within 1e-9), `frameRate` is the rate.
2. Otherwise it reads `fps`. An integer is itself. A decimal within 1e-9 of `n/1001`, or equal to `n/1001` rounded to three decimals, is `n/1001`, for `n` in 24000, 30000, 48000, 60000 and 120000 (23.976, 29.97, 47.952, 59.94 and 119.88). Any other value has no exact reading, and every command on such a graph is refused (`invalid`, "The project frame rate has no exact reading").

On output the engine always writes both: `frameRate` as the exact pair and `fps` as the float `num / den` (for example `29.97002997002997`). Fixture `normal-form/legacy-decimal-rate` shows a legacy `29.97` graph gaining its pair.

### 3.3 Seconds to frames

A payload time `t = num/den` seconds becomes the frame nearest `t × rate`. Exact halves round towards positive infinity:

```text
frames = floor( (2 · num · rate.num + den · rate.den) / (2 · den · rate.den) )
```

Compute this with exact integers (64-bit is not always enough; use arbitrary precision). The result must be a safe integer, or the command is refused (`invalid`, "The time is out of range").

- A `time` field that rounds to a negative frame is refused ("must not be negative").
- A signed `duration` delta (`clip.push`, `clip.slide`, `clip.slip`) may be negative. Its halves also round towards positive infinity, so −½ frame becomes 0 and −1½ frames becomes −1. This is not the "away from zero" rounding of the host's playback helper. **Native rule:** use this formula for every payload conversion.
- A value that is not a rational with safe-integer `num` and `den` and positive `den` is refused ("must be an exact rational time"). This includes a JSON number.

`vectors.frames` in the fixtures lists worked cases, including NTSC rates and an overflow (`frames: null`).

### 3.4 Source frames

A media clip's `sourceStart`/`sourceEnd` count frames of the source at `sourceFps`. That is the media's own frame rate, copied from the media record when the clip is placed. Converting a source time to source frames uses the same formula with `sourceFps` read as in 3.2, step 2. A source whose rate has no exact reading cannot be edited by commands that convert source time.

### 3.5 The media record

Commands that place library media read a **media record** for each asset. This is the engine's view of the asset, and it is not stored in the graph. The fields that matter (schema `$defs/mediaRecord`):

| Field             | Meaning                                                                                             |
| ----------------- | --------------------------------------------------------------------------------------------------- |
| `id`              | The library asset id. It becomes the item's `mediaId`.                                              |
| `fileName`        | Becomes the item's `label`.                                                                         |
| `mimeType`        | `image/*` places an `image`, `video/*` a `video`. Anything else is refused.                         |
| `duration`        | Seconds.                                                                                            |
| `width`, `height` | Pixels. They become `sourceWidth`/`sourceHeight`.                                                   |
| `fps`             | The video's frame rate (0 for a still). It becomes `sourceFps`.                                     |
| `audioCodec`      | Present when the video has sound. Its presence alone decides whether a linked audio item is placed. |

A native client builds the record from the asset's metadata, as the web host does when it probes the asset. The fixtures give the records they used (`media.standard`). Two clients that disagree on a record produce different graphs. That is a media qualification issue, not a protocol one.

## 4. Ids

### 4.1 Which ids exist

All ids are strings, unique within their kind in the graph: items, tracks, transitions, keyframes, effects, markers, compositions, modifiers and published controls. Ids minted by commands have the UUID version 4 layout (8-4-4-4-12 lowercase hex). Ids already in a graph may have any non-empty form (`v1`, `main`), and they must never be rewritten.

### 4.2 Deterministic minting

The engine does not mint random ids while applying a command. Every id an envelope creates is drawn, in order, from a stream seeded by:

```text
seed = idempotencyKey + ":" + batchIndex
```

Here `batchIndex` is the envelope's zero-based position in the batch the engine was given. The web host gives the engine one envelope at a time, so in practice the index is `0` and the seed is `idempotencyKey + ":0"`. Retrying an envelope with the same key therefore mints the same ids, and two envelopes with the same key at different positions mint different ones (fixture `ids/same-key-different-index`).

The stream is a 32-bit generator seeded by a string hash. All arithmetic is on unsigned 32-bit integers. "Multiply" keeps the low 32 bits of the product, "rotl r" rotates left by r bits, and "xor" is bitwise.

1. **Hash the seed.** Let `h = 1779033703 xor L`, where `L` is the seed's length in UTF-16 code units. For each UTF-16 code unit `c` of the seed, in order, set `h = h xor c`, then `h = h × 3432918353`, then `h = rotl13(h)`.
2. **Draw four state words.** Each draw sets `h = (h xor (h >> 16)) × 2246822507`, then `h = (h xor (h >> 13)) × 3266489909`, then `h = h xor (h >> 16)`, and yields `h`. The first four draws are `a`, `b`, `c`, `d`.
3. **Generate.** Each output computes `t = a + b`, then sets `a = b xor (b >> 9)`, `b = c + (c << 3)`, `c = rotl21(c)`, `d = d + 1`, `t = t + d`, `c = c + t`, and yields `t`. All additions wrap modulo 2^32, and `>>` is a logical shift.
4. **Make an id.** Take 16 consecutive outputs and keep the top byte of each (`output >> 24`). That gives bytes 0 to 15. Set byte 6 to `(byte6 and 0x0f) or 0x40` and byte 8 to `(byte8 and 0x3f) or 0x80`. Write the bytes as lowercase hex, grouped 8-4-4-4-12 with hyphens.

Each id consumes 16 outputs. `vectors.uuids` in the fixtures gives the first ids for several seeds, including non-ASCII and long ones. Use it to test an implementation before anything else.

### 4.3 Which draw goes where

Each applied fixture records, for each envelope, its `draws`: draw number `n`, the id, and every graph path that holds it. Draws that a command makes but does not keep are listed with no paths. They still consume their 16 outputs, and a native client must skip them in the same order. Parts 2 to 4 give the draw order for each command in prose. The fixtures are authoritative where the two differ.

For example, `clip.add` of a video with sound (fixture `ids/clip-add-draws`) draws the shared `originId` first, then the shared `linkedGroupId`, then the video item's `id`, then the audio item's `id`.

The engine also fixes its clock to the envelope's `issuedAt` while it applies it. No field written by a command in this protocol depends on the clock. `createdAt`, `updatedAt` and `duration` on the project are left as they were (fixture `ids/issued-at-does-not-change-ids`).

## 5. Ordering and overlap

- **Array order is data.** The engine writes `timeline.items` in its own order: existing items keep their positions, and items a command creates are appended in the order the command creates them. Removed items leave no gap. Tracks are written in stored order. Each command's rules (parts 2 to 4) say where its new entries go, and the fixtures fix it exactly.
- **Compositing order** is the track `order` value, ascending: the lowest `order` is the top layer. `order` may be fractional (`track.add` at an index between two tracks takes the midpoint).
- **No overlap on a track.** Two items on one track never share a frame, unless a transition joins them (part 3). Commands that would create an overlap are refused (`failed`, "... would overlap ..."), or they place, trim or ripple so that none results, as each command's rules state. Loading a graph that has an overlap repairs it (2.6). A native client must never save one.
- **Linked items** share a `linkedGroupId`: normally a video and its sound. Unless a command says otherwise, an edit to one applies to every item in its linked group.
- **Locked tracks.** A command never changes an item on a track with `locked: true`. A command that would do so is refused (`failed`), as each command states.

## 6. Canonical serialisation and digests

Both digests are the lowercase hex SHA-256 of the UTF-8 bytes of a **canonical JSON** text.

Canonical JSON of a value:

- `null`, `true`, `false`: as JSON.
- A number: the shortest round-tripping decimal form, as ECMAScript's `Number.prototype.toString` writes it. `1e21` is written `1e+21`, `1e-7` is written `1e-7`, `-0` is written `0`, and `5e-324` stays `5e-324`. Integers below 1e21 have no exponent and no `.0`. Non-finite numbers never occur in a graph.
- A string: JSON-quoted as ECMAScript's `JSON.stringify` writes it. `"` and `\` are escaped, as are control characters below U+0020 (`\b \f \n \r \t`, others as `\u00XX` with lowercase hex). Every other character, including non-ASCII, U+007F and U+2028, is written as itself in UTF-8.
- An array: `[` + the elements' canonical JSON joined by `,` + `]`, in order.
- An object: `{` + members joined by `,` + `}`, where each member is the JSON-quoted key + `:` + the value's canonical JSON. Members are sorted by key in ascending UTF-16 code-unit order (not code-point order, and not locale order). Members whose value is absent are omitted.
- No whitespace anywhere.

`vectors.canonicalJson` in the fixtures gives the canonical text and its SHA-256 for edge cases: number forms, escapes, non-ASCII and astral keys, and nesting.

The two digests:

| Digest              | Over                                                                                                 | Where it appears                                                                                      |
| ------------------- | ---------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **Graph digest**    | The graph object                                                                                     | The engine's own result. Every fixture's `digest`.                                                    |
| **Envelope digest** | `{ "schemaVersion": 1, "engine": "freecut", "engineRevision": <pinned revision>, "graph": <graph> }` | The server's `digest` on a project, a revision and a save response. Every fixture's `envelopeDigest`. |

A native client computes the envelope digest of what it saves. If it equals the head's `digest`, the save is a no-op (`unchanged: true`). A retried save must carry the same `requestKey` and the same digest.

## 7. Commands and batches

### 7.1 The envelope

A command envelope is `{ id, payload, revision, idempotencyKey, issuedAt }`:

| Field            | Rule (server-checked)                                                                                                                                                                                          |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`             | A command id from the catalogue.                                                                                                                                                                               |
| `payload`        | An object. Every required field is present, every present field has its catalogue type, and no other field is allowed. Optional fields may be `null` to clear what they name (where a command's rules say so). |
| `revision`       | The head revision the client was editing (integer, at least 0). It must not be later than the save's `expectedRevision`.                                                                                       |
| `idempotencyKey` | 1 to 128 characters, unique among the commands of one save. It seeds the id stream (4.2).                                                                                                                      |
| `issuedAt`       | Milliseconds since the epoch, finite.                                                                                                                                                                          |

### 7.2 Applying a batch

The engine applies an ordered batch of envelopes atomically. Either every envelope applies, or the input graph is returned untouched with the **first** failing envelope's index and a reason:

| Reason            | Meaning                                                                                                            |
| ----------------- | ------------------------------------------------------------------------------------------------------------------ |
| `invalid`         | The payload contradicts the graph or the rules: a missing clip, a time outside a clip, a malformed value.          |
| `failed`          | The payload is well formed, but the edit cannot be made here: a locked track, an overlap, not enough source media. |
| `not-implemented` | The command is in the catalogue but the engine does not implement it (8.2).                                        |

The web host adds `stale-revision` (the graph changed while the engine worked) and, for undo/redo, its own refusals (section 9).

Later envelopes in a batch see the graph the earlier ones produced. That includes a rate change: after `sequence.setSettings` changes the project rate, later envelopes' times convert at the new rate (fixture `batch/rate-change-moves-later-times`).

The fixtures record a refusal's index, reason and the engine's English `detail`. A native client must match the index and reason. The detail text is informative only.

### 7.3 What a save carries

A save's `commands` are the envelopes that produced the graph, in order, up to 500. The server checks each one (7.1) and counts them into the revision summary. Only commands the catalogue marks `mutatesGraph` may appear. The `history.*` commands are not sent in a save (section 9).

## 9. Undo and redo

Undo and redo are not engine operations. The host answers them over graphs it has already stored.

- **Session history.** Each accepted engine command records the graph it replaced. `history.undo` restores the most recent replaced graph exactly, byte for byte, as the next draft. `history.redo` re-applies the graph that undo replaced. A new accepted command clears the redo stack. A refused command records nothing. The session keeps the 100 most recent replaced graphs and drops the oldest beyond that.
- **Past the session.** When the session history is empty and the head revision is above 1, `history.undo` restores the stored revision `head − 1` as a new revision. History is append-only, so a restore is itself a new revision whose `restoredFromRevision` names its source. Which graph `head − 1` holds depends on when autosave wrote revisions, so the result is **implementation-defined**. **Native rule:** a native client keeps its own session history with the same semantics and limit, and goes past it only through the server's revision restore, never by guessing a graph.
- **`toRevision`.** With `toRevision`, undo or redo restores that stored revision as a new head and clears the session history. A value below 1, or a revision that cannot be restored, is refused (`invalid`). The current head is a no-op.
- **Nothing to do.** With no session history, undo at revision 1 and redo with nothing undone are refused (`invalid`).
- **Saving.** A graph produced by undo or redo is saved like any other. Its `commands` are the envelopes still in effect, and the `history.*` envelopes themselves are not sent.

The `history` scripts in the fixtures replay sequences of commands, undos and redos through the host's own history. For each step they record the outcome, the graph digest, the earliest earlier state with the same digest (`sameAs`, where 0 is the base), and the undo and redo depths. They model each staged graph as one stored revision, so steps that undo past the session show the implementation-defined case above.

## 10. Conformance fixtures

`studio/graph-conformance-v1.json` is generated by running the real engine (`studio/adapters/web/test/graph-conformance.test.ts`). It is never edited by hand.

| Key             | Contents                                                                                           |
| --------------- | -------------------------------------------------------------------------------------------------- |
| `engine`        | The engine name and pinned revision the answers came from.                                         |
| `media`         | Named sets of media records (3.5).                                                                 |
| `seeds`         | Hand-written starting graphs, possibly not in normal form.                                         |
| `bases`         | `seed` + `setup` envelopes → the engine's `graph` and `digest`. Cases start from a base's `graph`. |
| `vectors`       | `canonicalJson`, `uuids` and `frames` test vectors.                                                |
| `cases`         | `base`, `media`, an `envelopes` batch → `expect`.                                                  |
| `history`       | `base` + `steps` (command, undo or redo) → one outcome per step (section 9).                       |
| `commandStatus` | Each graph-changing command's status and owning story.                                             |

A case's `expect` is one of:

- `{ "status": "applied", "graph", "digest", "envelopeDigest", "fixedPoint", "clockIndependent", "draws" }`: the graph is the full expected graph, and `draws` lists each envelope's id draws (4.3). `fixedPoint` records that an empty batch returns the graph unchanged (2.6). `clockIndependent` records that the same batch with a different `issuedAt` gives the same graph (4.3).
- `{ "status": "rejected", "index", "reason", "detail" }`.

**Running them natively.** For each case, load the base graph, apply the envelopes with the case's media records, and compare the result:

- An applied case must give the expected graph, compared by graph digest, and the expected ids.
- A rejected case must be refused at the same index with the same reason, leaving the graph untouched.

Run the vectors first: id generation and canonical JSON must be right before any graph can match.

**Drift.** Two checks keep this page and the engine together:

- The engine replay runs in the Studio engine workflow. It recomputes every answer, fails on any difference, and checks that a second run gives identical answers.
- `studio/tools/graph-protocol.test.mjs` runs in the Scripts unit tests on every pull request, without the engine. It re-derives every digest, id draw and rounding answer from an independent implementation of sections 3, 4 and 6, and validates every graph against the schema.

A change to the engine that alters any answer fails the first check. A hand edit of any answer fails the second.

## 11. Implementation-defined behaviour

| Behaviour                                                                                | Native rule                                                                    |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Version migrations of graphs below `schemaVersion` 15 (2.6).                             | Open read-only; ask the person to open the project on the web once.            |
| Unknown timeline fields are dropped (2.3).                                               | Never add timeline fields.                                                     |
| Undo past the session restores `head − 1`, whose content depends on autosave timing (9). | Keep a session history; go past it only through the server's revision restore. |
| Negative half-frame deltas round towards positive infinity (3.3).                        | Use the section 3.3 formula exactly.                                           |
| The engine accepts unreduced rationals; the server does not (3.1).                       | Always send reduced rationals.                                                 |
