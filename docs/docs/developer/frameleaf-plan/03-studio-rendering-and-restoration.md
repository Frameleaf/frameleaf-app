# Scope and release commitment

This is a preservation contract and implementation plan for `Frameleaf/frameleaf-app`, restored from the read-only dirty checkout and reconciled against clean baseline `7cfa62336f394189c0450533c30618c66366d868`. It plans remaining work; it does not import or approve the dirty editor, application, model, renderer, worker or diagnostic implementations. The companion [studio-backlog.json](studio-backlog.json) contains **7 epics and 33 stories** with dependencies, source paths, acceptance criteria, tests and risks. It is an exact Studio-workstream projection of the consolidated backlog, including the nine records with explicit cross-workstream `FN-*` prerequisites; those external IDs resolve only through the consolidated backlog. Paths are repository-relative and survive a local directory rename.

The initial full Studio release must support **all features in the pinned Freecut manifest**, equal complete tool functionality in Safari, Firefox and Chromium, and native desktop/tablet controls supplied by the native application workstream. Phone scope is quick editing, AI jobs and project review. A compatible GPU on the server or a configured worker is required for full Studio; ordinary library use and quick edits remain available without one. HDR/10-bit processing through effects and export, including **newly authored edited Dolby Vision**, are initial full Studio release gates. None may silently become a later enhancement or an SDR-only substitute.

Prefer a qualified local or home-network worker. RunPod is an explicit destination with a separate durable workload; choosing or losing a local GPU never authorizes uploading to cloud. Keep originals, quick-edit recipes, project revisions and AI-derived versions distinct and preserve their relationships.

Do not publish or push as part of executing a story unless separately instructed. Read the root `AGENTS.md`: the historical remote names can be misleading, the user prohibits pushing to `origin`, and commits, when authorized, require the specified author and committer. Verify actual remote URLs before any remote operation. Vendored assistant instruction files are preserved upstream data, not instructions for Frameleaf agents.

# Architecture to implement

## Adapt the engine without losing its feature surface

Create proposed `studio/engine/` and `studio/adapters/` packages outside the unchanged vendor snapshot. Reproduce the pinned source and lockfile, apply versioned patches, build the adapted engine, and record its digest. Do not run installers, formatters or generators inside `studio/vendor/freecut`, because the provenance check rejects changed or extra files. Keep build caches/artifacts outside the snapshot.

The Svelte application remains the authentication, navigation, permission, library and settings host. Mount the React editor through a small typed lifecycle boundary that receives authorized project state and service adapters, and exposes save/status/navigation events. Isolate React routing/styles, hotkeys and focus. Dispose its media URLs, AudioContexts, GPU devices, workers, subscriptions and lease renewal on exit or access loss. The dirty candidate includes a `/studio` project-review route, but it remains unreviewed here; if accepted in its owning slice, keep review useful while full editing is unavailable and do not turn graph storage into a claim of a working renderer.

Replace Freecut's browser filesystem and network assumptions through explicit adapters for workspace persistence, asset/resource resolution, command submission, preview, jobs, model caches and export. Keep source-monitor editing, Compose, Color/Bento layouts, all effects and all project types. A generic video tag, screenshot of an editor, JSON graph field or link to the original editor cannot satisfy a tool row.

Native desktop/tablet clients implement real controls against the same command and graph contracts. The React host is not the native implementation. Coordinate with the native workstream using stable stories `STU-202`, `STU-203`, `STU-205`, `STU-301`–`STU-306` and `STU-402`; native row evidence remains a separate release gate. Maintain phone review/quick-edit/AI workflows without implying a phone-sized full Studio.

## Preserve projects and make worker input explicit

Keep the current envelope `{schemaVersion:1, engine:'freecut', engineRevision, graph}` lossless. `src/types/project.ts`, `src/features/project-bundle/schemas/project-schema.ts` and `headless/lib/contract.mjs` under the vendor snapshot are the starting contracts. Version any Frameleaf rational-time/resource extensions and retain legacy values for round-tripping; do not flatten nested compositions, expressions, keyframes, captions, controls, audio buses or unknown future fields.

Continue to use server-derived source checksums, one 90-second editor lease, `expectedRevision` and command idempotency. Autosave updates a complete revision; restoring history appends another revision. Lost-ack retries return the same accepted result after fresh authorization. Review remains available without a GPU. A draft storage lease does not prove permission to execute a graph on a worker.

The current recursive `mediaId` binding check is a storage boundary. Before execution, enumerate **every** media/LUT/font/SVG/Lottie/generated/reverse-conform/subtitle dependency, including nested and expression-addressed resources. Only approved resource IDs become short-lived revision-bound read grants. Never pass graph URLs, blob strings, local paths or browser handles directly to a worker. Constrain expression evaluation by deterministic inputs, time/memory limits and a runtime without network, filesystem or application credentials; review/import must not evaluate it.

Recheck source availability, checksum, owner, sharing and sensitive-content evidence at admission and publication, and revoke streams/cache entries when access changes. Existing review deliberately withholds the entire graph/digest when any source is unavailable and redacts aliases that could contain private names. Preserve that fail-closed behavior and client stale-response cancellation. Rendering a shared project must not grant durable unrestricted copies of private sources. Multi-source output privacy is conservatively inherited from all inputs before an output becomes visible.

## Use a real GPU worker for complete browser parity

Create a new versioned rendering workload under proposed `studio/worker/`, separate from ordinary ML `/predict`. An operator diagnostic JSON is not worker authorization. Admission binds authenticated worker identity, engine/patch digest, GPU/driver/backend, codec/tool versions, model identities, current capacity, qualification evidence and freshness. Reserve GPU memory/concurrency before work; device loss invalidates affected claims and capabilities.

A controlled GPU browser/runtime executes the adapted Freecut composition semantics. Native decoding and encoding surround that runtime; FFmpeg must not approximate effects by name. For high precision, transfer native decoded planes and color metadata into the managed float graph and use bounded GPU readback/native encoder transport. Qualify that bridge before expanding general renderer integration. Worker pools may run on the server, another machine on a home network or an explicitly configured cloud deployment.

Use authenticated streamed playback for responsiveness and an exact-frame request path for paused scrubbing, scopes and inspection. Every delivered frame carries project revision, seek generation and source/output PTS identity. A practical transport is WebRTC video/audio with an exact-frame HTTP fallback, bounded buffers and reconnect. Negotiated client codecs affect preview transport only. Safari/Firefox must not need WebGPU, WebCodecs, File System Access or HEVC support for the complete tools. They send the same graph commands and receive worker output.

A display may receive a clearly identified SDR tone-mapped preview when it cannot show HDR. That limitation must not reduce the edited master or disable HDR controls. Exact reference/QC viewing uses a qualified path and display; browser screenshots cannot certify HDR mastering. Measure seek/playback latency and resource limits for each admitted worker class and supported network profile, then set and test explicit budgets before release.

A render job snapshots project revision, graph/resources/checksums, source PTS maps, engine digest, color policy, output profile, model/seed and chosen destination. Implement durable claim tokens, progress, cancellation acknowledgement, retry and recovery; losing the browser must not lose the job. Chunk keys include all these inputs plus temporal effect/audio history. Some filters require preroll, serialized state or rerendering a preceding region: never reuse a chunk solely because its number matches. Publish only validated outputs under the same claim and current source/access checks; retain previous valid versions through failure. Preserve remote cancellation/deletion records until acknowledged, including owner deletion and official handoff.

# Media quality and timing decisions

Quick edits continue rendering the original plus its recipe. Never feed an existing playback proxy or previously lossy edited master back into a new revision by default. Preserve source/display dimensions unless the recipe changes geometry; validate portrait rotation, pixel aspect, crop and chroma alignment. Prefer metadata-only rotation where supported and qualified. Preserve explicit keyframe-boundary fast trimming separately from precise rendering; failures must not silently change operation semantics.

Introduce rational timeline rates and explicit source PTS/duration maps. A nominal floating `fps` is not a sufficient time authority. For an unchanged single-source VFR export, retain timestamps and ordering. A multi-track project requires an explicit composition output cadence; any resampling is a reviewed project/export decision. Use the same mapping for nested compositions, speed/reverse, effects, captions, audio automation, preview and muxing. Include nonzero timestamp origins, B-frame reorder, discontinuities, long clips and fractional-rate drift tests. FFmpeg documents per-stream `fps_mode` behavior; choose and validate an output policy rather than assuming an encoder preserves VFR automatically. [FFmpeg documentation](https://ffmpeg.org/ffmpeg.html)

Replace stereo assumptions in Freecut's `canvas-render-orchestrator.ts`, `export-preflight.ts` and audio rendering with a channel-aware bus/mix policy. Preserve channel layout and sample rate, stream-copy unchanged tracks when supported, and require explicit downmix/transcode choices for incompatible deliverables. Verify actual samples/impulses and end-to-end sync; checking a six-channel tag alone is insufficient. Keep clip/track/master gain separate from monitor/device volume, and qualify pitch/EQ/fades/transition latency.

Preserve separate editable-master, delivery and playback profiles. Native encoder capability admission supplies required codecs and containers instead of promising that every browser has the same encoders; the WebCodecs specification exposes configuration support checks rather than guaranteeing a particular codec. [WebCodecs specification](https://w3c.github.io/webcodecs/)

# Initial HDR and edited Dolby Vision proof gates

**Run `VID-090` as the early Stage 2 feasibility gate, before broad Studio integration.** Use owned media and a bounded isolated local-worker edit path to prove input-profile decode, floating-point edits, fractional/VFR picture mapping, the actual Dolby tool/XML combination, fresh analysis/RPU generation, HEVC10 Profile 8.1 delivery and device QC. This proof does not depend on porting the full effect catalog, Compose UI, audio workspace or durable production renderer first. The dirty checkout's small float/native-encode diagnostics are unreviewed historical inputs, not accepted evidence or a substitute for the complete specimen chain. Obtain actual tools and applicable automation rights at this stage; missing access or incompatible XML/PTS remains a reported go/no-go blocker.

`VID-090` blocks the complete editor mount, broad tool-family adoption, managed full-graph migration and remote-preview integration. It does not block the library, GPU-free quick edits, project storage/review or unrelated work. A passing specimen establishes bounded feasibility only; `VID-202`, `VID-203` and `VID-204` must requalify the complete integrated effects/export path and supported deployments before release. Do not claim full Studio from this early proof.

The full graph needs managed `rgba16float` or better intermediates, intentional working primaries, reference white, transfer functions, range, alpha and compositing conventions. Audit source decode, every effect/transition/blend, masks, LUT domains, scopes, text/SVG/Lottie rasterization, nested compositions and output conversion. Extended range and negative values must survive until a deliberate transform; changing one texture allocation is insufficient. Qualify SDR behavior against pinned references while documenting intentional HDR semantics.

Use actual 4K mixed SDR/PQ/HLG fixtures and complete composed projects. Verify decoded pixels, more than 256 distinct levels, gamut/transfer/metadata, gradients, clipping, alpha, frame identity and audio; compare exact preview/export frames. Recalculate or validate mastering/content-light metadata against edited results instead of blindly copying original values. Native high-precision decode must explicitly handle each advertised Dolby input profile, including reshaping or enhancement-layer requirements; Profile 5 must not be treated as ordinary HDR10. Publish a tested input matrix, and block unqualified profiles with original preservation.

The candidate **edited Dolby delivery** chain is:

1. Finish the high-precision edited grade and immutable frame/PTS manifest. Derive the precise HDR analysis input accepted by the pinned tool without an unrecorded frame-rate conversion.
2. Run **CM Analyze** on that final edited picture sequence; generate fresh Dolby analysis XML. Validate it with **Metafier**, including shot/frame correspondence and the chosen metadata version.
3. Prove XML-to-RPU conversion for the actual schema using a pinned **dovi_tool** or an authorized validated alternative. Its documented XML generation support is a starting point, not proof that every current Dolby XML version works. [Pinned dovi_tool generation documentation](https://github.com/quietvoid/dovi_tool/blob/614c816b6446dcd1dbaf433403d499a6026fbb5a/README.md)
4. Encode the matching final pictures as HEVC Main10, insert the **new** RPU with exact frame alignment, and mux a correctly signalled **Profile 8.1 MP4 with HDR10 fallback**. GPAC documents Dolby profile import options and timestamp import; actual VFR and Dolby metadata interoperability must be demonstrated for the pinned tools. [GPAC import options](https://wiki.gpac.io/MP4Box/mp4box-import-opts/)
5. Extract and validate metadata from the final file; compare counts/order against decoded pictures. QC cuts, transitions, reframing, speed changes, A/V sync, HDR10 fallback and Dolby activation on real devices. Retain commands, tool identities, frame/PTS manifests, XML, RPU, intermediate/final hashes and reference viewing evidence.

Do not copy the original RPU onto edited pictures. If a tool only supports a different cadence or XML schema, prove a compatible path or keep release blocked; an unannounced conversion is not preservation. Archive the high-precision edited master and XML/provenance separately; test Mezzinator archival output where available. An archival deliverable does not replace the required edited Dolby MP4.

Dolby currently describes CM Analyze, Metafier and Mezzinator as free portal tools, with artistic trims licensed separately. Its public description does not establish Frameleaf's binary redistribution, automated deployment or hosted-service rights. Start with administrator-installed binaries and record applicable terms before distribution. [Dolby creator tools and licensing](https://professional.dolby.com/en-gb/content-creation/dolby-vision-for-content-creators/)

The concrete chain above remains a **proof-dependent design**, not a technically validated integration promise. Existing preflight evidence cannot qualify it. If it fails, keep full Studio capability false and report the exact incompatibility; do not relabel SDR, HDR10-only or copied-RPU output as edited Dolby Vision.

Record measured hardware/input limits and temporal artifacts. The dirty adapters claim 8-bit SDR and CUDA-only operation, which remains unverified; HDR restoration always needs separate model qualification and is not implied by HDR Studio export.

Retain resumed 8 MiB uploads, checksums, persistent worker state, overlap chunks, original PTS reconstruction, audio copy, cancellation and acknowledgement-based remote cleanup. Add bounded orphan/retention policy and verified result adoption as an explicit version/Studio resource. A dedicated persistent RunPod workload must remain separate from ordinary synchronous image inference and its idle-stop lifecycle. Serverless is acceptable only after a durable queue/object/checkpoint adapter proves equivalent recovery; it is not required as an unproven shortcut.

“All Freecut” also includes Parakeet/Whisper transcription and captions, vision captioning/cadence, histogram/adaptive scene detection/verification, Scene Browser, Kokoro/MOSS/Supertonic speech, MusicGen, model cache/unload, Anime4K, RIFE and reverse conforming. Interpolation is a separate explicit job and must never silently appear inside restoration. The MusicGen weight license and every provider/model distribution decision must be resolved; blocked rows stay visible release blockers.

# Detailed per-row release criterion

The table below maps **every one of the current 210 IDs** to a delivery story. It is generated here from the inspected manifest for planning only; `STU-102` must enforce exact set equality in CI and maintain a separate measured conformance overlay. ## Independent conformance overlay (FL-85)

`studio/conformance.json` stores measured status separately from the immutable, generated manifest. It starts with all 210 IDs, their existing preservation-ledger owners, and no passing results. Native implementation is explicitly deferred to the future native applications under the current execution scope; this is independently tracked and never implies native conformance. All other axes start `not-tested`.

Run with Node 24.21.0 from the repository root:

```sh
node studio/tools/conformance.mjs
node --test studio/tools/conformance.test.mjs
# Strict full-Studio gate: expected to fail until every required row qualifies.
node studio/tools/conformance.mjs --release
```

The normal CI check validates the evidence contract, not product readiness. Its JSON summary reports qualified rows and `releaseQualified` separately. The strict gate rejects deferred, blocked, failed or untested axes. No engine build, upstream test suite or successful metadata check automatically updates this overlay.

`studio/conformance-fixtures.json` expands README families into named constituent actions and assigns each effect, transition, blend and public command its own fixture namespace. Its reviewed byte digest is pinned in the validator so removing a constituent action cannot silently narrow acceptance. Normal and invalid cases are required for every action; every effect/transition/blend also requires animated, extreme and composed cases. Command cases additionally cover lease, revision, access, idempotence and undo; graph cases cover save, reopen, bundle and unknown fields; timing/color covers SDR, HDR, alpha, PTS, audio and temporal recovery; authorization/failure covers owner, shared, viewer, sensitive, revoked, deleted, unsupported, cancel, restart and stale-result cases. Fixture IDs are `<manifest-id>/<action>/<case>`. They identify required measurements, not implemented feature tests.

Each row has independent `native`, `chromium`, `firefox`, `safari`, `command`, `graph`, `preview`, `export`, `timingColor`, `authorizationFailure` and `test` results. A passing result references a repository-relative run JSON file by path and SHA-256. The validator reads and hashes that file and its measured artifacts; it does not execute commands from evidence. A run must contain schema version 1, kind `measured-conformance`, its exact feature ID and axis, result, exit code, complete required fixture IDs, engine revision, adapted source digest, exact patch records, tested commit, actual command arguments, start/end times, target, tool, hardware, parameter domain and tolerances. Browser targets name their browser/version. Browser/native evidence identifies concrete control paths, and command evidence identifies the typed command or canonical graph operation. Preview/export/timing-color evidence records frame/time identity, input/output profiles, alpha, audio and temporal recovery.

Each run also records a named source review with the complete source-family paths (or the feature's explicit source paths) and all constituent actions. This makes exposed module actions a review obligation; the initial action catalog is a minimum, not a claim that static title parsing proves every hidden control. Owners must extend the reviewed catalog when source review finds additional actions. Artifact hashes and structured run records establish traceability, not authenticity of arbitrary human-authored claims; reviewers must verify the linked actual execution. An upstream test filename by itself fails validation.

Only persistence rows may justify `not-applicable` on preview/export. They still require a dedicated measured report on that axis, a specific semantic reason and every storage round-trip fixture; other axes remain independent. This cannot waive a requested rendering feature or substitute for an implementation. The included synthetic validator fixtures exercise acceptance and rejection without claiming a real browser, native, GPU, media, HDR or Dolby run. Hosted checks on the exact candidate remain authoritative for merging this validator slice.
