---
title: Cloud backup keys
---

Cloud backup supports a server-generated key, your own key stored on the server, and your own key held only in memory. Keep the downloaded key file or recovery code separately from the server. The key is required for independent offline restore in every mode.

In **own-memory** mode, loading a key unlocks the application worker that receives the request. Other application workers request an encrypted copy when needed. A restarted worker can recover from another unlocked worker. After all application workers stop, load the key again. Turning cloud backup off clears keys held in memory on the participating workers; stored keys and backups remain available. You can load the key again to restore while scheduled backups are off.

Workers authenticate with the Ed25519 instance identity in `FRAMELEAF_IDENTITY_DIR/instance-key.pem`, or the existing `<media>/frameleaf/identity` default. Only trusted application workers should be able to read that private directory. Separate hosts belonging to the same installation need the same identity through private operator-managed mounts. Mount it read-only on workers that do not create or rotate the instance identity, and exclude it from ML and plugin containers. A database public key or the displayed backup fingerprint cannot authorize a recipient. A missing or unreadable identity prevents exchange and leaves work waiting for its key; correct the private mount and load the key again.

Key requests are signed, bound to the instance and bucket, and expire after 30 seconds. Replies are signed and encrypted for that request's ephemeral X25519 key using HKDF-SHA256 and AES-256-GCM. PostgreSQL notifications and attachment fallback rows contain encrypted replies, never plaintext backup keys or recovery codes. Recorded replies cannot be accepted as unsolicited unlocks or replayed into a restarted worker. A complete instance-identity rotation during exchange may require a new request; workers read the current private identity for each exchange.

The owned root buffer is overwritten on replacement, lock and shutdown. Active operations hold a separate copy, wiped when the operation finishes, so locking cannot change a key already in use. Shutdown lets active backup or restore work finish before clearing it. Ephemeral private-key references are released on acceptance, expiry and lock. JavaScript garbage collection and the host operating system control reclamation of cryptographic objects and request strings; the private host and its administrators remain trusted. Stored key modes, older SSE-C backups and the standalone recovery command keep their existing formats. Update and restart all application workers together; older key-exchange messages are rejected.
