# Managed library setup protocol

This additive protocol is for the native iOS and Android clients. Existing photo and sync endpoints retain their contracts. A server without Manager provisioning refuses the managed-setup API; clients continue their ordinary onboarding flow in that case. Manager's administrator session is never a photo account or mobile credential.

After authenticating a normal photo session, call `GET /api/server/library-setup`. `origin: new_import` identifies an imported library; other origins are `new_library` and `restored_library`. The server reports `awaiting-account`, `rescanning`, `verifying`, `needs-attention` and `complete` phases. External scans use the existing durable library scan engine. Managed uploads and external originals also require completed Library Care integrity scans. Pending sidecar, metadata, thumbnail and video work prevents completion. Findings require administrator review and a new verification run. The server persists its state and continues preparing in the background when Manager is unavailable.

While preparation runs, call `POST /api/server/library-setup/sync` with `{}`. The response is the existing authenticated session's NDJSON catalog stream. Apply its records to the local database and acknowledge them through the existing sync acknowledgement API. Honor `SyncResetV1`; repeat with `{ "reset": true }` when the existing sync protocol requires reset. Resume using the normal session checkpoints after interruption. Never reuse a different account's local catalog or checkpoints.

Once the server has completed its rescan and verification, a fully delivered stream appends `FrameleafSetupRevisionV1` with a `revision` and an opaque session-bound `receipt`. Do not log the receipt. Apply and acknowledge the final catalog stream, then cache the browsing previews for that catalog using existing authenticated asset requests. Original photos and videos are not part of the required catalog download.

When both local steps finish, call `POST /api/server/library-setup/finish` with `{ "revision": "…", "receipt": "…", "previewsReady": true }`. The server checks its final revision, the receipt, this session's persisted sync acknowledgement and the client's preview completion report. Another session cannot use the receipt. If the call succeeds and `canFinish` is true, enable **Finish setup** on the phone. Manager receives only aggregate completion, without the phone's user identity, cursor, receipt or media details, and enables its own finish control.

`previewsReady` is a report from the native client; it does not download or verify a phone's cache on the server's behalf. Each native client must implement durable background catalog work, cancellation/account-switch isolation, preview caching and resume on foreground before this flow can be qualified on real devices. Server/API checks alone are not mobile acceptance evidence.
