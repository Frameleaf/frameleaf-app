# Contributing to Frameleaf

We appreciate every contribution, and we're happy about every new contributor.

## Getting started

To get started quickly, follow the [development setup guide](https://help.frameleaf.ai/developer/setup). If you prefer, you can also use [Devcontainers](https://help.frameleaf.ai/developer/devcontainers).
The [developer documentation](https://help.frameleaf.ai/developer/architecture) covers Frameleaf's architecture, database migrations, the use of OpenAPI and more.

## General

Keep pull requests as focused as possible. A PR should do exactly one thing and not bleed into other, unrelated areas. The smaller a PR, the fewer changes are likely needed, and the quicker it will likely be merged. For larger or more impactful PRs, start a thread in [GitHub Discussions](https://github.com/Frameleaf/frameleaf-app/discussions) first to discuss your plans. Fill out the entire template when opening a PR.

## Finding work

If you are looking for something to work on, look for discussions and issues with a `good-first-issue` label. If none of them fit your skill set, ask in GitHub Discussions and we'll help you find something.

We usually do not assign issues to new contributors, since a PR is often never opened. Ask first if you're worried about putting a lot of time into an issue and ending up with a duplicate PR.

### Opening new issues

If you find bugs or other problems while working on something, open an [issue](https://github.com/Frameleaf/frameleaf-app/issues) if none covers the problem yet. To make it easier to debug and fix, fill out the whole issue template.

## Use of generative AI

We ask you not to open PRs generated with an LLM unless you fully understand and have verified every change. Even a one line change can have significant impact. If it's non-trivial for us to verify that a change works and you don't show that you understand all its implications, the PR is not worth reviewing.

If you use an LLM to translate a PR description or title, that is fine. Stick to the PR template and keep the text concise.

LLMs must not be used to fix GitHub issues labelled good first issue. Those issues are learning opportunities for new contributors, and PRs that automate them will be closed.

Misrepresenting LLM use, contribution farming (automated low-effort PRs), or repeatedly hitting auto-close rules may be grounds for a block at maintainer discretion.

## Non-code contributions

If you want to contribute to Frameleaf but you don't feel comfortable programming in our tech stack, there are other ways you can help.

### Translations

Translations live in the `i18n` folder. Corrections and new translations are welcome as pull requests.

### Community support

If you like helping others, answering questions in GitHub Discussions is always appreciated.
