# Frameleaf NAS packages

`node packaging/nas/build.cjs RELEASE frameleaf-vX.Y.Z-N qualification-receipts.json OUTPUT` builds the DSM SPK, the TrueNAS Community app source, and the Unraid Community Apps XML templates from one certified Frameleaf release. Before writing any output it runs the shared release-bundle validator, checks all `SHA256SUMS` entries against the asset hashes in the signed release manifest, verifies every application image signature and exact release attestation with the committed `cosign.pub`, and reads the exact successful build and migration evidence from GitHub. Install Cosign and the server workspace dependencies first; set `GITHUB_TOKEN` for authenticated GitHub reads when required. `release-manifest.json` and `nas-manifest.json` are release assets; keep both with the generated packages. Never replace a digest with `latest` or `release`.

The current repository's `server/src/fork-schema/supported-versions.json` has `externalProductionGate: required`, covering the fork handoff in the opposite direction. No Immich or older Frameleaf source is certified for NAS import. `certified-sources.json` contains only the migration version allowlists; these become part of the signed release assets. Both lists are empty until reviewed source versions are selected. Selecting a version does not qualify it.

Qualification receipts are supplied separately after the release images exist. For each allowlisted version, `qualification-receipts.json` contains `{version, evidence: {commit, path, digest}}` under `officialImmich` or `priorFrameleaf`. The immutable `packaging/nas/qualification/<name>.json` report binds `sourceVersion`, exact `targetServer` and `targetPostgres` digest references, `environment: sanitized-production-shaped`, `schemaVersion: 1`, and passing `preflight`, `backupRestore`, `migration`, and `rollback` checks. Its `run` and `sourceCommit` identify the separate trusted `.github/workflows/nas-qualification.yml` run. That run must contain a successful `NAS qualification (<family>, <version>)` job with successful `Preflight`, `Backup and restore`, `Migration`, and `Rollback` steps.

Each report must also have a Frameleaf-key Cosign attestation on its target server digest using predicate type `https://frameleaf.app/attestations/nas-qualification/v1`. The packager verifies the exact signed report, its immutable content hash, its target digests, and its successful run at the qualification workflow's own commit. The release build still requires its own exact source commit. Release commit R, later qualification run Q, and report-storage commit C can therefore differ without changing R or its signed bundle. The qualification workflow, real runs and signed receipts remain open gates; synthetic roundtrip jobs and unsigned reports cannot satisfy them. Do not edit generated release assets or bypass `build.cjs`.

## Synology

DSM 7.2.1 or later with Container Manager 1432+ and a 64-bit x86 or ARM host is required. The SPK contains a Docker Project with server, PostgreSQL 14, Valkey and optional CPU ML. The wizard asks for pre-existing media/database directories, a web port, a database password, and ML choice. Container Manager must be able to write both directories; the Compose bind mounts refuse to create missing paths. Data is outside the SPK target; uninstall leaves it in place. Upgrade requires confirmation of a consistent database and media backup. The SPK's `INFO`, resource worker, wizard, scripts, icons and Compose are in `synology/`. The [Docker Project worker](https://help.synology.com/developer-guide/resource_acquisition/docker-project.html) acquires at `WHEN_POSTINST`, which Synology defines as [before the postinst script](https://help.synology.com/developer-guide/resource_acquisition/timing.html). `preinst` stages a private `.env` under the documented [`SYNOPKG_PKGINST_TEMP_DIR`](https://help.synology.com/developer-guide/synology_package/script_env_var.html) extracted payload; it rejects an absent or unexpected staging layout. On upgrade it copies the retained configuration into that new payload. It never assumes the installation target exists before payload transfer. After the installer transfers the staged payload, the worker can build with the wizard values, and `postinst` persists the new configuration afterward. Missing values abort Compose configuration. **DSM 7.2.1+ qualification remains open:** verify that the installer preserves the staged `.env` through payload transfer, then confirm fresh install, worker acquisition, upgrade and recovery before submitting the SPK.

## TrueNAS

Copy the rendered `truenas/ix-dev/community/frameleaf` directory to a current fork of `truenas/apps`. Vendor the current matching library as directed by its contributor guide, run the catalog render and install tests, and submit a PR to the `community` train. The app uses independent media and PostgreSQL datasets, a dedicated internal network, optional ML, and a web portal. Keep the Frameleaf PostgreSQL 14 digest; the current upstream Immich catalog's PostgreSQL 18 image is not a compatible shortcut for this package.

## Unraid

The generated XML files belong on a versioned `nas-catalog` branch of `Frameleaf/frameleaf-app`, with `ca_profile.xml`. Create a user-defined `frameleaf` Docker network. Install compatible PostgreSQL 14 and Valkey containers on that network using the manifest's pinned images, then install Frameleaf Server and optionally Frameleaf Machine Learning. Use separate persistent paths for `/data`, PostgreSQL data, and ML cache; enter the same generated database password in both containers. Only port 2283 needs a host mapping. Validate and scan the repository in the Community Apps submission portal after publishing the XML. Digest pins mean an update requires a new reviewed catalog commit.

## Migration and rollback

Migration is opt-in and only from versions in the release manifest's explicit allowlist. The first intended Immich source is exact v3.1.0 after external production-shaped qualification; later Frameleaf sources require their own recorded compatibility result. Refuse all other source versions, PostgreSQL major versions, schema ledgers, or extension sets until tested; direct PostgreSQL 18 to 14 volume reuse is forbidden.

1. Record the source version, image digest, PostgreSQL version/extensions and migration ledger; verify the source is in the target release allowlist. Record all media roots, external libraries, database paths, users and permissions. Estimate target free space before copying.
2. Enter source maintenance mode and stop API, microservices, ML and background workers. Create mutually consistent, immutable PostgreSQL and media checkpoints; verify the backup file and snapshot IDs and test restore on a disposable clone. Keep the source stopped until the target is accepted.
3. Restore the database into a fresh PostgreSQL 14 target. Copy or snapshot media into the target's `/data` path, preserving bytes and ownership. Never start a second application stack against the same live database directory. Preserve the old stack and both checkpoints.
4. Start the target at the pinned version, with one server instance for migrations. Verify authenticated login, user and asset counts, sample original and derivative checksums, albums/permissions, background jobs and ML. Record exact source/target digests and results. For a large library, compare full media manifests and database table counts before acceptance.
5. If anything fails, stop the target and restore **both** PostgreSQL and media from the same pre-migration checkpoint. Do not downgrade the new database in place or replay only one side of the backup pair. Resume the source only after its original state is verified.

The packager and local fixtures validate structure, not platform behavior or a customer's installation. Release qualification requires real Synology, TrueNAS and Unraid install, restart, update, failed update, retained-data uninstall, restore, and sanitized production-shaped migration/rollback runs. Submit listings only after those receipts are reviewed.

## Focused validation

Run `node --test --test-concurrency=1 .github/frameleaf-release.test.cjs .github/verify-release-bundle.test.cjs packaging/nas/build.test.cjs` with server dependencies and Docker Compose available. This runs no containers. Set `TRUENAS_LIBRARY` to the matching catalog `base_v2_3_4` directory to include both ML render modes using its real Python library; that check also requires the library's Python dependencies. The fixtures fake signature and GitHub responses to exercise acceptance and rejection paths; they are not certification receipts.
